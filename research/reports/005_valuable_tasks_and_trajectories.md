# 什么是有价值的任务，什么是有价值的任务轨迹

团队判断口径 v1 · 2026-09-18

用途：帮助团队判断真实企业会话中哪些事情值得关注、哪些经历值得沉淀、哪些经验应该生成或更新 skill。本文不展开实验设计，也不制定未经校准的分数与次数门槛。

## 1. 建议采用的定义

**任务：在具体情境与约束下，为某个使用者或业务对象达成可辨认结果的一次工作单元。** 结果可以是交付物、决策依据、系统状态变化或问题解决，不要求一定有文件、工具调用或多轮对话。

**有业务价值的任务：完成后能够推进真实工作、减少实际负担或避免有意义损失，并能说明谁受益、怎样受益的任务。** 任务尚未做成，也不影响它值得被解决。

**值得纳入 skills 沉淀范围的任务：有业务价值，而且其中的方法、判断或约束具有可信的未来复用机会，保存后有理由帮助未来执行。** 复用可以发生在同一个人，也可以发生在组织内，不要求所有人都能用。

**任务轨迹：围绕一个任务及其目标变化，实际发生的请求、行动、产物、反馈和修订之间的有序关联记录。** 它记录发生了什么，而不是事后编写的标准步骤。

**有沉淀价值的任务轨迹：能够从可追溯记录中提取至少一条有依据、适用条件可说明、可改变未来执行或判断的经验，或者为已有经验的有效性与适用边界补充可信证据的任务经历。** 不要求整体成功，也不要求每次都产生新规则。

以上是综合下文研究后，为本项目提出的工作定义，不是某篇论文的原句或学界统一标准。最重要的区分是：**值得做、值得学、值得新建 skill，是三次不同的判断。**

## 2. 研究给了哪些依据

| 来源与阅读范围 | 可以借鉴的认识 | 对本项目的边界 |
| --- | --- | --- |
| [NN/g：Task Analysis](https://www.nngroup.com/articles/task-analysis/)，全文 | 围绕用户目标分析任务、子任务和条件化执行计划 | “发了几条消息”不是任务定义；本文的企业价值标准是我们的综合判断 |
| [Leno 等：从未分段 UI 日志发现候选例程](https://arxiv.org/html/2008.05782v2)，方法与结果相关章节 | 噪声可能夹在任务之间或内部；分段和候选选择是不同问题 | 高频或长模式的识别不等于商业价值；UI 操作挖掘规则不能直接搬到自然语言会话 |
| [OCEL 2.0 官方说明](https://ocel-standard.org/)，事件、对象与关系定义 | 事件关联具体对象，角色和对象关系也应保留 | 给任务对象关联提供依据，不能靠事件关联自动证明任务成功 |
| [Agent Workflow Memory](https://arxiv.org/html/2409.07429v1)，方法与分析 | 从经历中归纳可在其他任务中使用的工作流 | 可复用单元可以是子流程，而不是原任务全文 |
| [ReasoningBank](https://arxiv.org/html/2509.25140v1)，§3、§5.2、局限 | 成功和失败经历都能提供经验；其成败标签来自模型判断 | 模型判断是代理信号；失败能否被有效利用取决于提炼方式，不能一股脑加入 |
| [Trace2Skill](https://arxiv.org/html/2603.25158v1)，§2 | 区分成功经验提炼与失败分析；分析失败时检查轨迹和产物，缺乏有效归因的记录不进入补丁池 | 有日志不等于有足够依据写出修复规则；企业通常没有论文环境中的标准答案 |
| [AutoSkill](https://arxiv.org/html/2603.01145v2)，§3.4、§4 | 从用户要求提炼持久程序、约束与偏好，并作新增、合并或丢弃决策 | 稳定规范不一定要来自成功执行；但规范要求与已经验证的执行经验应分开 |

这些来源共同支持按目标、行为、结果和可复用知识分析会话；它们并没有提供一套可以直接套用到本企业的统一“价值分”。

## 3. 判断任务价值：先看实际用途，再看沉淀机会

### 3.1 是否是一件能辨认的任务

团队应能用一句话说明：**谁要在什么条件下，对什么对象完成什么，结果将用于什么。**

例如，“根据本月两张销售表，按公司区域口径形成供经营会使用的差异说明”是一件可辨认的任务。“讨论一下销售”“继续”“请认真分析”分别可能是模糊话题、续接指令或要求，单独看不足以确定任务；结合上下文后可能归属于清晰任务。

接受条件可以随着澄清逐步形成，不要求第一句话就写成完整规格。探索性工作也可以是任务，例如“比较三种方案，形成供负责人决策的取舍说明”；结果的用途与判断维度比唯一正确答案更重要。

### 3.2 是否有真实业务价值

| 价值来源 | 团队应能说明的具体事实 | 不能拿来代替的信号 |
| --- | --- | --- |
| 推进交付或决策 | 结果给谁使用，支持哪个交付或决定 | 标题听起来很专业 |
| 减少重复负担 | 经常需要重复整理、解释、对齐或检查什么 | 消息数量多 |
| 减少错误和返工 | 哪类错误会影响实际结果，什么检查能避免 | 用户语气激烈 |
| 保留稀缺经验 | 专家掌握了什么可说明的方法或条件 | 任务步骤长 |
| 保持组织一致性 | 哪些业务口径需要在多人或多次执行中一致 | 很多人讨论同一话题 |

至少要有一个具体价值理由；重要性不足以从聊天文本看清时，保留“价值待确认”，不让模型凭空判断业务影响。

高频可以放大累计价值，却不是价值本身。同一份报告改十遍，是一次任务的多次返工；每周为不同周期做一次报告，才是多个独立实例。低频但影响大的异常处理也值得关注，不应因未出现五次而排除。

### 3.3 是否值得为 skills 沉淀

业务价值成立后，再判断以下三点：

1. **存在复用机会。** 有周期性工作、相似对象、同角色任务，或明确会再次遇到的条件。可以只有一次记录，但要说明未来在哪里用；“模型觉得通用”不是充分理由。
2. **有可以保存的方法。** 包含条件化步骤、判断标准、核对办法、组织约束、有效模板或错误规避。只有一次具体答案，通常不够。
3. **保存会带来实际帮助。** 可以少解释一段组织规则、少摸索一条路径、少犯一种错误，或更稳定地符合约束。方法不必在学术上新颖，稳定封装常规流程也可能有用。

不要求复杂、多轮、使用工具或全自动。一个包含关键组织口径的单轮答复，也可能比冗长的通用建议更值得沉淀。反过来，一次重大但完全不可迁移的交付仍有业务价值，只是未必应该进入技能库。

现有技能已经覆盖时，任务仍然有价值，但新建技能的理由不足；优先复用、补充证据或修改已有能力。

## 4. 判断轨迹价值：记录必须支持我们想学的那条经验

### 4.1 轨迹需要保留的关系

| 内容 | 要回答的问题 |
| --- | --- |
| 目标与对象 | 哪一件事？处理哪份数据、哪位客户、哪个交付？ |
| 约束及变化 | 原先要求什么？后来是纠错还是新增要求？ |
| 实际尝试 | 做了哪些可见操作或内容修订？不能用“准备做”替代“已经做” |
| 产物与观察 | 得到什么版本、工具结果或业务状态？ |
| 反馈指向 | 用户针对哪版、哪一步、哪条规则提出反馈？ |
| 结果状态 | 完成、部分、失败还是未知？哪些方面接受了、哪些方面核验了？ |
| 来源与范围 | 经验依据在哪里，适用于什么角色、环境、技能版本？ |

轨迹可以包含分支和回退，不必是一条无分叉直线。不需要模型不可见的内部思维链；可见行动、交互、产物和结果足以作为研究对象。

### 4.2 什么样的轨迹足以沉淀

建议按四个条件检查，缺失时具体说明缺哪一项：

- **归属清楚：** 可以确认记录围绕哪个任务或子任务，而不是把相邻消息机械拼接。
- **依据足够：** 关键经验能指回真实请求、行动、反馈或产物，且依据足以支持该经验的强度。
- **经验具体：** 能说明未来在什么条件下应该做什么、检查什么、避免什么，或现有规则的适用范围怎样变化。
- **有后续用途：** 这条经验能用于新技能、已有技能修改、个人约束或覆盖证据，而非只是重复原始故事。

“依据足够”是相对于具体经验而言，不要求每条轨迹都全量记录所有事件。例如用户明确要求“这类报告始终保留原始分类”，足以保存该用户的规范；但不足以证明系统已经按此执行成功。整体失败的任务也可能包含一个独立检查通过的子步骤，可以只沉淀这一段。

### 4.3 不同轨迹能支持不同强度的结论

| 实际记录 | 可以保留什么 | 不可以升级为什么 |
| --- | --- | --- |
| 用户明确给出长期有效的规范，尚未执行 | 规范或偏好证据，标明来源和范围 | 已验证成功的方法 |
| 行动、产物和相应检查齐全，达到目标 | 有依据的成功程序候选 | 对所有未来任务都有效 |
| 失败后修正，修正处有明确检查 | 条件化纠错或恢复经验 | 每个修改都是成功的原因 |
| 明确知道某种尝试不满足某项要求，尚无解法 | 有限范围的反例、排除条件或诊断经验 | 已经知道正确解法 |
| 只知道失败，不知道失败位置和条件 | 待分析材料；若重复可提示能力缺口 | 一条确定的规避规则 |
| 没有最终验收，但局部事实充分 | 已核实的局部经验，整体结果未知 | 整条任务成功 |
| 使用旧 skill 顺利完成，没有新知识 | 现有版本的使用与覆盖证据 | 必须生成一个新版本 |
| AI 自称“已检查”、无可查结果 | 未证实声明 | 真实核验通过 |

因此，**结果未知不等于整条无价值，结果成功也不等于每一步都值得照搬。** 要围绕具体经验判断证据，而不是给整段聊天贴一个成功标签后全部吸收。

## 5. 一个贯穿例子：为什么有价值任务与有价值轨迹不一样

以下为构造示例，不是本项目数据。

用户需要每月按公司客户分类形成经营汇总。该任务有明确使用者、周期性需求和组织口径，值得关注，也有 skills 沉淀机会。

**记录 A：** 只有“生成月报”和“已完成，见附件”。没有附件内容、实际过程或反馈。这是有价值任务的一条信息不足记录；不能据此提炼已经成功的企业月报方法。

**记录 B：** 初稿合并了两个必须分开的类别；用户指出具体记录和规则；系统按规则修改；汇总核对通过，用户接受。它能够支持“这些类别必须保留，汇总前后按映射核对”的条件化经验。值得提炼的是这条业务规则及核对方法，不是所有改稿动作。

**记录 C：** 系统中间出现网络超时，反复说“马上好”，后来交付正确。轨迹可能包含可用主流程，但网络失败本身没有可靠原因，不足以生成“必须重试三次”的规则。

**记录 D：** 已使用月报 skill v2，用户补充特殊客户类别，核对后确认 v2 漏掉该条件。它更适合成为 v2 的修改依据，而不是另建一份几乎相同的月报 skill。

四种记录对应相近的任务价值，却有不同的学习价值和产物去向。

## 6. 团队可直接采用的判断顺序

| 顺序 | 判断问题 | 处理结果 |
| --- | --- | --- |
| 1 | 能否辨认一件具体工作及用途？ | 不能：联系上下文或留待澄清；不要直接建技能 |
| 2 | 做成后给谁带来什么实际帮助？ | 不清楚：价值待确认；高频不能替代解释 |
| 3 | 哪个方法或条件可能再次使用？ | 没有：可以完成本次服务，不必沉淀技能 |
| 4 | 当前记录究竟支持哪条经验？ | 分开规范、执行经验、反例、猜测和未知 |
| 5 | 这条经验会改变下次什么行为或判断？ | 说不清：暂存或去除空泛总结 |
| 6 | 存量技能是否已覆盖？ | 新建、修改、个人覆盖或只补充证据 |

一个候选经验可以用这句话检验是否具体：

> 当【条件】出现，为完成【目标】，应采用／避免【具体方法】，因为本次【来源证据】支持这一判断；目前只适用于【范围】，尚不确定【缺失项】。

不是每项都必须写成长段；如果只能填成“当用户有需求时，要认真分析并检查结果”，说明还没有提炼出可操作经验。

## 7. 对当前系统口径的直接影响

1. 把回合数与独立任务数分开，重试不增加任务频率。
2. 长度、工具数和轮次只作为值得查看的信号，不直接决定价值。
3. 任务是否重要与轨迹是否足以学习分别记录，避免有价值需求因暂未解决而消失。
4. 不再只问“最终成功了吗”，还要问“哪条经验有证据、证据支持到什么程度”。
5. 新建 skill 前先比较存量；优先补充或修改，减少同类技能堆积。
6. 记录已用 skill 的版本和使用结果。无新规则的成功也可提供覆盖证据，有失败不代表一定要改正文。

对前轮口径的补充：偏好优先放个人层，是本项目减少碎片技能的产品建议，不是学术上“偏好不属于技能”的定论；完整成功轨迹是强来源，但不是唯一允许的知识来源。明确的组织规范和有依据的局部反例也应有沉淀通道。

本轮完成的是文献支持下的团队定义，不是效果证明。没有把这些条件换成任意权重或统一分数，也没有开展实验或修改系统。
