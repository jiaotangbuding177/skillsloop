# 新数据包能否支持真实会话到 Skills

日期：2026-09-26。范围：本地读取与结构统计、有限正文抽查；未连接生产库、执行导出脚本、调用外部模型或生成技能。

## 判断

**能提取真实企业成员的用户输入；联合上一份原始导出，可以取回用户与 AI 的双侧消息，并准备一次真实来源的技能生成案例。但新包本身不是完整对话集，两份数据合并也还不能宣称完整任务轨迹与技能生命周期已经恢复。**

已有材料足以开始案例筛选与人工核对，不必等待全量工具日志。首例优先选择正文自足、目标与修改理由明确的任务。恢复顺序、输入完整性和技能执行证据必须逐例检查。

企业成员的会话不等于企业业务任务；真实来源的 skill 候选也不等于经过独立任务验证的有效 skill。

## 3. 会直接影响轨迹质量的问题

### 3.1 清洗误删短反馈

clean.mjs 在去前缀后删除不足4字且不含字母数字的内容。354条被删记录中，174条的原始正文就满足这一短文本条件；包括确认15、继续12、可以8、好的8、是的7、同意2、谢谢1。

这些词需结合上下文解释：确认不一定代表验收，可以也不一定代表业务成功；但一律删除会损害动作授权、修订承接和接受证据。**以 user_messages.json 为底稿，清洗生成视图并保留原文引用，短反馈作为独立事件保留。**

### 3.2 序号与时间尚不能直接互换

8,026条用户消息中3,952条采用 `sessionId:msg_N`，分布在875个会话；其中562个会话有两个以上这类用户消息。按时间排序检查，相邻序号下降出现90次。这是90个逆序相邻对，不是90个会话，也不能据此断定时间或序号哪一个错误。

本地源码 `enginering/insightweaver/apps/api/src/zclaw/zclaw.service.ts:16924` 显示：读取不到远端createdAt/timestamp时会以当前时间兜底。这提供了需检查时间语义的理由，但不是对生产逆序原因的证明。远端msg_N的生成语义也尚未核验。

177个会话满足“至少3条本包用户消息且旧包trusted消息都采用msg_N”；其中153个没有记录到files元数据。这只是候选筛选集合，不能称153条完整有效轨迹。首例可先结合用户时间、序号及语义承接人工核对；批量恢复需要原始事件顺序或远端日志支撑，不能依赖JSON文件行序。

### 3.3 没有附件元数据不等于没有附件依赖

抽查发现，无files字段的会话正文仍会说“翻译这个文件”，助手也会说明读不到PDF内容。因此候选筛选必须同时检查正文依赖；缺材料时保留UNKNOWN/输入缺失，不把通用建议当作任务完成。

### 3.4 关键词统计不是轨迹聚类

analyze.mjs 对每条用户消息进行多标签正则匹配；同一任务的多次修改会反复计数，同一消息也能命中多类。“合同275条”不能直接解释为275个独立合同任务。样本片段还截断了正文并丢失消息/会话ID，不适合直接用于证据归纳。

### 3.5 使用请求与执行回执必须分开

skill_invokes 在清洗前匹配“请使用技能……”；只证明请求。不能据此分流为已验证UPDATE，更不能假定当时加载的技能版本。助手说“技能已创建”也不是文件存在、注册成功、实际读取的证据。

### 3.6 数据需要二次脱敏

有限抽查出现未完全遮盖的凭据文本；一个保守API-key形态扫描在4条用户消息中命中疑似未遮盖值，并非有效性验证或全量安全审计。研究记录不复制值。真实模型生成前应处理所选案例正文、工具输出和附件中的敏感字段；不直接把整包发送到模型。

## 4. 已找到的真实案例线索

### 案例A：方案修订→明确要求沉淀→再次提出任务

受控本地定位：旧包/新包共同session ID `conv_59a22e8bccac`。5条用户消息、5条助手消息；用户msg_1/11/13/15/31的时间与序号递增一致。这里只是局部一致性核对，助手原始时间仍缺失。

| 观察阶段 | 去标识摘要 | 可提炼的证据 |
| --- | --- | --- |
| 初始目标 | 用户要求依据销售方法设计摆摊方案 | 存在具体交付目标，但条件不足 |
| 初次回答 | AI直接给出方案 | 有方法选择可供追踪 |
| 用户纠正 | 用户指出应该先问经营内容再设计 | 明确的流程纠错，比简单“不满意”更可解释 |
| 补充条件 | 用户给出品类、地点、目标与顾虑 | 需求条件发生具体化 |
| 修改及接受 | AI修改，用户认可并要求沉淀skill | 有显式采纳意愿，不等于技能文件已落盘 |
| 再次提出任务 | 用户再次提出同类目标，AI先询问条件 | 可观察行为变化，但可能来自同一会话上下文，不能归因于skill |

适合提炼的候选经验是“方案生成前先收集关键条件，按约束组织方案”。不能无批判地固化原回答全部业务建议；其中规避管理的策略不应沉淀为推荐流程，应改为合法场地和必要许可等合规边界。

这个案例体现了真实修订链和显式沉淀需求，适合做管线诊断；但它是企业成员的个人场景，不适合作为企业业务价值的主案例。该会话消息没有技能包或版本payload；旧包仅有一条工具样本，尚未验证创建/读取链，不能称历史完整闭环成功。

### 案例B：文件翻译/风险评估的未完成片段

受控本地定位：`conv_25c0d5cc4fd4`。4用户/4助手消息，包含提醒、文件翻译和风险评估请求；助手多次表示不能提取PDF文本。

这证明会话可能跨任务，重复请求也可能来自输入缺失。不能按一个session生成一个skill，不能把重复翻译请求计为多个成功任务，也不能仅凭助手通用风险框架认定任务完成。适合作为轨迹切分和输入缺失处理的负例。

另有招聘匹配正文线索，但涉及未提供的原始简历；助手摘要不能替代简历真值，因此尚未选为可验收首例。

## 5. 到底能走到哪一步

| 环节 | 当前判断 | 开始执行时的要求 |
| --- | --- | --- |
| 会话提取 | 联合两包可取双侧正文 | ID关联、稳定用户归属、保留短反馈 |
| 任务识别 | 可以开展 | 切分换题，区分企业任务与个人/系统内容 |
| 轨迹恢复 | 局部可人工核对，批量可靠性未解决 | 核验顺序、补缺失输入，不伪造反馈指向 |
| 相关轨迹聚合 | 可以在恢复之后开展，尚未完成 | 同用户范围、按目标/方法聚合，不按关键词次数直接成簇 |
| 技能生成与封装 | 可准备真实来源的待验证候选，尚未运行 | 选正文自足案例、脱敏、证据引用、UNKNOWN正常处理 |
| 个人采纳与实际使用 | 可在demo新执行，静态导出不能替代 | 用户选择、技能文件/hash、实际读取与新任务产物 |
| 反馈修订与UPDATE | 条件性可新执行 | 绑定消费版本、反馈指向与修订证据 |
| 组织审核与跨用户复用 | 需要后续真实授权/执行 | 原提交审核流程，不把组织成员关系当发布授权 |

**本轮结论是“具备启动真实案例准备的材料”，不是“已经生成skill”或“已经验证全链路”。**

## 6. 建议下一步交付

1. 建立小范围合并视图：原始消息ID、稳定用户别名、角色、原文/去前缀视图、日期来源、序号、状态、附件/工具引用。不改源文件。
2. 选择一个企业业务且正文自足的用户，核对2—3个相关任务；另外保留一个未完成负例。单次重要方法也可保留，不为了聚类硬凑样本。
3. 逐条给出任务边界、反馈指向、成功/失败/UNKNOWN及依据；无法确认的顺序不进入强因果归纳。
4. 在现有demo生成一个证据可追溯的技能候选并由creator封装，保存各环节输入输出。随后在不复用原会话上下文的新任务中实际读取skill并交付产物。
5. 若案例依赖缺失证据，只补该会话的有序 user/assistant/tool/toolResult（含原始时间、稳定事件顺序、toolCallId/runId）及必要附件；UPDATE再补相应skill文件/版本。无需先导出全部约1.1GB工具数据。

本轮未修改demo、未生成技能、未实测成本或企业效果。以上执行步骤为后续建议。
