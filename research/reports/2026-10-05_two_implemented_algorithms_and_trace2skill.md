# 已实现的两个核心算法：轨迹恢复与工作流聚合

日期：2026-10-05。本文依据当前独立 Demo 源码解释实际机制，不把上一轮设计中的全部设想视为已经实现。本文只做源码和论文核对，没有启动新实验或训练。

## 1. 方法定位

我们的研究问题不是“如何把一段成功对话总结成提示词”，而是：**当会话包含任务交错、要求修改、失败尝试和相互冲突的完成信号时，如何先恢复可学习的任务关系，再从多条经历中归纳有适用边界的技能。**

当前原型包含两个核心算法：

1. **基于语义候选与证据约束的轨迹恢复**：模型提出任务归属和关系，程序检查来源、时间、要求版本、尝试及反馈对象，输出可以回查原始证据的标准化轨迹。
2. **基于流程兼容性与整簇约束的工作流聚合**：模型提出局部流程及两两兼容关系，程序进行保守聚类，再由模型归纳工作流，程序检查每条方法是否得到来源支持。

“启发式”指模型打分、有限搜索和贪心聚类共同构成的推断过程；当前没有训练恢复模型，没有强化学习，也没有最优性或显著增益证明。

```mermaid
flowchart LR
  A[原始会话、工具记录\n公开上下文、可见评价] --> B[模型提出任务与关系候选]
  B --> C[程序检查来源与关系\n保留要求版本及未知]
  C --> D[标准化任务轨迹]
  D --> E[模型提取局部方法\n提出流程兼容关系]
  E --> F[程序检查两两兼容\n整簇要求与依赖]
  F --> G[模型归纳工作流\n程序核对条款来源]
  G --> H[creator 封装技能候选]
```

十二阶段契约不变。阶段 2 负责提出任务及线索，阶段 3 负责恢复关系；当前实现允许它们共用一次结构化模型调用，程序仍分别检查和交付。本文第二个算法属于阶段 4；技能封装属于阶段 5。

## 2. 算法一：基于语义候选与证据约束的轨迹恢复

### 2.1 输入和输出

输入包括三类信息：

- **可见事件**：用户和助手消息、实际工具调用及返回、原始消息位置和标识、附件是否可见。
- **公开上下文**：工具说明、政策等任务执行时可以获得的资料。
- **可见评价**：用户反馈、工具回执、业务验收或演化任务的评估反馈。可以缺失，必须说明来源、评价对象和评价范围。

测试答案和隐藏任务归属不能作为恢复器的输入。演化阶段如额外提供验收反馈，需要单独声明信息条件，并给比较方法相同反馈。

输出不是一串重新排序的问答，而是每个任务的六部分：**目标和对象、要求变化、实际尝试、尝试与反馈的关系、结果证据、仍然缺失或无法归属的信息。**

可用如下形式表达一条恢复轨迹：

\[
\tau_k=(g_k,Q_k,A_k,L_k,O_k,U_k).
\]

这里分别表示任务目标、要求时间线、已定位的尝试、关系、带作用范围的结果证据和未决信息。这是对程序输出的概念化描述，不是新增的训练模型。

**标准化不等于成功，也不等于内容完整。** 一个失败或缺少附件的任务，只要忠实保存了关系、证据和缺口，同样可以形成适合学习的轨迹。系统结束整理当前可见窗口，也不代表业务完成。

### 2.2 实际推断过程

**第一步：固定原始证据。** 程序为事件建立来源索引，保留原文引用、调用标识和顺序。缺少的合同、交付物或业务结果标为未知，不生成替代内容。

**第二步：模型提出几种可能的关系。** 模型识别任务目标，允许把一条用户消息拆成多个目标分片，并提出：这句话属于哪个任务、是否回到先前任务、修改了什么要求、反馈针对哪次尝试、哪些步骤有依赖。助手的计划、进度陈述、完成声明和可见交付分别标注。

例如，“回到刚才那份合同，编号别改”可以指向先前的合同任务；“顺便写一份通知”则提出另一个任务。模型不是只匹配关键词，而是在原文和上下文中提出语义候选。

**第三步：程序约束拼接。** 当前采用宽度为 8 的束搜索：先处理任务归属候选，再处理关系候选，每一步保留若干高分合法方案。主要约束包括：

- 引用必须存在于真实输入，不能引用编造的消息或工具调用。
- 反馈和要求修改必须有相应的用户原文支持。
- 关系不能指向尚未发生的目标；有关联的片段必须有相容的任务归属。
- 依赖不能形成环；不确定的候选不能被强行写成已确认关系。

候选分数来自模型，是排序信号，不是校准后的概率。对近似同分的保留方案，只有稳定的归属和关系才确认；仍分不清的部分保留为未决。有限搜索可能错过方案，程序不能保证全局最优，也不能证明模型所有语义判断都正确。

**第四步：按维度维护要求版本。** “改成表格”只替换交付形式，不抹去“站采购方立场”和“保留原编号”。要求还区分本次任务、本次交付与未来同类任务的偏好。用户只说“以后这样做”，不能自动认定当前产物也已照此完成；如果同时要求本次应用，需要保留本次应用的依据。

**第五步：把尝试与结果接准。** 实际工具调用和可见文本交付形成已定位的尝试；正确标注的承诺或完成声明不会单独变成执行证据。已有明确调用归属时，程序可以用调用标识等信息连接实际返回；无法归属的工具记录仍保留未决。当前尝试粒度主要是单次已定位调用或可见交付，尚不是任意多步执行过程的完美分段。

“用户表示感谢”“工具返回成功”“业务验收通过”分别保留。文件写入成功只证明相应技术动作完成，不能证明合同审查正确；任务总分也不能自动给每一步记为正确。

### 2.3 具体例子：交错会话及失败修订

**以下是构造的说明例子，不是本轮新增实验结果，也不是 038 原始对话的逐字复现。** 假设合同正文已作为可见材料提供；未提供的材料仍需标记缺失。

| 轮次 | 用户输入 | 助手及实际可见事件 |
| --- | --- | --- |
| 1 | “审阅协议甲，站采购方立场，保留原条款编号，先给文本。” | 给出草稿，但把原 2.1 条写成了第 1 条。 |
| 2 | “顺便写一份周五培训通知。” | 给出通知文本。 |
| 3 | “回到协议：2.1 不要改成 1，审查结果改成表格。” | 给出新的审查表。 |
| 4 | “以后同类审查，每项附来源依据；这份也补上并写成文件。” | 声称已完成文件；实际写入调用返回“目录不可写”。 |
| 5 | “谢谢。” | 普通回应。 |
| 6 | “刚才文件没写成，重新写到可写目录，无法确认的单列。” | 重新调用写入工具，返回成功。没有独立合同质量验收。 |

恢复结果应当是：

- **合同任务**连接第 1、3、4、5、6 轮；第 2 轮属于通知任务，不夹入合同工作流。
- 合同任务的交付形式由文本改为表格；采购方立场和原条款编号保持有效。第 3 轮的纠正关联到此前编号问题。
- 第 4 轮包含“未来同类任务偏好”和“本次也应用”两种要求，不把两者混成一个无范围规则。
- 第一次写文件失败，第二次写文件技术成功；两次尝试分别保留。完成声明和“谢谢”不覆盖失败回执。
- 当前文件写入已完成，但合同审查业务质量仍未知。仍可学习明确用户要求及可见方法，而不把未知包装成业务成功经验。

如果另一句只有“刚才那个再改改”，且合同与通知均可能指代，恢复器应保留歧义，而不是仅凭距离选最近一条。

**这里恢复的是关系，不是凭空修复现实：** 它不能补出丢失的合同，不能让失败调用变成成功，也不能从一句感谢推导出验收通过。

## 3. 算法二：基于流程兼容性与整簇约束的工作流聚合

### 3.1 聚类对象不是整段聊天

一条任务轨迹可能包含多个局部方法。模型先提出流程轮廓：它解决什么目标、有哪些步骤、步骤输入输出是什么、适用条件是什么、怎么检查完成，以及哪些原始尝试支持它。

因此，聚类对象是**带要求、依赖和证据的局部流程**。不是整个会话，也不是合同等话题词。当前新链路没有使用词向量距离，也没有使用旧链路的文本相似度 0.72 阈值。

### 3.2 先判断能学什么，再判断能合并什么

程序检查每个方法的证据性质：

| 经验类型 | 允许怎样理解 |
| --- | --- |
| 明确用户规则 | 可以作为有范围的用户要求；不等同于已验证有效方法。 |
| 已执行但未验证的方法 | 正常处理，保留验证状态和适用限制。 |
| 具有具体步骤或方法验收的成功经验 | 只能在验收实际覆盖的范围内作为成功经验。 |
| 失败边界 | 需要具体失败依据及防范条件；不能把失败路径写成推荐成功路径。 |
| 已验证修订 | 需要先前失败、明确修订关系及同一可比较标准下的后续成功；不等于因果证明。 |
| 只有计划或承诺的设想 | 暂缓作为执行方法，不能靠“我会处理”扩充技能能力。 |

要求已失效、相关关系未决或结果矛盾的部分可能被暂缓。未验证的方法不被整体丢弃，以符合用户“未验证候选正常处理”的要求。

当前失败处理以识别有支持的失败边界和已有修订为主；没有实现通用的主动失败复现、根因验证和重新执行修复。

### 3.3 实际聚类过程

模型在一批轨迹中提出局部流程的两两关系：**可共用核心流程、有条件兼容、不兼容、信息不足。** 当前批次最多 8 条轨迹。模型通常以一次批量提取给出方法和兼容关系；程序的两两和整簇检查不另调用模型。

程序从单个流程开始，逐步尝试合并簇，满足三个条件才合并：

1. **边界相容**：所有者、数据用途和学习路线相容；已有技能更新必须对应同一个实际使用的技能及精确版本，不能把不同技能更新混成一簇。
2. **所有跨簇流程对都兼容**：没有明确兼容关系就不合并。甲和乙兼容、乙和丙兼容，不足以将甲乙丙并在一起；还必须检查甲和丙。
3. **整个簇的要求与依赖相容**：同名要求维度的不同取值，必须在双方流程中明确作为参数，或有明确条件分支；已经纳入的依赖不能形成环。

用论文形式表示合并规则：

\[
\operatorname{Merge}(C_a,C_b)\iff
\left[\bigwedge_{f_i\in C_a,f_j\in C_b}c(f_i,f_j)\right]
\land \operatorname{ReqCompatible}(C_a\cup C_b)
\land \operatorname{Acyclic}(D_{C_a\cup C_b}).
\]

其中，两两兼容关系来自模型提议和程序边界检查，不是一个向量相似度。该流程可描述为**带整簇约束的完全链接式贪心聚类**：完整检查跨簇配对，按当前遍历顺序选择可合并簇。它不是标准距离矩阵聚类，也不是最优分簇算法。

当前要求冲突检查依赖一致的维度名称和显式参数声明。程序没有自动学出参数，也没有通过执行证明所有参数取值都可用；语义别名和错误的兼容提议仍可能影响结果。

### 3.4 从簇到可封装的工作流

模型再批量归纳簇内流程：共用步骤写为主流程，适用条件不同的部分写为参数或分支，重复方法去重。每个方法都必须得到“纳入、重复、排除、暂缓”中的一种处置，不能悄悄遗漏。

程序检查归纳结果是否跨簇引入方法、是否重新纳入被暂缓的方法、步骤是否违反已恢复的依赖顺序。未纳入但必须依赖的步骤，要写成前提或待确认事项。每条工作流方法保留私有来源台账，记录支持它的轨迹、要求范围、依赖、检查和未知信息。

随后复用当前 creator 封装为原项目规范的 `SKILL.md` 候选，进入个人采纳与使用。聚类不授予组织共享权限；跨成员复用仍需用户提交、组织审核。

单条轨迹中的高价值方法也可以形成候选，不要求“至少出现两次”或用户明确说满意。形成一致工作流仍不等于已经验证复用价值。

### 3.5 继续上面的例子

假设同一用户、同一学习用途和同一新技能路线下另有两条经历：

- **轨迹甲**：上面的协议审查，保留原编号、按采购方立场审查、以表格交付；可见文件失败及重写过程。
- **轨迹乙**：另一份协议，同样按指定立场和原条款编号审查，但要求文本交付；没有明确业务质量验收。
- **轨迹丙**：撰写培训通知，流程为确认时间、对象和内容，再生成通知。

如果模型指出甲乙共用审查核心，且双方都把“交付形式”明确列为参数，程序允许将二者放入同一簇；否则需要明确条件分支，或保留为不同簇。通知与审查没有共同的操作核心，不应仅因同在一个会话窗口而合并。

按此机制可形成如下**说明性候选表示**，不是声称本轮模型已经生成或验证了这个技能：

> 按用户指定立场及原条款编号进行协议审查；交付形式作为参数。对该用户明确要求长期应用的“附来源依据”，保留个人适用范围。需要文件交付时，只有取得成功写入回执才能声称文件已写入；回执失败则进入重写或失败说明分支。文件成功写入不代表审查质量已通过业务验收。

其中，“协议甲”、某个目录和某个条款号是实例信息，不应无条件固定成未来技能规则。技术失败支持的是文件交付的检查边界，不能据此声称已经证明合同审查方法有效。

## 4. 与 Trace2Skill 的区别

本文以 **Trace2Skill v5，2026-06-04** 为主要对照。它不是简单摘要：已有成功轨迹分析、失败诊断和多轨迹经验合并。其采样协议按已知任务产生执行轨迹及正确性标签；成功分析归纳有效行为，失败分析可以检查产物、比较参考答案并验证修复，随后合并技能补丁。[原论文方法部分](https://arxiv.org/html/2603.25158v5#S2)、[官方实现](https://github.com/Qwen-Applications/Trace2Skill#readme)。

| 比较点 | Trace2Skill | 当前我们的原型 |
| --- | --- | --- |
| 学习入口 | 按任务采样得到的轨迹和结果标签。 | 可交错的会话事件、公开上下文与可能缺失或冲突的评价。 |
| 归纳前的关系 | 分析已给定任务轨迹内部的行为和经验。 | 先推断任务归属、要求版本、尝试与反馈对象，保留未决归属。 |
| 多经历归纳 | 从逐轨迹经验补丁出发进行层次合并，检查重复和冲突。 | 从带关系及证据的局部流程出发，检查两两兼容及整个簇的要求、依赖，再归纳工作流。 |
| 失败学习 | 包含主动检查、参考比较及修复验证。 | 区分声明与执行、失败边界与已支持修订；通用主动修复验证尚未实现。 |
| 程序约束 | 技能补丁和最终应用有程序检查。 | 在恢复关系、流程归簇和工作流条款支持三个位置做程序检查。 |

Trace2Skill 已有轨迹内分析，因此不能声称它完全不理解关系；其论文没有把混合企业会话的任务恢复作为上述采样协议下的核心问题。双方都使用模型归纳和程序检查，这些基础技术不能单独称为我们的原创贡献。[Trace2Skill 成功分析提示](https://github.com/Qwen-Applications/Trace2Skill/blob/main/analysis/success_analysis_system_llm.txt)、[论文归纳部分](https://arxiv.org/html/2603.25158v5#S2.S4)。

**我们的贡献候选是：恢复出来的任务、要求、尝试和结果关系，不只用于整理输入，还决定哪些流程可以合并、哪些经验可以进入技能，以及条款能推广到什么范围。** 这一点具有明确机制差异，但尚未证明具有性能优势或全球独有性。

合理的研究检验应固定技能学习后端和可见反馈，比较“直接学习混合输入”与“恢复后学习”，并观察关系变化是否改变条款和新任务行为；另外再比较完整方法。不能将额外提供评分带来的收益全部归于恢复算法。

补充来源核对：此前用户提供的“depends on the quality and coverage of sampled rollouts”未在本次核查的 Trace2Skill v1—v5 中找到逐字原文，不作为其 Limitations 直接引语。这延续[073 中已记录的出处待核实说明](073_rq1_trace_recovery_controlled_experiment.md)，研究动机由输入协议差异与本地数据问题支撑。
