# 最新 τ²-bench 三域实验报告：技能有帮助，也有退步，尚未证明稳定增益

日期：2026-10-05（北京时间）。

**本次拉取并核算的是 AutoSkill 强基线，不是我们新算法的成绩。** 最新结果覆盖零售、航空和电信：零售、航空的单次成功率各增加 5 个百分点，电信减少 5 个百分点；三个差值的统计区间都包含零，目前不能确认稳定的正收益或负收益。

## 1. 这次拉取和核对了什么

来源为 `skillsloop` 仓库的 `main`，固定提交 `14f5b59ab29351973429777fb013afafd15297ce`，提交时间为 **2026-10-05 07:24:36（北京时间）**。最新提交新增航空267 v1、电信268 v1，并保留零售148 v4。

原始文件、冻结技能、账本和报告已下载到[独立快照](../imports/2026-10-05_tau_remote/README.md)，没有覆盖本地旧实验。完整性检查确认三个实验目录与该提交无差异；六份正式结果重新按任务、重复编号和种子配对，保存 SHA256 和离线复算脚本。没有调用新模型、重跑评测或修改技能。

规模是**100道测试任务，每题4次，在有／无技能两种条件下执行，共800场**。其中零售40题、航空20题、电信40题。重复场次不是独立任务；不同任务还可能共享订单、预订或故障模板。

## 2. 最值得看的指标

### 2.1 有没有真正做好任务

| 指标 | 零售148 v4 | 航空267 v1 | 电信268 v1 |
| --- | ---: | ---: | ---: |
| 每组测试规模 | 40题×4次＝160场 | 20题×4次＝80场 | 40题×4次＝160场 |
| 无技能成功 | 126/160，78.75% | 54/80，67.50% | 127/160，79.375% |
| 有技能成功 | 134/160，83.75% | 58/80，72.50% | 119/160，74.375% |
| 单次成功率变化 | **+5个百分点** | **+5个百分点** | **−5个百分点** |
| 同题同次：改善／退步／持平 | 20／12／128 | 12／8／60 | 23／31／106 |
| 按每题4次均分：改善／退步／持平 | 15／7／18题 | 7／3／10题 | 10／13／17题 |
| 任务级95%收益区间 | −2.50到+12.50个百分点 | −5.00到+13.75个百分点 | −16.25到+5.63个百分点 |
| 辅助配对检验p值 | 0.215 | 0.503 | 0.341 |

这些分数看的是任务目标是否满足验收：零售主要检查实际数据库状态及相应自然语言条件；航空检查数据库状态和必须告知的信息；电信主要检查设备／网络状态，其中12/40道测试题还要求正确转人工，共48场／组。这些无法自行恢复的无服务题，不能与目标为恢复上网的数据题混用结束标准。**回复很礼貌、用户说谢谢、某次工具执行成功，都不能单独代替整个任务成功。**

本批评分均为0或1，所以平均奖励与成功率相同。全部指定正式结果有分数、没有重复任务与重复编号，配对种子一致；此前失败尝试和重跑过程另有记录，不能据此说整个实验从未发生故障。

“区间跨过零”的人话含义是：目前这些题和重复次数，还不能排除收益为零。p值只作辅助，场次之间存在同题相关性。**未显著不等于证明技能无用；也不能把+5个百分点当作已确认收益。**

### 2.2 能不能稳定做好，以及是否更慢

| --- | ---: | ---: | ---: |

| 平均耗时变化 | 约+28.3% | 约+1.5% | 约+3.6% |
| 平均对话消息数 | 25.56→26.06 | 26.55→29.60 | 54.22→47.36 |
| 平均业务工具调用数 | 7.33→7.81 | 7.80→9.66 | 16.93→15.09 |
| 原生工具显式错误数 | 23→38 | 5→8 | 5→30 |

电信的业务工具数包含客服和模拟用户双方的工具；技能文件读取不计入该数。错误数只统计工具返回明确标记的错误，不包括所有业务错误，也不能直接归因于技能。

**电信最值得注意：有技能后40道题都至少成功过一次，但4次全部成功的任务从22道降到17道。** 这说明“能碰巧做对更多题”和“稳定做好任务”是两件事。只报告覆盖率，会掩盖稳定性退步。

三域平均耗时都增加；但耗时包含网络、模型及模拟用户等待，不等于人类工时。电信工具次数减少却成功率下降，也不能据此声称效率提高；减少主要来自模拟用户侧，客服侧工具调用反而从1,059次增至1,105次。模型总费用目前无法计算。

“失败材料”不应整体删除，其中可以有正确步骤、用户规则或可靠的失败经验。问题在于这些部分能否被正确区分及关联。

读取扫描器依据工具调用或相关返回文本命中路径计数，没有检查每次读取是否成功、是否完整返回正文。航空、电信固定快照中没有原生会话sqlite或首轮提示归档，因此不能在本地重放验证。这里保留远端的**读取触发审计报告值**，不能升级为“全文已读且规则被遵循”。没有归档也不证明实际没有读取。

航空的唯一技能是退改签与退款政策核验流程；电信是包含无服务、移动数据和彩信的综合诊断流程。航空原始技能文件约7.25KB；电信正文约32.10KB，加29个参考文件，全库约62.70KB。电信其中两个参考文件确为空文件；这证明资源质量有检查空间，不证明它们造成了失分。

字节以远端Git原始内容为准；Windows换行会让本地字节变大。还原CRLF后，新两域全部31个冻结文件的SHA与原清单一致，未发现技能内容被改变。

### 2.4 哪些资源指标现在还算不出来

新航空账本有2,773条请求记录，电信有14,900条；它们包含多阶段记录，不能直接当作有技能组的成本。请求序号在重启后有重复，不能只按序号去重或用预算快照代替账本。

最终结果保留了模拟用户侧的部分token用量，客服模型、技能读取和学习侧的总用量没有完整记录；账本也没有计费用量和金额。因此**总token、真实金额、每成功任务总成本，以及技能是否省钱，当前均未知**。原结果中的空费用或消息费用0不能证明实际免费。详细分项见[资源与读取审计](../reviews/tau_remote_2026-10-05/resources_and_read_audit.md)。

## 4. 从真实案例看，什么环节发生了变化

### 4.1 航空改善：工具允许写入，不代表符合改票政策

任务29，第0次：用户希望把行程目的地从LGA改到JFK。无技能组直接用改票工具换航段，工具允许写入，但政策禁止直接改票改变目的地，最终数据库不符合验收，0分；用户感谢没有改变结果。有技能组先说明该限制，取得确认后真正取消旧票并重新订票，最终通过，1分。

冻结技能包含“政策不允许时说明限制，并提供允许的取消重订路径”。这条执行与技能内容相容，是一条有意义的正例；由于两组原本都有政策，也不能由单对证明是哪条技能产生了因果作用。

### 4.2 航空退步：操作完成了，却没有满足最便宜的要求

任务16，第1次：用户要求行程顺延一天，选择最便宜的普通经济舱，并退差额。无技能组选了207的航班组合并实际改票，成功；有技能组在可见搜索结果已包含207方案时，选择了216方案并称它最便宜，实际改票完成，用户也表示满意，但最低价目标没满足，0分。

这是候选比较和目标满足问题，不能把一次写工具成功或用户满意当作整任务成功。技能要求核实价格，是否需要更具体的组合比较流程是后续假设，尚未证明补条款可以解决。

### 4.3 电信退步：规则写对了，执行仍漏了关键一步

选取移动数据上网任务，重复第0次，同配对种子670487。用户在国外，手机有节流设置及漫游相关问题。

| 对照 | 实际可见执行 | 最后验收 |
| --- | --- | --- |
| 无技能 | 读取网络状态，发现手机本身的数据漫游没有打开；区分“账户允许漫游”和“手机开关已打开”；让用户打开手机漫游，再关闭节流设置；测速约275Mbps、Excellent。 | 成功，1分。 |
| 有技能 | 查到账户允许漫游，但没有检查并打开手机本身的数据漫游；只关闭节流设置；后续测速仍无连接，最终转人工。 | 未达到本题上网目标，0分。 |

冻结技能已经明确写了：**账户漫游开启，而手机漫游关闭时，要单独打开手机开关并复核。** 因此，这条失分不能作为“AutoSkill没生成正确规则”的证据；它首先暴露了本次消费者没有完整执行规则。

有技能组的助手还公开自述读取受到上下文限制，但原生读工具返回未上传，本轮不能证明真实发生了该限制，更不能拿它替代已观察到的漏步事实。

另外核查了“技能是不是把Excellent测速要求错误泛化”这一解释：本例用户目标和验收确实要求相应速度／质量，该解释在本例不成立。转人工在某些故障题可以是正确动作，但**并不自动满足这道恢复上网题的目标**。

具体消息位置、原始文件及其他案例见[协议与案例审计](../reviews/tau_remote_2026-10-05/protocol_and_cases.md)。本例证明存在一条真实漏步路径，不能单独证明总体−5个百分点的因果来源。

## 5. 与我们的轨迹研究直接有关的新发现

### 5.1 输入适配丢掉了双边动作关系

电信模拟用户会实际调用工具操作手机，不是只回答一句“已经操作了”。70条采集经历包含**866次用户侧工具调用、477次客服侧工具调用**。

当前基线转换脚本保留用户正文，保留客服调用，但没有把866次用户侧调用写进学习文本；部分工具返回仍在，却失去了对应调用的标识。航空还有5段较长工具正文被截断。

这属于**本实验的输入适配损失**，不能概括为AutoSkill作者方法天然无法理解用户动作。它也不等于用户操作完全不可见——正文和部分返回仍然有线索。

对我们的启示很具体：标准化轨迹应在可获得日志的前提下保存双方的调用、返回和状态变化，并恢复“客服指引→用户实际操作→复查结果”这条关系。无法观测的真实企业操作仍标未知，不能从公开benchmark的完整日志反推企业历史也一定有这些资料。

### 5.2 评价已经存在，却没有进入学习文本

航空和电信原始采集都有结果，但学习文本仍以对话和工具内容为主，没有明确任务成败标签。失败经验和正确步骤可以共存，归纳器需要区分具体对象、条件、尝试及评价范围。

**这支持继续研究过程与结果的关联，但没有证明“加评分就会提高分数”。** 给新方法额外反馈时，强基线也需要同等反馈条件，才能分开信息收益与关系算法收益。

### 5.3 生成问题与执行问题要分开

同一失分可能来自输入丢信息、归纳时推广过度，或消费者没有执行已有规则。上面的漫游案例属于第三类的具体观察。

我们的轨迹恢复应把“查到账号支持漫游”“手机实际开启漫游”“测速恢复”分开绑定，工作流聚合再处理它们的依赖与适用条件。但如果正确技能仍没有被消费者遵循，仅重复生成相同条款未必能改善成绩。需要测量条款是否实际影响新任务行为。

## 6. 本轮对远端报告的更正和结论边界

| 原报告或展示用语 | 本轮按原始数据的核对结果 |
| --- | --- |
| 航空演化均分约0.72 | 19/26＝**0.730769**。 |
| 电信演化52成功＋18失败、均分约0.75 | 原始结果与学习清单均为**53成功＋17失败，0.757143**。 |
| 新两域技能“真实读取率100%” | 报告的读取触发率100%；成功全文读取和实际遵循尚不能独立证实。 |
| 电信只有环境状态评分 | 主要检查环境状态；部分正式题还含特定动作检查，必须按每题实际验收理解。 |
| 配对报告标题中的v4／frozen_skills_v2 | 是沿用脚本的旧展示标签；新两域实际是各自v1冻结库，按清单和原结果解释。 |

更正另存，没有改写远端历史报告和原始结果。

本实验使用固定v1.0.1任务、指定模型资源和本地适配。航空、电信采用官方拆集，但存在共享预订对象或故障组件；这不是额外偷看测试的证据，却限制了“全新实体／全新模板泛化”的主张。零售还有旧批次测试接触和适配历史。不能拿这些绝对分与其他论文排行榜直接排名。

**当前能成立的结论：AutoSkill技能库已经产生可测的正负变化，整体收益尚不稳定；电信移动数据与消费漏步值得优先诊断，学习输入的双边动作及评价关系也有明确缺口。**

**当前不能成立的结论：我们的恢复算法已经提高分数、AutoSkill在所有领域有效或无效、技能读取已经保证执行、费用已经下降。**

建议下一步先固定可见输入和消费条件，做小规模的关系恢复对照；把输入适配修复与恢复算法的收益分开。在此之前，不依据少数失败就同时改学习器、消费者和评分，也不通过选择性重跑覆盖负结果。本轮未执行这些后续实验。
