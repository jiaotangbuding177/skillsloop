# Trace2Skill 企业表格会话技能生成：总实验报告

日期：2026-10-06。范围：固定历史会话→候选技能生成与打包。

**本轮实际生成1个“表格生成与核验”技能包。直接学习组完成，任务与轨迹恢复组在第四条会话的关系校验处停止，没有生成第二个技能包。两组完整效果比较未完成。**

全批共19次实际模型请求，已报告265,639 tokens；另有1次超时请求的实际用量未知。本报告保留失败，不把格式通过等同于技能有效。

## 2．两条链路与实际完成情况

**直接学习组：**完整会话和工具记录→提炼带来源与条件的经验→官方局部补丁→合并→程序更新技能→检查与打包。

**恢复组：**同样的会话和工具记录→模型提出任务、消息归属和关系候选→程序核对来源、角色、同任务关系、环路与歧义→同一经验分析→同一官方生成器。

恢复后的分析器仍看到全部原文、选中关系和未决候选。原始导出按角色分组，程序没有把展示相邻关系当真实回合或时间先后。

### 官方链路的复用边界

本轮应称为**企业历史输入适配＋Trace2Skill官方离线技能更新核心＋OpenClaw脚本封装**，不能称完整原版端到端复现。

2026-10-06进一步更正初稿归因：原论文的创建路线确实先由模型仅凭参数知识生成弱初稿；本批改用手写22行初稿，没有执行该初始化。公开CLI要求既有技能目录不代表原方法没有初稿步骤。具体证据及重新完整运行的输入缺口见[原版初稿与运行核查](2026-10-06_trace2skill_native_initialization_and_execution_boundary.md)。本批原结果保持，不计为新完整实验。

| 环节 | 本轮实际做法 |
|---|---|
| 初始技能 | 我们先写了一份22行弱草稿，预定技能名称和表格主题。官方更新器读取该目录再修改；不是由模型从空目录自主决定技能数量、名称和结构 |
| 成功/失败处理 | 没有调用官方成功/失败分析入口；使用我们写的结果中立经验提示，因为企业历史整任务结局未知 |
| 局部补丁和合并 | 实际调用官方编排、解析及合并代码，但改写了局部提议提示，合并提示增加未知结果边界 |
| 轨迹聚类 | 本轮没有语义轨迹聚类或跨会话工作流聚合。6份记录按每2份分3批，是分批提议；补丁合并不能当成轨迹聚类 |
| 补丁定位与修复 | 使用JSON补丁，跳过官方可选文本定位翻译，关闭LLM格式自修复、续写和多轮校验修复；仍执行最终格式检查 |
| 包装与效果 | 用OpenClaw脚本校验和归档；没有运行skill-creator智能体、技能注册、执行消费或新任务评测 |

因此本轮的输出质量属于这一适配与配置，不能外推为作者完整方法的性能结论。我们现在交付的是A直接学习组结果，恢复组未进入技能更新与封装。

## 3．生成的技能是什么

技能名：`spreadsheet-generation-audit`，中文主题“表格生成与核验”。正文较初始弱技能确有变化，新增了以下方法：

- 对比版本前建立字段和实体对应，辨别改名与真实增删。
- 保留模板公式与格式，先检查表头和数据起始行。
- 按实际须知处理缺失年份，先明确科目映射。
- 核查输入输出数量，保留未识别数据及其数量。
- 在环境可用时重算公式，检查结果与交付路径。
- 脱敏前明确短名称和重名策略，执行后检查残留。

本轮生成物只有技能说明，没有附带执行脚本。技能能通过本地OpenClaw的格式检查与打包；尚未注册个人/组织库，也未证明在新任务上有效。

具体封装过程是：把手写初始SKILL.md复制到目标目录→官方程序将合并补丁应用到该文件→调用`quick_validate.py`检查文件与YAML元信息→调用`package_skill.py`把目录压成ZIP格式的`.skill`文件。两个脚本没有调用模型，不会补全技能方法或改写正文；本轮归档仅包含`spreadsheet-generation-audit/SKILL.md`，没有references、脚本或另一次skillscreator生成。

## 4．失败在哪里，怎样处理

| 版本 | 实际中断 | 本轮处理 |
|---|---|---|
| v1 | 第二条恢复给了真实关系端点，却漏填冗余来源索引 | 原失败保留。v2仅允许程序由已有真实端点补缺失索引，不改关系、理由或成功标签 |
| v2 | 第三条恢复在120秒内未收到完整返回 | 原超时及未知用量保留。v3将等待时间延至600秒，明确重发该请求1次，原请求载荷完全相同 |
| v3 | 第四条恢复输出5条“用户指向AI”的回复关系，违反契约中“AI回复用户”的关系方向限定 | 程序拒绝继续，结束本批；没有翻转关系、改提示、筛掉会话或再立版本重跑 |

v3免费重放4个已经成功的恢复/分析响应，A原包也原样复用。这些重放没有新增模型请求，不能算独立重复实验。唯一超时重发单独计费记账；总预算未重置。

第四条关系错误属于输出契约不合规；不能仅凭类型违规断言这5条自然语言关系的语义一定错误。当前程序会因非法候选使整条恢复失败，暴露了局部拒收与容错能力不足。

## 5．生成内容和恢复质量的审阅发现

审阅从原文开始，之后核对模型输出与最终技能；审阅意见没有反馈给本轮生成器。以下是定向复查发现，不是黄金集准确率。

| 发现 | 实际证据与影响 |
|---|---|
| 来源真实不保证标签正确 | A把助手对缺失须知的置零解读标成用户要求；A和B都把助手哈希比对自述标成已验证，已有工具记录没有对应证明 |
| 部分分析错学被最终合并缓和 | A最终没有固化“注册前年份必置零”，改为依实际须知；也未宣称旧哈希核查已认证。但这不能证明合并器总能纠错 |
| 最终规则仍有泛化 | A写“严禁硬编码列索引”，并将仅填叶子节点、合并区域填值等方法扩大到缺少对应前提的情况 |
| 最终文档结构有缺陷 | 新内容末尾与“工作流程”标题拼在同一行，后面初始三步重复。格式检查和打包通过没有覆盖这些问题 |
| 恢复边界有过拆风险 | 研究模板会话被分为10个任务，9条跨任务反馈未进入选中图，明确居中拒绝关系也未被选中。原文和未决关系仍进入分析，正文没有丢失 |
| 恢复并未稳定消除证据升级 | B前两条增加了部分条件限定，但第三条仍将哈希自述标为已验证，并把用户更新要求说成虚假更新；原文不足以支持该判断 |

因此，本轮可确认“候选能生成并打包”，不能确认“候选已有效”。恢复组没有最终技能，不能给出最终技能优劣或无效skills减少比例。

**初始三步为何仍在：**原始合并返回使用“替换章节内文本”操作，却没有提供要替换的旧文本。官方解析器默认为空字符串，应用器执行空串替换，将新增流程插在原标题之前，旧三步因而保留；新增内容末尾没有换行，又与原标题连成一行。这一缺陷发生在补丁应用时，ZIP包装没有改坏正文。检查器只核文件和YAML名称/描述等，不检查正文重复、标题结构或执行能力，所以仍然通过。可查[实际合并补丁](../experiments/20261006_trace2skill_ecnu/private/run_v1/A/official_intermediates/final_patch.json)、[实际修改差异](../experiments/20261006_trace2skill_ecnu/private/run_v1/A/official_intermediates/applied_diffs.patch)和[官方应用代码](../baselines/Trace2Skill/skill_evolver/parallel_evolving_agent.py)。本轮没有修原包或重新生成。

## 7．本轮结论

1. 固定真实会话在附件实体和业务结局缺失时，可以通过结果中立入口接通官方补丁、合并、应用和技能打包。本轮交付1个有真实改动的候选。
2. 当前恢复组没有跑通全部6条会话，不能证明恢复优于直接学习。失败和语义审阅已定位任务边界、关系类型契约、证据标签与局部容错问题。
3. 技能格式检查需要补充正文结构与条款适用范围检查；能打包不足以判定可复用质量。
4. 本轮没有独立新任务消费、成功率或业务价值评分，没有无效skills减少的实证结果，也没有模型成本下降的结果。
