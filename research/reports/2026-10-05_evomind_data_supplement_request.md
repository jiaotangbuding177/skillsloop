# EvoMind 真实会话：给数据方的补交清单

日期：2026-10-05。本文依据现有两份导出、本轮全量结构统计及 InsightWeaver 本地源码制定。没有连接生产数据库或 KM；本地源码与生产导出的字段已有差异，因此下面的表名、接口应先由数据方核对线上版本。

我们现在能读到会话文字，也能看到一部分文件名称和路径，但无法核验“输入文件是什么”“AI到底改了什么”“哪个操作失败后怎样修好”。本次补数的目标，是让原文字、文件、工具动作和真实结果能按同一会话串起来。**请固定现有1,466条会话的编号范围补取，不重新按今天的成员名单换一批会话。**

## 一、已经拿到什么，缺口多大

以下统计只针对整理后的1,466条主集会话，不混入19条内部用途会话或39条只有元数据的记录。

| 资料 | 现有内容及数量 | 仍缺的内容 |
|---|---|---|
| 用户输入文件 | 442条会话、938组用户正文带文件元数据，保留1,656条原出现位置的文件引用 | 原文件字节、当时版本、文件哈希。1,656是引用次数，重复引用仍在，不能称1,656个独立文件 |
| AI产物 | 14条会话、68组AI正文带文件元数据，共111条引用；另有71条会话的正文出现产物或文件位置候选 | 文件真实内容、生成后修改版本、对应哪次请求、实际生成/交付凭据。正文路径也可能指输入或参考文件，需确认 |
| 工具过程 | 57条会话有2,388次载荷内活动快照 | 原导出明确未包含约9.3万行完整工具及返回消息；快照不等于全部独立调用 |
| 原始时间与关联 | 7,439组用户正文至少有可用用户时间；全部19,734组AI正文缺独立可用消息时间 | KM原生日志顺序、真实发送时间、请求/尝试关系、工具调用编号。不能用导出行号补造历史时间 |
| 技能信息 | 有“请使用技能”等包装、安装意图和技能路径文本 | 它们不证明真实安装或执行。用户此前已确认这批历史agent没有实际skills，本轮按此处理；如生产日志存在反证，应交真实版本及执行凭据，再修正 |
| 企业范围 | 会话来自当时的企业成员名单，正文主集有34名实际出现的用户 | 每条会话当时使用的是哪个个人/企业实例；成员名下会话可能含个人咨询、测试和平台内容 |

文件引用已经逐条列出，数据方不用重新从正文猜：

- [AI正文中的文件位置候选](../reviews/2026-10-05_evomind_full_audit/private/assistant_artifact_text_references.json)：用于扩大查找范围，候选需区分输入、参考资料与真正产物。
- [固定会话编号清单](../datasets/evomind/analysis_20261005/private/session_ids.csv)：1,466条，供本次补导统一范围。

## 二、数据方具体查哪里、怎么交

现有导出脚本证实平台数据库是 PostgreSQL 的 **`insight_weaver_prod`**。KM为独立服务，当前没有其内部库表或对象存储桶的源码证据；这部分由KM负责人通过已存在的接口或文件备份导出，不能假设都在平台数据库。

| 优先级 | 要补的东西 | 平台库中查什么 | 再从哪里取实际内容 | 交付要求 |
|---|---|---|---|---|
| P0 | 用户原附件 | `zclaw_messages.rawPayload.files`，关联`zclaw_sessions.userId` | 正确用户及实例的KM工作区；个人/共享文件content接口 | 每个引用对应原文件，或明确“找不到/已删/路径缺失”；附SHA256、大小和历史/当前快照属性 |
| P0 | AI生成的文件与修订 | `generated_artifacts`先按会话查，再按清单中的用户＋路径、核实的企业补查；回查消息及原生manifest | KM用户工作区与历史备份 | 原始版本和各次修改独立保存，绑定会话/请求/尝试。该表同用户同路径会更新并覆盖会话归属，不能只按当前会话漏查，也不能用当前行冒充完整历史 |
| P0 | 全量用户、AI、工具、工具返回 | `zclaw_messages`，不排除失败和工具角色 | 同步不足时补KM会话history/原生日志 | 保留原消息ID、角色、正文、时间、完整载荷；调用与结果通过真实调用编号关联，重试不先合并 |
| P0 | 会话与KM日志对应关系 | `zclaw_chat_bindings`、`zclaw_sessions`、`zclaw_agent_instances`；`enterprise_openclaw_instances.kmAgentBaseUrl`给企业实例路由 | KM原生session日志 | 交会话编号到原生会话键及实例路由的映射、连续分页history、原始数组/日志行顺序。平台消息表没有`replyTo`或持久序列号，不要生成一个假字段；路由配置不导出令牌 |
| P0 | 企业实例及用户边界 | `enterprise_memberships`、`zclaw_agent_instances`和会话实例关联 | 若实例配置有历史，补发生时快照 | 每会话标明个人/企业实例及企业ID，缺历史归属则未知；不要只凭当前企业成员身份认证企业业务 |
| P1 | 业务验收/真实使用结果 | 现有对话反馈；实际业务审批/交付系统由数据方定位 | 业务方的验收记录或有限人工评审 | 写清评价针对哪个任务、尝试或文件，依据哪条标准，是否采纳，哪里需返工。系统`done`和AI“我完成了”不能代替验收 |
| 条件P1 | 真实技能库存、版本及消费 | `skill_inventory_snapshots`、`skill_usage_events`、个人/组织配置及提交版本表；线上启用时再取trace表 | KM技能bundle、个人revision、原生工具日志 | 如果确实没有技能，交“当时无安装/消费”的确认即可；若有，交完整技能包、版本/hash/生效期及选择、注入、读取、执行各层证据 |
| 条件P1 | 依赖的知识库与外部资料 | `ragflow_datasets`、`ragflow_documents`、`ragflow_file_blobs` | RagFlow负责人取当时文档/命中片段；KM取检索工具返回 | 保留来源文档、版本/hash、查询和命中内容；链接/映射表不是实际资料正文 |
| P2 | 模型和人工成本 | `billing_tasks`、`billing_task_events`、`zclaw_enterprise_token_usage_settlements` | 上游模型usage与实际账单，人工计时由业务方提供 | 逐请求模型、起止、token/缓存/重试、金额；原始计费数量和模型tokens分开，缺失不填零 |

技能使用特别要注意：当前源码的`skill_usage_events`是在任务完成时记录**选中的技能**，还不能证明正文实际被读、脚本被执行或任务用了技能方法。`savedHours`由固定0.5小时分摊而来，**不是实测节省工时**。本轮不会把这些字段作为真实收益。

## 三、具体查询与KM接口

[生产表和关联SQL核对](../reviews/2026-10-05_evomind_full_audit/data_supply_source_audit.md)已经列出各项源码依据、schema检查和参数化查询。[固定范围SQL模板](../datasets/evomind/analysis_20261005/provider_export.sql)进一步以现有会话编号锁定范围。由数据方使用既有只读账号执行；研究端本轮不接生产。

按当前KM客户端已存在的能力，文件与技能可以从以下入口补取：

```text
GET /api/km/workspace/files/{按路径段编码的文件路径}/content
GET /api/km/shared-workspace/files/{按路径段编码的文件路径}/content
GET /sessions/{原生会话键}/history?limit=...&cursor=...
GET /api/km/skills
GET /api/km/skills/{技能ID}/bundle
GET /api/km/skills/personal/{技能key}/revisions
GET /api/km/skills/personal/{技能key}/revisions/{版本号}
```

这些路径对应不同API前缀，数据方应按线上实例配置路由，并在正确用户作用域下调用。客户端通过`x-km-user-id`选用户；服务鉴权沿用现有配置，无需把服务token明文交给研究端。`/workspace/对话附件/…`这类历史路径不能脱离用户/实例直接在一台服务器上按文件名查找。

导出时间请直接输出ISO日期字符串或数据库原始可解析时间，避免把日期对象序列化成`{}`。同时说明是原生消息发生时间、同步写库时间还是时间兜底值；本地源码存在缺远端时间时用当前时间兜底的路径，不能只补一个格式正常的时间就称历史顺序已恢复。

## 四、一次性交付包

```text
evomind_supplement_YYYYMMDD/
  export_manifest.json             # 导出时间、原范围、线上版本、行数、各文件SHA256
  source_schema.json               # 实际库表与列，不包含连接密码
  sessions_and_bindings.jsonl      # 会话—用户—实例—KM原生会话键
  messages_all_roles.jsonl         # 用户、AI、系统、工具、工具返回及失败
  files_manifest.jsonl            # 每个输入/输出引用与实际文件对应
  files/<SHA256>/<原文件名>        # 原始字节，避免同名覆盖
  km_histories/<原生会话键>/       # 原生完整历史与分页说明
  business_outcomes.jsonl          # 如存在，逐对象验收及证据
  unresolved_manifest.jsonl        # 补不到的项目也逐条交原因
  skills/                         # 当时确有skill时才交：版本包与消费凭据
  retrieval/                      # 任务依赖知识库时补文档和检索回执
  usage/                          # 需要做成本分析时补模型账本
```

每条文件清单至少能回答：**哪个用户的哪个会话、哪条消息引用了它；它是输入还是输出；源路径是什么；交来的文件hash是什么；能否证明是当时那个版本；若拿不到，具体原因是什么。** 数据方可保留已有字段名，新增字段说明要附在README；不要因为补不到文件而删除会话。

每条结果记录至少能回答：谁按什么标准，评价了哪一次尝试或哪个版本的产物，判断和证据是什么。新增人工评价必须注明“本次回溯评审”，不能冒充历史自然反馈。

## 五、最先补哪批最有用

先按既有442条文件相关会话交原附件、AI产物和完整工具history，就能核验大量文字中声称的读取、修改与修复。合同、招聘、文件编辑等任务优先；正文自足的任务可以继续做技能涌现，但缺文件的案例只能学有文字依据的局部经验，不能认证文件编辑成功。

038合同案例尤其需要原合同、每次修订稿、修订/批注实际内容和生成/校验工具回执。当前可追踪用户如何改变要求，不能核实AI到底修改了哪些地方。其原会话编号和源消息位置已保留，可直接给数据方按编号查，而不是让其重做语义整理。

本轮补交建议不自动授权生产接入，也不认定文件仍然存在。补不到的历史证据保留为未知；当前快照与新增执行可以作为新材料，但必须保留独立身份。
