# WWW Industry Track 调研与本项目研究定位

调研日期：2026-09-18。性质：定向文献调研与研究建议，不是本项目实验结果。

## 1. 结论与证据范围

本项目与 WWW Industry Track 有潜在契合点：面向企业在线工作平台，将会话经验转化为可复用能力，并验证真实工作收益。但“完成自动提炼、入库、检索和演化闭环”不足以单独证明创新，相关工作已覆盖多个环节乃至相当完整的闭环。

本轮核查官方 CFP、2026 Industry 录用名单，并定向阅读三篇 2025/2026 相关工业论文的评估和部署章节。它们用于归纳可借鉴的论证方式，不构成对全部录用论文的统计调查；不存在据此推导的录用保证或统一效果门槛。相关算法主要依据作者 arXiv 原文；未标明正式发表情况的条目按预印本处理，不混称 WWW Industry 论文。没有运行代码或复现实验。

## 2. 官方要求与年份边界

[WWW 2026 Industry CFP](https://www2026.thewebconf.org/calls/industry.html)要求体现工业问题、原创结果与实际影响，并明确说明部署或发布方式及持续时间；关注现实约束、系统取舍和对 Web 社区的意义。2026 规则为正文最多 8 页、全文最多 12 页，单盲，进入主论文集。不能将这些细则直接套用到下一届。

[WWW 2027 官方日期](https://www2027.thewebconf.org/important-dates/)当前列出 Research & Industry 摘要截止 2026-10-18、全文截止 2026-10-25。当前用户尚未确定投稿年份。本轮未核实 2027 独立 Industry CFP 的完整细则，因此不继承 2026 页数等规定；第三方网站仍有旧日期，采用官方页面。

对本项目的推断：需要说明企业会话如何发生在真实 Web/SaaS 工作流中，以及系统如何改善这些工作流。不能只因系统有网页界面就认为 Web 相关性充分。只有离线原型时，应如实陈述成熟度，不能写成生产部署。

## 3. 论文内容应围绕的证据链

下列是本项目建议的内容结构，不是会议规定的章节模板。

| 内容 | 应回答的问题 | 应准备的材料 |
| --- | --- | --- |
| 真实问题与影响 | 谁在反复做什么，现状损失是什么？ | 任务分布、重复说明/返工、人工沉淀成本 |
| 已有系统与约束 | 为什么直接用记忆、RAG、人工 SOP 或已有 skills 方法不够？ | 现有流程、可核查失败实例、延迟和审核预算 |
| 研究问题与机制 | 新方法到底改变哪一步、为什么有效？ | 问题定义、机制、与近邻工作的差异 |
| 系统设计与取舍 | 新方法如何接入现有服务？ | 同步/后台路径、个人/组织边界、版本与回退机制 |
| 离线证据 | 方法是否有效，收益来自哪里？ | 可信基线、消融、时间/用户/任务留出 |
| 实际影响 | 用户是否完成得更好、更快、更省？ | 真实试点或在线实验、端到端质量与总成本 |
| 长期行为与经验 | 多轮演化是否退化、哪些人受益或受损？ | 时间曲线、失败案例、分组分析、可迁移经验 |
| 限制与可复核性 | 结论适用何处？ | 数据来源、评估协议、保密条件下可公开产物 |

“已有系统的功能”和“本论文新增研究贡献”应在架构图中明确区分。各环节都实现，不等于各环节都有创新。

## 4. 三个工业论文案例：工程价值如何落到数字上

### 4.1 When Rules Fall Short（WWW 2026 Industry）

[论文原文](https://arxiv.org/html/2601.11634v1)，[官方录用名单](https://www2026.thewebconf.org/accepted/industry.html)。阅读位置：§5、§6.2.2–6.2.4。

作者将“发现新内容问题”接到策略更新和下游治理：在线问题视频观看占比从 0.0047% 降至约 0.0040%，相对下降 14.9%；发现到策略更新周期从 25.8 天缩至 7.7 天，下降 70.2%。同时报告日处理约 3 万视频，Agent 约用 12.5 H100 GPU-hours/day，SFT 对照约 1.7。周期比较包含人工审核时间；它不是人均工作小时的直接估计。

可借鉴：本项目应追踪“发现任务 → skill 被采用 → 新任务成功”的下游链路，并同时报告额外计算和审核成本。

### 4.2 Data-Driven Function Calling Improvements…（WWW 2026 Industry）

[论文原文](https://arxiv.org/html/2604.05387v1)，录用身份见同一官方名单。阅读位置：§4、§5。

腾讯元宝金融 QA 案例评估 350 个端到端问答对、近 2,000 个 query–tool-call-list 对；作者报告 F1、工具执行率、最终答案准确率分别提升 39.1%、40.7%、20.3%，人工比较为 72% 更好、16% 更差。这些是原文报告的提升百分比，不改写为百分点。协议描述的是两套流程的配对评估，不能额外声称是用户随机 A/B。

可借鉴：skill 被检索、加载和执行只是中间环节，最终任务结果须独立衡量。

### 4.3 GenMentor（WWW 2025 Industry）

[作者项目与 track 说明](https://github.com/GeminiLight/gen-mentor)，[论文原文](https://arxiv.org/html/2501.15749v1)。阅读位置：§5.3、§6。

系统部署于 AIEP，并开展 20 名员工的研究；10 名技术岗位、10 名非技术岗位。报告易用性 4.6±0.7、满意度 4.3±0.7，并结合输出偏好评估与访谈。主观效率改善不能直接换算成客观节省工时。

可借鉴：企业系统可以用真实用户研究呈现采纳与体验，但应将主观满意度、客观任务质量、实际用时分别报告。

## 5. 本项目建议的量化体系

以下全部是拟议指标，不是会议规定，也不是本项目已经取得的结果。先确立一项主要效果指标和一项主要效率指标，其余用于解释机制。

| 环节 | 建议指标及分母 | 需要避免的误读 |
| --- | --- | --- |
| 任务发现 | Precision@K；固定专家审核小时内发现的有效机会数；已标注重要任务覆盖率 | 高频不等于重要，聚类质量不等于业务收益 |
| skill 形成 | 经独立新任务验证有用的候选数 / 被审核候选数；重复候选比例 | “写出了 SKILL.md”不等于可复用 |
| 用户入库 | 接受数 / 实际展示数；审核分钟/候选；修改后接受比例 | 未展示候选不能混入采纳率分母 |
| 持续采用 | 在有后续适用机会的已入库 skills 中，固定窗口内再次使用的比例 | 无适用机会不能直接判为失活 |
| 端到端任务 | 通过预定义业务验收的任务数 / 全部合格评估任务数 | 不能只保留成功调用 skill 的任务 |
| 人工负担 | 每任务主动操作、重复说明、审阅和返工时间；人工干预次数 | 响应更快不代表人工用时下降 |
| 总成本 | 生成、检索、执行、失败重试、演化、验证和人工审核的总成本 | 不只计算执行阶段 token |
| 组织复用 | 留出用户的任务收益；每个有效 skill 覆盖的非作者用户数 | 被分享或被安装不等于产生收益 |
| 演化 | 相同留出任务上新旧版本成功率差；旧成功新失败比例；学习曲线 | 版本号增加、judge 分数增加不等于能力提高 |
| 系统约束 | P50/P95 延迟、吞吐、失败率、回退率；库增长下的性能 | 平均延迟会掩盖长尾；越多 skills 未必越好 |

推荐的核心指标：

- **任务成功率差**：ΔTSR = TSR_system − TSR_baseline，使用百分点报告；另报相对提升，明确区分。
- **每成功任务总成本**：C_success = 全部评估任务的服务、失败、维护与审核成本 / 成功任务数。历史建库投入另报，并说明摊销窗口。
- **净节省人工时间**：H_net = 同等任务量和质量要求下的基线人工时间 − 系统使用人工时间 − 额外入库审核/维护时间。等待时长和主动人工时长分开统计，避免重复计算。
- **版本退化率**：Reg = 旧版成功且新版失败的配对任务数 / 旧版成功的任务数；同时报告反向改善数。随机输出需要重复运行与区间估计。
- **跨用户收益**：在未参与 skill 生成的用户及其新任务上，与无该 skill 或个人库条件配对比较；另报关键角色或部门的下降情况。

一个仅用于说明核算口径的假设：100 个可比任务各节省 6 分钟，共 10 小时；额外审核、维护 3 小时，净节省才是 7 小时。这里所有数字均为假设，未表示预期结果。

业务价值不一定要折算营业收入。若无法可靠货币化，报告通过验收的额外任务数、主动人工工时、实际服务成本和维护投入即可；ROI 只能在成本边界与价值换算有依据时计算。

## 6. 实证设计：如何让闭环成为可信论文

### 6.1 三层证据

1. **历史事实分析**：选取经过授权的会话，辨认重复任务、真实失败和可沉淀信息，形成可定位的案例与任务族。
2. **时间顺序离线评估**：早期会话生成库，开发段选择参数，锁定测试段检验未来新任务；再做用户留出。环境和可用知识只采用当时可得内容。
3. **真实用户试点/在线研究**：报告部署时间、用户/部门、合格任务量、曝光与采纳、端到端结果及成本。小试点如实称试点；不能提前承诺样本量满足统计要求。

静态泛化与在线演化分开评估：前者冻结库；后者在每个时间点先测再更新，只允许用过去的反馈。监控用回归集与最终未触碰测试集分开，不能不断在同一最终测试集上挑选更新。模型、工具、预算与检索条件应固定或明确作为变量。

### 6.2 基线和对照按问题选择，不必全部堆入论文

| 要证明什么 | 必要的对照类型 |
| --- | --- |
| skills 相比现状有用 | 现有企业助手；同模型的历史会话/RAG/普通记忆；人工 SOP 或人工 skills |
| 自动生成有价值 | AutoSkill 类实现或忠实适配；固定任务和检索条件 |
| 发现策略更好 | 高频优先、随机候选、全量提炼、简单收益启发式；固定审核预算 |
| 跨用户机制有效 | 仅个人库、单一共享库、适用范围规则；必要时 SkillClaw/FederatedSkill |
| 演化优于静态 | 同一初始库的冻结版、简单反馈改写、EvoSkill/SkillEvo 类更新；匹配计算预算 |

不要将不适合当前数据形态的论文强行改成弱基线。明确官方复现、机制适配和自定义提示基线。若 SAPO 等依赖 RL，不把“冻结模型的提示版”称为官方复现；可用其候选增益验证机制做受控对照，注明边界。

评估自选择入库时，采纳用户与未采纳用户本就可能不同，不直接作因果比较。能随机时按合适的用户或团队单位随机，主要报告分配人群的效果，采纳者结果为补充。组织共享存在组间扩散时隔离库或按组织单位设计；不能让对照组接受处理组更新。不能随机时报告匹配/前后设计的局限。

评价优先用业务验收、可执行结果和盲评。LLM judge 可辅助，但需专家校准，且不以生成 skill 的同一模型自评作为唯一证据。置信区间和统计单位按用户/任务族依赖关系处理，不能把一人的多轮会话当成大量独立用户。

## 7. 相似研究：哪些创新表述已经不够

下表中的差异分析是针对本项目的研究判断。论文结果不能跨数据集直接排成能力排行榜。

| 工作与时间 | 已核查的重叠点 | 对本项目的约束 |
| --- | --- | --- |
| [AutoSkill，2026-03，v2](https://arxiv.org/html/2603.01145v2) | 用户查询提炼、add/merge/discard、版本演化、混合检索；区分用户与共享存储 | 最直接近邻；个人/共享两层库也不能单独称创新。§5 主要是 SkillBank 统计和案例，不能把版本变化当成效益证据 |
| [SkillClaw，2026-04](https://arxiv.org/html/2604.08377v1) | 汇聚多用户使用轨迹、演化并验证更新、共享同步 | “跨用户集体演化”和“先验证后发布”已被覆盖；其实验为基准上的模拟部署 |
| [FederatedSkill，2026-06](https://arxiv.org/html/2606.03143v1) | 共享语义 skill patches 而非原始轨迹，按客户端能力差异返回个性化更新 | “隐私 + 跨用户 + 个性化”不能作为未经限定的首创；少传原文也不自动等于形式化隐私保证 |
| [SkillEvo，2026-08](https://arxiv.org/html/2608.13120v1) | 多轮交互反馈生成与独立治理，关注退化和知识膨胀 | “多轮反馈 + 防退化”已存在，需要更具体问题及证据 |
| [EvoSkill，2026-03](https://arxiv.org/html/2603.02766v1) | 分析执行失败，生成/修订 skills，用验证表现筛选 | 单纯失败驱动更新不是充分差异 |
| [SAPO / Co-Evolving Skill Generation and Policy Optimization，2026-06](https://arxiv.org/abs/2606.08755) | 匹配 rollout 比较候选 skill 的边际效用，入库前验证，与策略训练结合 | 单纯“衡量增益再入库”也已有工作 |
| [Agent Workflow Memory，2024-09](https://arxiv.org/abs/2409.07429) | 从经历归纳可复用工作流并支持后续任务，离线/在线构建 | “历史工作流复用”有明确前史 |
| [SkillWeaver，2025-04](https://arxiv.org/abs/2504.07079) | Web 环境探索、练习、将经验抽象为可复用 APIs | 主动发现与练习改进 skills 不是空白 |
| [ACE，2025-10](https://arxiv.org/abs/2510.04618) | 生成、反思、整理持续演化的 playbook | 普通上下文反思演化是重要对照 |
| [Corpus2Skill，2026-04，v4 2026-08](https://arxiv.org/abs/2604.14572v4) | 将企业知识库编译为可导航 skill 目录，用于 QA/RAG | 企业材料转 skills 已有工作；其主要来源是文档，不等于本项目会话闭环 |

优先精读顺序：AutoSkill → SkillClaw → FederatedSkill → SkillEvo → SAPO。上述前四项读取了方法/系统或评估相关原文章节；SAPO 本轮主要核查作者摘要，需继续全文审查其适配和实验协议。其他条目作为次级比较与技术背景，本轮未完成逐项源码核验。

建议使用的公开评估资源：

- [SkillsBench v4](https://arxiv.org/abs/2602.12670v4)：87 个任务、8 个领域，匹配有无 curated skills 的评估；平均通过率 33.9%→50.5%，+16.6 个百分点。该版本数字不能与旧版混用，也不能推出自动生成必然有效。
- [SkillFlow](https://arxiv.org/abs/2604.17308)：166 个任务、20 个任务族，序列式发现、修补和复用；适合补充长期演化评估。使用率与收益并不等价。
- [SWE-Skills-Bench](https://arxiv.org/abs/2603.15401)：报告许多 skills 无收益且可能增加 token；仅用于提醒收益依赖任务与上下文，不把软件任务结果泛化为所有企业场景，也不因此启动开发技能链路。

这些资源可以补充可复核性，不能替代企业真实任务和用户效益证据。

## 8. 建议的创新定位：候选，不是已经成立的贡献

### 候选 A（优先核查）：审核预算约束下的任务机会发现与 skill 沉淀

问题不是“能生成什么”，而是“有限审核能力应先花在哪些经验上”。将企业会话视为需求流，同时考虑复发机会、已有助手能力缺口、错误或返工代价、可泛化证据、生成与验证成本。学习的是任务是否值得沉淀，而不只是对已存在 skills 做检索排序。

拟议方法方向：通过少量有无候选 skill 的配对验证估计可改善空间，对收益不确定的候选选择有判别力的额外证据，在固定审核预算下做生成/暂缓/合并/放弃决策。重要性必须由任务后果或业务定义支撑，不能直接让 LLM 无依据评分。

近邻与风险：SAPO 已有边际效用验证，其他效用驱动 skills 工作也存在。本项目需证明区别确实来自真实会话的机会发现、稀疏反馈与人工审核约束，而非把既有公式改名。

判别实验：相同生成器、执行器和审核小时，比较频率优先、简单价值启发式及候选方法对未来新任务带来的净收益。若简单频率×收益启发式已相当，或收益仅来自更大预算，淘汰复杂机制。

### 候选 B（与企业主线最贴近）：从个人经验到组织 skill 的适用范围发现

问题：一次用户纠正，到底是个人偏好、角色约定，还是组织通用规则？主题相似不代表执行条件兼容；全局共享可能掩盖少数角色的退化。

拟议机制：把稳定程序与用户/角色/环境条件分开，利用支持与冲突证据维护适用范围；对组织候选在未参与生成的用户上验证，决定个人保留、条件化推广、分支或拒绝推广。用户仍自主决定是否个人入库/提交，机制负责提供证据，不取消选择权。

近邻与风险：AutoSkill 已有私有/共享存储，FederatedSkill 已处理客户端异质性，SkillClaw 已跨用户同步。因此“多加组织库”“保留个人覆盖层”只是设计，必须证明新的范围学习/推广决策在冲突反馈下更有效。

判别实验：构造来源真实的同主题不同约束任务，在同一审核预算下比较个人库、单一共享、简单角色规则与近邻方法；测新用户增益、关键群体退化和审核成本。若静态角色规则足够，不能把复杂范围机制包装为必要创新。

### 候选 C（配套优先）：稀疏且有噪声的使用反馈下持续演化

问题：用户不纠正不代表正确，一次失败也可能来自工具故障、错误选用或环境变化，而非 skill 内容。更新错误部件可能破坏原有能力。

拟议机制：区分可用于修订的证据与仅可用于诊断的事件，在技能内容、适用范围、检索选择和环境变化之间做归因，证据不足时保留版本并收集信息。所有使用均产生观测，不要求每次都改写。

近邻与风险：EvoSkill、SkillEvo、ACE 和 SkillClaw 已覆盖大量反馈与治理机制。这一方向当前重叠较高，优先作为闭环质量保证；只有新的反馈归因机制在真实使用中有明确优势时，再提升为核心贡献。

### 当前建议

优先用真实系统案例检验 A 与 B 中哪一个瓶颈最突出，再选一个作为核心贡献，另一个作为系统设计或辅助实验。论文可暂定位为：

> 在有限审核预算与异质用户约束下，将企业会话中的任务经验转化为经验证、可跨用户复用并持续演化的 skills。

这是一条研究问题陈述，不是首创声明；没有证据时不使用“首次”“首个”或“SOTA”。系统实现、企业场景或多个已有方法拼接，都不能自动替代原创机制。

## 9. 适合本项目的论文贡献与行文草案

可争取的三项贡献，均须后续实现证据：

1. 通过真实企业会话分析，揭示“出现频率/用户接受/个人有效”与“组织可复用价值”之间的断点。
2. 提出针对其中一个断点的明确机制，并以匹配预算、用户留出和消融识别独立收益。
3. 在已有系统中验证完整闭环，以长期任务质量、净人工收益、成本与失败经验说明工业价值。

建议正文顺序：业务动机与观测 → 问题及近邻差异 → 核心机制 → 系统集成与取舍 → 离线实验 → 部署和用户研究 → 局限及经验。篇幅随实际年份要求确定。

工程价值表述模板（全部待填，不是结果）：

“系统在 [真实平台/任务场景] 运行 [时间]，覆盖 [用户/团队] 与 [合格任务数]。相较于 [明确基线]，通过业务验收的任务成功率从 [a] 到 [b]，净人工时间减少 [h]，每成功任务总成本改变 [c]。新增审核与演化成本为 [m]；在未参与生成的用户上仍观察到 [g]，关键群体与历史能力的退化为 [r]。消融显示主要收益来自 [机制]。”

## 10. 下一步需要的事实，不是本轮执行任务

- 已有系统提供什么能力，skill 具体执行什么，涉及哪些 Web/SaaS 工作流。
- 能使用哪些历史会话、工具轨迹、用户纠正和结果；是否能关联匿名用户、角色和任务。
- 哪些任务有可判断的完成标准，以及实际重要性依据。
- 能否做真实用户试点、合理对照和持续版本观测；可负担多少人工审核。
- 目标投稿年份。

本轮无本项目实证发现。完成的是文献证据核查与候选研究定位；不据此承诺可发表性，也不启动实验或开发。
