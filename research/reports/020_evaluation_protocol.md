# 020：Skills Loop 分层评测与工业试点方案

2026-09-24。**拟议协议，尚未执行论文实验。**依托[论文蓝图](020_paper_blueprint.md)中的官方CFP与已发表案例；下列数据规模、对照和统计方法为本项目建议，不是会议规定或已获得结果。

## 1. 先锁定哪些主张可以被推翻

| 问题 | 主要解释竞争 | 关键对照 | 支持/否定如何影响决策 |
| --- | --- | --- | --- |
| RQ1：任务轨迹是否减少无效沉淀？ | 只是少生成，或强摘要本来就能解决 | QA原子、完整会话摘要、任务轨迹，共用提炼器与额度 | 无效率下降但方法保留下降，不能宣称目标达成 |
| RQ2：skills是否改善新任务？ | 只是更长上下文、更多tokens或人工选中 | 无skill、相关原始经验、人工skill、自动skill，共用消费者 | 读了文件但验收不提高，应查方法内容/执行，不能以读取率代替收益 |
| RQ3：演化是否有净增量？ | 只是重写、反馈泄漏、测试集越学越熟 | 同一初始库冻结、固定周期更新、增量更新 | 只改善已经见过的修正例而不改善新例，不算泛化演化 |
| RQ4：是否值得企业使用？ | 审核维护抵消节省，或收益只来自高手 | 原有流程对照，全部合格任务，角色分层 | 净人工时间不降/成本越界，改部署策略或收窄场景 |

先指定任务成功率为主要终点，净人工时间和每成功任务总成本为关键次要终点；有效方法保留和退化作为约束。哪些指标共同组成正式成功标准应在看结果前写定，不能后验挑最好的一项。

## 2. 数据分层：四类材料不能混用

1. **软件夹具**：目前回放与本地合成服务。只验证状态机、工具读取与数据流，不进入主结果表。
2. **受控任务材料**：从获授权业务规则构造可核查的新实例，包含正确/错误控制和边界。能定位机制，但不是在线部署证据。
3. **去标识真实会话**：保留目标、时间、角色、运行终态、修订和技能版本。用于发现分布、时间留出和错误诊断；不能自动推断完成或满意。
4. **真实使用试点**：实际成员在真实流程中使用，记录全部合格机会、任务验收、人工修改、审核和维护，用于工业净价值。

建议先选3—5类确有复用需求的任务，如运营周报、工单归类与处置建议、企业知识答复、规范化文档整理。每类同时包含可复用规则与不可复用个例。不要全部使用同一个“跨期退款”示例，也不要选当前文件工具无法完成的任务然后把失败记为算法失败。

标注单位是独立任务/方法，而非消息数。任务标注至少含：目标与交付物、起止片段、关联依据、attempt、纠正关系、技术结果、业务结果/UNKNOWN、可复用方法及适用条件、噪声类型、实际技能版本、是否存在未决冲突。两名业务知情标注者先独立标注部分样本并仲裁；报告一致性及未知比例，不把仲裁当额外独立数据。

## 3. 拆分防泄漏

- **时间拆分**：早期会话用于生成，中间区间调规则/阈值，后期任务只评测。具体截止时间预先固定。不得随机把同一长会话的问答拆进训练和测试。
- **任务族拆分**：将同一对象、模板、派生实例归组；分别报告同任务族新实例与未见任务族。关键词换名不自动成为独立新任务。
- **用户拆分**：组织库生成者和留出用户分开；只有审核后的技能可跨成员传递。评测数据使用授权不等于产品共享授权。
- **演化拆分**：每轮先执行并锁定评分，之后才暴露该轮反馈并更新。下一轮用新实例；另设不参与任何更新的固定审计集。
- **答案隔离**：参考答案与验收程序由独立流程锁定，不进入生成/改写输入。若人工诊断修复skill，只能称人工控制，不与自动算法结果混报。

“生成过的任务再做一次”只可作回放诊断，不能作为未来任务收益。

## 4. 基线分两层，避免一次比较改变全部系统

### 4.1 提炼机制比较：固定消费者

| 编号 | 基线/方法 | 必须固定或披露 |
| --- | --- | --- |
| G0 | 现有QA原子链路的可运行复现 | 同样输入机会、提炼模型、输出格式、发布门槛 |
| G1 | 强完整会话摘要→skill | 不截掉关键纠错；同样生成额度与可用上下文 |
| G2 | 透明任务分段→skill | 最简单规则分段，作为复杂机制的现实替代 |
| G3 | AutoSkill官方实现或明确标注的机制适配 | 提取、维护、检索边界及改动；先验证实现忠实性 |
| G4 | Trace2Skill官方实现或机制适配 | 批量多轨迹归纳，分别报告原生预算与匹配预算 |
| O | 本项目可修订任务+增量路由 | 与G2主要差异应实际发生：迟到重开、来源失效、增量归因 |

优先完整运行G0/G1/G2和最直接近邻G3；G4在可忠实运行且确有不同预测时加入。不能用改名提示词取代官方方法，再宣称胜过论文。无法复现要报告原因；不把基础设施失败记成方法低分。

### 4.2 端到端消费比较

- C0：同模型/同工具，无skills。
- C1：等来源的原始经验或检索片段，控制“多给上下文”解释。
- C2：专家人工skill，作为参考控制，人工时间计入成本；不是必胜上界。
- C3：由G0/G1/G3/O生成的skills，在相同选取与消费者条件下使用。

分别做**给定适用skill**的归因实验和**实际选取流程**的端到端实验。前者不代表检索/用户选取无误；后者要计入未找到、误选、未读和拒用。两种结果不能混成一个成功率。模型、版本、工具面、任务输入、超时、可用tokens和技能包加载方式保持可比。

## 5. 指标口径

| 指标 | 定义与分母 | 防止错误解释 |
| --- | --- | --- |
| 任务成功率 | 满足预先业务验收的任务数 / 全部合格任务数 | 技术异常作为端到端失败保留；另报告成功执行子集作诊断 |
| 无效候选率 | 人工/独立规则判无复用价值或错误的候选 / 全部已生成候选 | 同时报告绝对无效数、有效数、待评估数，不能把UNKNOWN判无效 |
| 有效方法保留率 | 被有效产物覆盖的参考有用方法数 / 参考有用方法总数 | 一个skill可覆盖多个方法；分母来自独立参考集，不能只审已生成的候选 |
| 增量更新有效率 | 在新实例有正收益且未违反预设退化约束的更新 / 已评更新 | 未完成验证的版本独列，不自动算成功 |
| 版本退化率 | 旧版成功、新版失败的配对任务数 / 旧版成功任务数 | 若分母0记NA；另报旧失败→新成功 |
| 净人工时间 | 原流程时间−新流程任务时间−新增审核维护时间 | 以操作计时/抽样观察为主，问卷单列；避免重复扣费 |
| 每成功任务总成本 | 全部执行、生成、验证、演化、失败重试、审核成本 / 成功任务数 | 使用固定计价口径并报告机器与人工分项；成功数0记未定义 |
| 覆盖/延迟 | 合格机会覆盖、DEFER/QUEUED占比及等待时长 | 不得靠全部延期制造低成本和高精度 |
| 消费证据漏斗 | SELECTED→CONTEXT_INJECTED→FILE_READ→行为遵循→业务成功 | 每层分母明确，最后两层依独立验收 |

“生成数量下降”只有与方法保留/任务收益共同成立才支持我们的目标。将同一有效方法装进更少skill，不应误判能力减少。高频任务按独立发生次数统计，重要性按预先业务损失/优先级；不拿模型自评分替代业务重要性。

采纳率=采纳数/展示数；再次使用率分母应限于有后续适用机会的用户/技能。部署同时报告P50/P95延迟、失败、回退、队列积压、库规模与角色差异。

## 6. 专门验证“少花资源、有效能力保留”

同时报告两种口径：

1. **固定观察窗口/固定合格任务数**：用户全部经历上，执行+学习+重试总成本是否增加，净人工是否下降。
2. **固定总预算**：各法能覆盖多少有效方法、完成多少后续任务。画质量—总成本前沿，不只对齐外层调用次数。

预算账本分开记录模型服务HTTP请求数（若可获得）、输入/输出/缓存tokens、真实计价、工具成本、人审时间。底层请求未知就记UNKNOWN；OpenClaw外层一次调用不等于一次LLM请求。审核用LLM的成本也要计入。

预设有效保留和成功率的非劣界值δ，并检验差异区间是否落在允许范围。δ需业务方在见到结果前确定；不能把“不显著下降”当成“证明保留”。要求成本不增加时，应观察差异上界/预算上限，而不仅是平均值小一点。

## 7. 消融只改变一个待证机制

- QA原子 vs 完整任务轨迹：固定提炼器与调用额度，观察纠正丢失和未来任务差异。
- 完整轨迹 vs 仅终稿：验证失败→修正路径的额外价值。
- 固定封口 vs 可重开：用实际晚到纠正，观测过期候选和错误版本传播。
- 所有使用均重写 vs 仅增量更新：同一流量、原始反馈及版本起点，比较收益、退化和成本。
- 冻结初始库 vs 持续演化：同一未来任务流，先评后学。
- 同预算有/无筛选：同时测有效方法保留和候选质量，防止“少生成自然低成本”。

如果多个改动绑定，称联合消融，不作单一机制因果归因。版本CAS和权限属于工程可靠性，可做故障/冲突测试；不要把并发用例通过自动当成算法质量消融。

## 8. 真正的持续演化实验

从同一初始库复制三个隔离分支：冻结库、固定周期全量更新、增量更新。对任务流q1…qT，在t时刻各自使用当时版本完成任务，先锁定验收、成本、时间，再释放允许的反馈并更新到下一时刻。保持执行资源可比；更新超预算则排队并记等待。

每个版本在新任务和固定旧能力审计集上配对评估，画累计任务成功、累计总成本、旧成功→新失败、净审核维护时间。反馈可有正确纠正、无增量赞许、相互冲突和模型自身错误；“用户最新一句话必正确”不是合理假设。

若只对单个skill修订一次，称单次更新试验，不称长期演化。若引入模拟用户，明确标注合成反馈，不能代替真实采用证据。

## 9. 工业试点与统计

先做小规模可行性检查，建议3—5任务族、约30—50个独立新任务，目的为验证通路、验收可靠性和效应方差，**不是录用样本量标准**。失败要分清：未执行、服务失败、工具不支持、未读取skill、读了但没遵循、规则本身错误、评分有问题。

正式样本量依最小有用效应、基线方差、任务相关性和功效计算，不直接抄350问答或20人。一个skill的50个消费者任务不等于50次独立技能生成；bootstrap或混合模型应在用户/团队/任务族等实际独立层聚类，报告置信区间。配对二元结果可用适合的配对检验，并处理跨任务族相关性与多重比较。至少重复生成/运行的一部分样本估计模型随机性。

试点优先按团队或隔离库命名空间随机化，防止共享skill污染对照；记录暴露与串组。若采用交叉设计，使用等价但不同任务并平衡顺序；人的学习难以洗脱，应明确残留效应。无法随机化时，使用匹配/分阶段上线并降低因果措辞，报告时间趋势与同时发生的流程变化。

纳入所有预先定义的合格任务，包括没采用skill、误选和失败；主报告按分配组，实际使用子集仅作补充。试点必须积累真实复用机会和更新周期，具体运行周数由业务频率决定，不先许诺“跑一周就够”。

机器可判的字段、计算、文件与约束用独立程序；开放文本用锁定rubric的盲评。LLM judge只辅助，并用专家审计校准；报告位置偏差、与人一致性和不确定项。审查者不知道方法标签，参考答案不可由待评skill生成。

## 10. 最先执行的决策卡

**问题：**完整会话摘要是否已经能处理当前最主要的修订丢失，导致复杂任务机制没有增量？

**材料：**从获授权真实任务中抽取包含初稿→纠正→终稿与晚到反馈的少量不同任务族；另有纯问答和工具Bug负例。业务规则与验收由独立人员锁定。

**对照：**G0、G1、G2、O，共用提炼器、模型、消费者和总预算；每个来源方法用不同参数/对象的新实例测消费。记录是否正确提炼、是否实际读取、是否按规则执行。

**资源：**在真实模型配置后，根据一次通路和少量控制请求的计量确定总额度，先批准/配置明确金额或token上限再扩样本；本轮不自动执行大规模付费实验。

**停止/转向：**若G1已经等效，缩小任务机制主张；若skill内容正确但消费者不遵循，先查消费；若所有方法同错，查原证据/评分；若只有O在新实例改善且成本不增加，再扩大独立任务族。任何分支都能改变下一步决策，不以“继续调到赢”为协议。

## 11. 每次运行的可复现制品

run_id、代码/数据版本、模型/服务/参数、工具与skill包哈希、时间和用户划分、原始提示、响应、实际读取回执、工具结果、交付文件、来源与发布版本、验收器版本、评分及未知原因、请求/tokens/成本、人审时间、所有延期/失败。密钥不进入日志；企业数据保存受控引用而非公开原文。

最终每条论文主张都要连到结果表、原始证据和不可变制品。没有数据时保持TBD，不在图表填模拟提升值。
