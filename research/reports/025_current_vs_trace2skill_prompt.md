# 当前 Demo、Trace2Skill 与简单 Prompt 的边界

日期：2026-09-24。面向项目团队的现状澄清。本报告只比较已经核对的机制和当前 demo 行为，不把潜在创新写成已证实结论。

## 1. 结论先行

当前 demo 解决的是**企业技能生命周期问题**：从开放式会话中恢复可修订任务，依据运行和纠错证据决定 NEW、UPDATE 或 SUPPORT，调用 OpenClaw 与官方 `skill-creator` 生成技能包，再经过个人采纳、组织审核、版本发布、权限加载和后续使用反馈形成闭环。

Trace2Skill 解决的是**轨迹到技能的归纳与演化问题**：在固定初始技能和可判定结果的前提下，批量收集成功／失败执行轨迹，分别提出局部补丁，再层次化合并为一个可迁移技能。其核心不是“调用一次 skill-creator”，而是 many-to-one 的轨迹归纳、失败因果分析和补丁合并。

简单 prompt 只是**一段指令文本**。它可以要求模型“根据下面对话写一个技能”，但本身不提供任务边界、证据链、版本、权限、发布、使用回执或演化状态。

因此，当前 demo 可以准确描述为：**企业会话轨迹驱动的技能生命周期原型，借鉴 Trace2Skill 的轨迹归纳思想，但尚未实现 Trace2Skill 的核心多轨迹补丁算法，也不能借用其论文结果。**

## 2. 三者的机制对照

| 比较维度 | 当前 demo（已验收行为） | Trace2Skill v5 | 简单 prompt |
| --- | --- | --- | --- |
| 输入 | 多轮企业会话、工具运行、交付文件、选用技能版本、后续纠错 | 固定技能下生成的执行轨迹，含查询、推理／工具历史、最终输出和二元正确性标签 | 人工拼接的文本、问答或一段轨迹 |
| 轨迹单位 | 先按规则恢复任务，再保留初稿、失败、修订和使用关联；不把一问一答当作最终单位 | 每个演化任务一条带结果标签的完整执行轨迹，之后批量分析轨迹集合 | 没有强制的任务边界或事件模型 |
| 任务结束 | 自动封口；迟到纠错可以重开；未知结果保留，不等于成功 | 由基准任务执行和评测结果确定 | 由 prompt 或模型自行猜测 |
| 生成／演化 | 无已选技能且有新方法信号走 NEW；选用某技能后有方法变化走 UPDATE；无变化只记 SUPPORT | 成功分析器与失败分析器并行提出 patch；失败必须能解释并验证原因 | 通常一次生成一个文本结果 |
| 合并 | 当前 demo 主要是单候选、单基准版本的封装与版本发布；没有实现多轨迹 patch 池的层次合并 | 对 patch 池进行多层 many-to-one merge，去重、冲突处理、保留普遍模式后 APPLY 到基准技能 | 没有合并、冲突或基准哈希约束 |
| 技能产物 | `SKILL.md` 加辅助脚本／测试，官方 creator 验证和 `.skill` 打包；个人／组织版本有 hash | 同样是可移植技能目录，重点是由合并 patch 更新目录 | 通常只有 prompt 或一段 Markdown，未必可执行、可验证 |
| 授权与存储 | 个人采纳；组织提交和审核后才跨成员复用；下载和版本权限可核验 | 论文主要评估技能效果和迁移，没有本项目的企业提交／审核权限链 | 没有库、审批或访问控制 |
| 使用后反馈 | 使用回执回到任务；无增量 SUPPORT；纠错可产生下一版本 UPDATE；当前已跑通 Alice v1→v2→组织→Bob | 主要是离线／批量演化后在独立测试任务上评估；不是企业权限闭环 | 不会自动记住或更新 |
| 资源控制 | 规则先筛、学习派发限额、精确去重；内部模型轮次和历史失败仍需单独计量 | 论文使用并行分析器和层次合并，目标是相对顺序编辑更快／更强；资源口径属于其评测设置 | 没有预算、幂等或重试对账 |
| 价值证据 | 当前有功能验收和文件／权限／数值检查；尚无真实企业收益、无效率下降或成本下降证据 | 在 SpreadsheetBench、数学、DocVQA 等任务上报告独立测试集能力提升和跨模型／OOD迁移 | 没有默认的独立消费评估 |

Trace2Skill 的原文明确把流程拆成三阶段：冻结技能下生成带成功／失败标签的轨迹；并行提出成功和失败 patch；层次合并并应用到一个可移植技能目录。[Trace2Skill v5](https://arxiv.org/html/2603.25158v5#S2)

## 3. 当前实现距离 Trace2Skill 具体差在哪里

### 已经重合的部分

1. 都把可复用能力放进 `SKILL.md` 加辅助资源的目录，而不是只保存一次回答。
2. 都允许从成功经验提取稳定步骤、从失败或纠错中提取规避方法。
3. 都保留基准技能并产生新版本，而不是无条件覆盖旧文件。
4. 当前 UPDATE 的语义与“在已有技能上加入局部经验”相近；官方 creator 产物也具有可加载性。

这些重合只能说明使用了相同问题空间的设计，不足以证明实现了 Trace2Skill。

### 当前缺少的 Trace2Skill 核心机制

1. **没有论文式的带真实正确性标签的轨迹池。** 当前企业会话可能只有用户纠正、工具状态和交付物；“模型回复完成”不能替代业务正确性。当前 demo 已把未知结果保留，但尚未建立普遍的业务验收标签。
2. **没有独立的失败因果分析器。** Trace2Skill 的失败分析会检查轨迹、产物和答案，无法解释的失败不进入 patch 池。当前 demo 的主要实现是任务规则、方法信号和 creator 封装；失败经验是否能归因仍依赖生成阶段和后续验收。
3. **没有多轨迹 patch 池及层次 many-to-one merge。** 当前一次学习派发主要对应一个 NEW 或 UPDATE 候选；尚未把同一任务族的多条独立轨迹先各自产生 patch，再分层去重、解决冲突、保留高频模式。
4. **没有 Trace2Skill 的离线独立测试闭环。** 当前真实验收证明的是封装、注册、读取、交付和权限；还没有证明新版本在未参与生成的新任务上提高成功率或跨模型迁移。
5. **演化触发条件不同。** 当前重点是自然会话中的迟到纠错和技能使用归因；Trace2Skill重点是固定任务集上的批量演化。前者更贴近企业生命周期，后者的轨迹标签和可控测试更适合算法效果比较。

### 当前 demo 新增、但 Trace2Skill 不等价提供的部分

- 自动恢复企业多轮任务边界，区分寒暄、无目标问答、技术故障和业务失败。
- 使用技能后的 SUPPORT／UPDATE 分流；没有方法增量不生成新版本。
- 个人库和组织库分离，组织技能必须提交和审核后才能跨成员复用。
- 版本 hash、下载权限、历史版本和交付文件核验。

这些是企业工程闭环能力，但“有更多工程组件”本身也不是论文创新；需要后续证明它们在真实约束下减少无效沉淀、保留有效方法或降低维护负担。

## 4. 与简单 prompt 的本质区别

可以把一次简单 prompt 写成：

```text
请阅读下面对话，总结一个可复用的技能，输出 SKILL.md。
```

它只规定了输出文字，不规定以下事实：

- 哪些消息属于同一个任务，哪些是噪音或另一个目标；
- 用户没有说“完成”时如何自动结束并保留未知状态；
- 失败是业务失败、工具故障，还是没有足够证据归因；
- 新技能与已选技能的 UPDATE 如何关联；
- 生成结果是否包含完整文件、测试、来源和基准版本；
- 谁能采纳、谁能提交组织库、谁能加载哪个版本；
- 使用后是否真的读到了技能、是否产生了方法增量、何时形成新版本；
- 如何回滚、去重、计量调用和处理并发版本。

当前 demo 使用 prompt 的位置仍然存在：OpenClaw 和官方 `skill-creator` 负责理解自然语言、写技能文件和辅助脚本。但 prompt 只是链路中的一个模型操作，外层还有规则轨迹、证据冻结、状态机、版本库、权限和交付核验。也就是说，**技能包不是“更长的 prompt”**：它是带触发范围、步骤、边界、资源、测试、版本和来源的可加载运行资产。

同时必须保留一个限制：当前 `SKILL.md` 的具体内容仍由模型生成，规则层主要负责任务归属、路由和发布约束。因此不能把当前系统描述成“完全由算法生成技能”，也不能仅凭包成功生成就声称技能有效。

## 5. 对论文定位的影响

当前最稳妥的定位不是“复现 Trace2Skill”，而是研究一个不同的输入和生命周期条件：**在企业自然会话中，反馈不完整、任务会被多次修订、技能使用受个人／组织授权约束时，如何用可追溯任务证据决定何时新建、何时更新、何时只记录支持，并控制新增模型资源。**

要把这一区别变成论文贡献，至少还需要证明三件事：

1. 相对于问答对链路和简单规则分段，任务级可修订轨迹能减少无效候选，同时不丢失后续被验证的方法。
2. 相对于每次使用都重写，SUPPORT／增量 UPDATE 分流能减少重复封装和版本膨胀，并保留有效更新。
3. 在真实企业任务或充分去标识的数据上，个人采纳、组织审核和跨成员使用能够带来可复核的任务成功、人工负担或交付周期变化。

当前已确认的是功能闭环，不是上述三项效果。024 验收使用构造销售案例，6 次 agent 派发、35 次模型请求、报告 498,204 tokens；成本未知，不能据此证明比 Trace2Skill 或简单 prompt 更省资源。

## 6. 团队统一口径

- 对外介绍当前 demo：**trajectory-driven enterprise skill lifecycle prototype**，或中文“会话轨迹驱动的企业技能生命周期原型”。
- 只有在实现固定基准、局部 patch、失败因果分析、批量合并并完成独立消费评估后，才可以说“包含 Trace2Skill 核心机制的适配实现”；仍需准确引用原论文。
- 不要说“简单 prompt 已经能实现同样功能”。它可以复刻一次文本生成，却没有当前 demo 的任务、证据、权限和版本闭环。
- 也不要说“当前已经超过 Trace2Skill”。当前两者评估对象不同，且本项目尚无真实企业收益和独立测试集结果。
