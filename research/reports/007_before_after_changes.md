# 任务发现与 Skills 闭环：改动前后对照

团队讨论版 · 2026-09-18

本文对照[当前系统说明](初步洞察报告.md)与[拟议落地方案](006_task_discovery_and_instrumentation.md)。改动尚未实施；当前情况按用户提供文档整理。下面的“改后”指完成相应能力后的目标行为，案例是构造示例。

## 1. 整体链路变化

**改前：** 成功且未用 skill 的回合 → 问答指纹 → 聚类 → 工作流 → 门禁 → 生成技能 → 个人采纳/组织提交。

**改后：** 关键交互与执行事件 → 识别具体任务和多次尝试 → 关联纠正、产物与结果 → 提炼经验 → 同类任务归并与存量比较 → 新建/修改/暂存 → 个人采纳/组织提交 → 后续使用反馈再次进入任务整理。

新增的是任务整理、经验筛选和使用反馈连接；原聚类、周期调度、封装与采纳基础继续使用，但输入与决策规则需要调整。

## 2. 逐项对照：改哪里，改什么，得到什么

| 环节 | 改前 | 具体改动 | 改后目标行为 |
| --- | --- | --- | --- |
| 采集入口 | 主要在成功回合完成时记录 | 在消息保存、运行开始/全部终态、产物和反馈产生处记录 | 即使运行失败，目标与失败过程仍可追溯 |
| 采集范围 | 已用 skill 回合、失败/取消等被跳过 | 取消这两类排除，以来源和状态分流；保留授权边界 | 未用 skill 可发现新能力，已用 skill 可贡献演化信息 |
| 分析材料 | 用户提问与最终回答为主 | 补充关键工具结果、产物版本、反馈对象、检查引用 | 能关联做过什么、哪版被纠正、哪些结果有依据 |
| 学习单位 | 一轮问答是一条独立证据 | 新增 task 与 attempt，后台关联事件 | 一件任务的多次改稿属于一个任务及多个尝试 |
| 任务发现 | 从回合描述直接归类任务类型 | 先识别新任务、继续、纠正、变更和无关内容，再归类 | “再改一下”不再默认作为独立需求处理 |
| 成功口径 | 技术正常结束进入成功证据 | 分开运行状态、业务完成、接受信号和检查结果 | 初稿即使正常生成，也可保持未知或被后续标为部分不满足 |
| 失败经验 | 失败不采集，或纠错分散在问答中 | 保存失败—反馈—修正—结果关系，区分原因已知与未知 | 有依据的失败规避可沉淀；偶发异常不自动变规则 |
| 高频判断 | 按回合证据累计 | 按独立任务实例统计，父子任务不重复相加 | 多次重做不再机械放大需求频次 |
| 建模样本 | 聚类最近 5 条脱敏样本 | 选择独立任务及其关键经验，保留条件和不同结果 | 一次长链不再机械占满多个“独立”样本位 |
| 生成门禁 | 四类通道任一命中可进入候选 | 通道触发后共同检查经验、复用用途与已有技能覆盖 | 长度或频次命中后仍可不生成、暂存或修改已有技能 |
| 封装输入 | 泛化工作流草稿 | 工作流附带有效约束、失败规避、来源与适用范围 | 技能具备可追溯的具体方法，避免仅包装通用步骤 |
| 使用后反馈 | 不进入本涌现学习路径 | 记录实际 skill 版本与任务结果，先归因再决定修改 | 能区分选错、未遵循、规则缺失、环境问题与个人偏好 |
| 更新方式 | 新证据可触发同名整体重生成 | 生成可比较的修改建议，保留人工约束，检查影响后采纳 | 修改原因和受影响规则可解释，不凭新证据静默覆盖 |
| 迟到反馈 | 原问答证据缺少修订关联 | 任务和经验带修订号，新增批评使相关候选待重审 | 旧半成品经验可以被纠正，而非一直作为有效来源 |
| 处理进度 | 按已封装数量的位置水位 | 跟踪具体事件、任务修订及候选来源集合 | 可说明哪批证据已处理，避免列表变化使处理范围模糊 |
| 采集可靠性 | 文档描述旁路异步写入 | 留可重投凭据、幂等标识与缺失对账 | 写入失败可发现和补采，不默认过程完整 |

以上行为依赖事件覆盖和任务关联正确。模型分错任务、反馈指向缺失、产物不可读取时，应保留待确认，不能承诺全部自动识别正确。

## 3. 同一段会话，前后各得到什么

构造案例：用户要求“按公司客户分类生成本月经营报告”。初稿 V1 合并错了两个类别；用户指出具体错误，系统生成 V2 并通过分类核对。用户随后要求增加摘要，系统生成 V3，用户接受。期间一次工具调用超时后重试。

| 项目 | 旧链路可能看到的内容 | 新链路应得到的内容 |
| --- | --- | --- |
| 任务数量 | 多个正常结束问答各算一条证据 | 一项经营报告任务，包含多次尝试 |
| 初稿 V1 | 问答正常完成，可被当作成功样本 | 明确关联分类错误，不作为完整成功方法 |
| V2 修正 | 一条新问答，与 V1 的关系容易丢失 | 对 V1 的纠正，保留规则和核对结果 |
| 新增摘要 | 可能混为又一次改稿或新任务类型 | 同一交付的新增约束，不回溯认定 V1 缺摘要是错误 |
| 工具超时 | 中间工具过程不可见；若导致运行失败还可能整轮缺失 | 作为工具异常和重试记录，不直接学习为业务规则 |
| 最终接受 | 未形成任务级版本接受关系 | 明确记录接受 V3，核对结果仍指向实际检查的版本 |
| 经验产物 | 可能形成宽泛的报告/润色流程，或在同一聚类合并后缺失条件 | 提炼“保留指定类别映射、按口径核对”的具体经验 |
| 是否生成 | 多回合可能推动次数门槛 | 只算一次独立需求；经验是否生成另行判断 |

注意：旧链路不必然每轮生成一个 skill，也可能将这些回合归到同一聚类。问题在于统计和建模可能把同一次任务的中间尝试当成多条独立成功证据。

也不能把 V2 的检查直接冒充 V3 检查。若 V3 修改可能影响已检查内容，需保留检查范围或重新检查；用户接受与客观检查仍分别记录。

## 4. 最终系统应产出的三个可见对象

### 对象一：任务卡

> 任务：本月经营报告；目标：经营会使用；约束：保留公司分类。尝试：V1 分类错误 → V2 修正 → V3 补摘要。接受：用户接受 V3。检查：V2 分类核对通过，V3 相应检查覆盖待确认。需求次数：一个实例。

团队能追溯一件事的过程，而不必从多条问答猜测其关系。

### 对象二：经验候选

> 经验：处理该公司分类口径时保留类别映射，并核对汇总前后结果。来源：用户具体纠正、V2 修改及检查。用途：后续同口径经营报告。去向：已有月报 skill 则提修改；没有且有复用理由则形成新候选；信息不足则暂存。

用户看到的是具体用途与来源，不只是一个技能名称和宣传说明。

### 对象三：技能修改建议

> 基于 S@v2 的使用反馈，建议补充“特殊客户类别必须分开处理”的条件。展示旧规则、新规则、触发反馈与影响范围；保留人工修改，按个人/组织流程采纳。

系统能够连接使用与改进；并非每次使用都必须修改。

## 5. 分阶段完成后，能得到什么

| 阶段 | 改动范围 | 做完后的能力 | 尚不能据此声称 |
| --- | --- | --- | --- |
| 第一阶段：任务可追溯 | 新埋点、任务/尝试关联、多维结果 | 能看懂同一任务的尝试和反馈，统计单位切换为任务 | 已具备自动优质生成或自进化 |
| 第二阶段：经验进入生成 | 经验提炼、任务级样本、共同门禁、存量比较、封装输入适配 | 新建、修改、暂存有明确理由，候选可说明具体用途和来源 | 有效率已达到某个数字 |
| 第三阶段：使用进入改进 | skill 版本关联、归因、修改检查、采纳与回退 | 形成发现—生成—使用—反馈—修改的闭环 | 更新一定不退化，或总成本一定下降 |

对当前三个主要痛点的预期作用分别是：减少重复和泛化空泛候选；保留修订与失败规避；让使用后的反馈成为改进来源。实际有用比例、返工减少和成本变化留待落地观察，不承诺提升幅度。

新增代价也应明确：事件与版本存储增多，后台多一层任务关联和经验处理，需要处理错误关联、缺失信息及反馈晚到。增量处理、关键内容引用和先筛经验后封装可以控制投入，但当前没有证据保证净成本下降。

## 6. 对现有基础的复用

原有开关、脱敏存储、后台调度、评估留痕、封装沙箱、草稿及个人/组织流转继续作为基础。聚类角色保留，样本和判断口径改变；人工版本管理继续利用，但须补上使用来源和变更理由。

第一版目标是同会话任务关联与完整反馈链；跨会话只采用明确续接依据。本文为行为与方案对照，未列出未经源码确认的文件修改清单，未修改系统代码。
