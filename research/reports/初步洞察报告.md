# Skills 涌现与演化：当前系统、主要不足与落地方向

团队讨论版 · 2026-09-18

配套定义：[什么是有价值的任务与任务轨迹](005_valuable_tasks_and_trajectories.md)，说明业务价值、经验依据和技能新建的判断边界。

本文帮助团队形成三个共同认识：当前系统如何把对话变成 skill；为什么现在会生成大量低价值 skills、丢失修订经验；接下来需要补齐哪些能力，才能形成生成、使用、反馈、改进的完整闭环。

**当前阶段的目标是先做出来并落地。** 量化暂时用于发现问题、观察方向，不展开实验设计，也不把论文论证要求作为当前交付门槛。

现状依据为[已有链路说明](C:/Users/39835/Doubao/chats/2026-09-18/new-chat/skill-emergence-report/index.html)及用户实际反馈。下文“当前实现”按该说明整理，尚未独立核验源码；“建议”表示待补能力。文中示例均为说明性示例。

## 一、先看全貌：我们已经有什么，还缺什么

现有系统已经具备一条自动生成链路：从用户自然对话中收集信息，归纳任务类型，达到条件后生成技能包，再交给用户纳入个人库或提交组织。它已经解决了“无需用户手工编写，也能产生 skill 候选”的问题。

目前主要有两个断点：**前端采集没有还原用户真正完成一件事的过程；后端没有把 skill 使用结果接回改进链路。** 因此前端容易把中间答案包装成技能，后端难以判断技能是否有用、哪里需要更新。

| 能力 | 当前情况 | 团队需要理解的边界 |
| --- | --- | --- |
| 从自然对话发现任务 | 已有埋点、指纹提取和聚类 | 观察单位是一问一答，不是完整任务 |
| 判断是否生成 | 已有频次、深度、价值、长任务四类条件 | 命中条件不等于经验有用 |
| 生成技能包 | 已有独立封装与校验 | 校验主要确认包存在、可读和符合质量规则，不能说明实际任务收益 |
| 个人采纳、组织提交 | 已有草稿与用户决策、组织提审 | 提交不等于组织已采纳，安装不等于使用有效 |
| 技能版本相关能力 | 已有重生成、人工修订历史、组织版本与回退 | 这些还没有连接到使用反馈驱动的自动改进 |
| 使用后自进化 | 目前缺失 | 使用了 skill 的回合反而被涌现采集排除 |

## 二、当前系统是怎么运行的

### 2.1 系统实际读到什么

只有开关开启、技术上成功完成、没有使用任何 skill 的回合才进入采集。B 端由企业管理员或所有者开启，C 端由个人偏好开启。失败、取消、中断、超时回合被跳过；隐藏的系统编排会话与定时任务不进入这条路径。

对于被采集的回合，系统主要读取**该轮用户提问和 assistant 最终回答**，结合用户、企业、会话、消息等标识以及长度信息做分析。它不读取完整工具过程、文件内容和中间过程消息。

所以，一个用户连续五轮修改同一份材料，在当前链路中可能留下五条独立证据。系统能够看到“每次说了什么”，但缺少结构化关系来说明“为什么重做、哪版被否定、最后哪版被接受”。

进入分析前，邮箱、手机号、URL、路径被替换，空白被折叠，总长上限为 12,000 字符；观察记录保留 90 天，看板主要看最近 30 天，不回填部署前历史对话。原说明对快照在记录还是分析阶段冻结的表述存在差异，具体时点待确认。

### 2.2 六个处理阶段

| 阶段 | 系统做什么 | 产生什么 | 触发节奏 |
| --- | --- | --- | --- |
| ① 观察 | 回合结束后，旁路记录符合条件的问答及关联信息 | 观察记录、脱敏快照 | 随回合结束触发，异步写入 |
| ② 归类 | 模型提取任务、输入、输出、步骤和工具；系统对任务/输入/输出描述计算哈希 | 任务指纹、任务聚类 | 后台约每 60 秒处理 |
| ③ 路径建模 | 从聚类最近 5 条脱敏样本归纳目标、输入输出和执行路径 | 工作流草稿，步骤上限 8 条 | 达到建模条件后处理 |
| ④ 门禁评估 | 判断是否值得进入封装，并检查该用户是否有新增证据 | 评估留痕、封装候选 | 周期评估或手动触发 |
| ⑤ 封装 | 在独立隐藏会话中，依据工作流生成技能包，读回并校验 | SKILL.md 及可选附属文件、不可见个人草稿 | 独立队列约每 30 秒处理 |
| ⑥ 用户决策 | 用户纳入个人、忽略，或提交组织审批 | 可见个人技能或组织提审记录 | 用户操作；也有按设置自动纳入的路径 |

评估默认周期为 B 端 1 天、C 端 7 天，可配置在 1–30 天范围。**后台每分钟归类，不代表证据一够就立即生成。** 生成仍需等待评估与封装。

“路径建模”和“允许封装”也是两个不同判断。前者决定什么时候归纳工作流，后者决定什么时候真正创建技能包，团队讨论阈值时需要说明正在讨论哪一层。

### 2.3 什么情况下会进入生成

当前封装门禁有四条通道，命中任一条即可进入候选：

| 通道 | 原说明中的主要条件 | 意图 |
| --- | --- | --- |
| 频次 | 30 天内成功证据不少于 5 次 | 发现反复发生的事情 |
| 深度 | 不少于 2 次，可复用且步骤、分支或工具等达到条件 | 发现较复杂的任务 |
| 价值 | 不少于 2 次，具有结构化价值信号 | 覆盖有价值但未必高频的任务 |
| 单次长任务 | 池内只有 1 条，满足步骤、工具或超长对话条件 | 让一次复杂任务也有机会沉淀 |

系统还记录“这个用户在这类任务中，哪些证据已经用于封装”。新增证据再次达到条件，可以对同一个 skill 重新封装。

这些设计并非都应移除。覆盖高频、复杂和低频高价值任务是合理目标；需要补的是所有通道共同遵守的有效性判断，避免“对话很长”直接等于“值得建 skill”。

### 2.4 谁的数据在一起，技能最后给谁

| 层次 | 当前单位 | 含义 |
| --- | --- | --- |
| 证据 | 一个回合 | 一次问答算一条观察 |
| 归类与工作流 | 企业 × 任务类型 | 同企业用户贡献同一类任务的样本 |
| 是否生成的个人进度 | 用户 × 任务类型 | 每个人分别记录新增证据、封装和冷却 |
| 交付产物 | 用户 × 任务类型 | 最后形成该用户的个人技能候选 |

因此，**个人产物不等于仅使用个人数据生成。** 聚类和工作流可能来自企业内多人。原说明还指出 C 端用户共用全局组织 ID，需要确认它是否使无关用户进入同一任务池。该边界应检查采集、计数、取样、工作流和最终产物，而不只检查生成时取了谁的文本。

### 2.5 生成之后发生什么

封装不是直接公开发布。系统先生成隐藏草稿，再经过存在性、可读性和质量校验。用户可以纳入个人库、忽略或提交组织；忽略后有 7 天冷却，组织提交复用已有审批流程。技能标识由系统确定，新的同类证据可能覆盖同名技能。

这条链路值得保留的基础包括：理解与创建分开、封装隔离、候选草稿、用户选择、评估留痕和已有版本机制。后续可以在这些基础上补齐任务理解与反馈闭环。

## 三、目前的三个主要问题，分别发生在哪里

### 3.1 技能太多，真正有价值的比例低

**实际反馈：十几个生成结果中，可能只有一个真正有价值。** 目前这是团队使用观察，还不是精确统计。

从现有机制看，低价值候选可能在多个环节累积：一件事反复重做，被计算成多次需求；长对话被当成复杂任务；泛化过程中只留下“整理、分析、检查”等通用步骤；最终封装又把这些薄弱内容写成形式完整的技能包。

例如，用户只是要求同一份材料“再简短一点”“补一个结论”“换个表达”，如果分别作为独立任务建模，就可能产生多个内容接近的“润色助手”。它们看起来都有完整说明，却没有增加值得保存的独特方法。

**目前的洞察：应该先判断有没有值得保留的经验，再决定要不要包装成一个新技能。** 标题、正文和市场信息完整，不代表用户下次使用时会得到额外帮助。

### 3.2 只留下问答，丢掉了做成事情的路径

实际使用经常是“初稿不满意 → 指出问题 → 修改 → 再确认”。有价值的信息不只在终稿里，还在于哪里错了、为什么改、哪些条件必须保留。

当前每轮单独观察，失败回合又被过滤，容易留下多个“系统已经回答完成”的记录。结果既可能把初稿当作成功经验，也可能把最终真正有效的纠错方法丢掉。

**目前的洞察：需要围绕一件任务组织多次尝试，并保留反馈指向。** 单纯把整个会话拼起来再总结仍然不够，因为一个会话可以有多个任务，一个任务也可能跨会话继续。

### 3.3 使用后的信息没有进入改进链路

当前排除“已经使用 skill 的回合”，初衷是避免重复发现已有能力；但同时失去了最直接的学习来源：这个 skill 到底哪里好用、哪里失效、用户补了什么。

同名技能重新生成也不能代替自进化。它可能使用新的样本整体重写，却不知道旧版为什么失败、哪些人工修改必须保留、新版是否解决了原问题。

**目前的洞察：已用 skill 的会话应进入演化分支，而不是被整体忽略。** 每次使用都留下可追踪反馈，有新增可信经验时才修改版本。

## 四、会话应该怎样整理，哪些内容值得沉淀

### 4.1 先还原一个任务，再提炼经验

一条可理解的任务轨迹至少要回答：用户要完成什么、有哪些约束、系统尝试了什么、用户针对哪版提出了什么反馈、后来如何修正、最终有什么结果。

下面用一份客户分析报告举例：

| 对话过程 | 应如何理解 | 应保留什么 |
| --- | --- | --- |
| 用户要求按某业务分类汇总数据 | 明确目标与口径 | 分类约束与资料对象 |
| 系统给出 v1，用户指出类别被错误合并 | 一次未通过的尝试 | 错误位置、受影响规则 |
| 系统修正分类，给出 v2 | 对原错误进行修复 | 修改内容及检查结果 |
| 用户要求再增加管理层摘要 | 新增交付要求 | 新要求的加入时间；不能倒推成 v1 的错误 |
| 系统交付 v3，用户接受 | 一个有接受信号的结果 | 接受针对 v3；事实正确性仍看相应检查 |

这里首先是一件任务，包含多个尝试。可能值得沉淀的经验是“特定分类口径下如何保留映射并核对汇总”，而不是每次改稿都生成一个技能。

### 4.2 不能把哪些信号直接当成成功

| 信号 | 它实际说明什么 | 还不能说明什么 |
| --- | --- | --- |
| 系统正常结束 | 运行完成 | 业务结果正确 |
| 文件保存、下载 | 产物存在或被取用 | 内容通过验收 |
| 用户不再回复 | 没有后续可见反馈 | 用户满意 |
| 用户说“可以了” | 接受某个结果 | 所有事实都经过客观核验 |
| 用户说“不对” | 有负面反馈 | 一定是 skill 规则错，也可能是新增要求或理解变化 |

建议保留“完成、部分完成、失败、未知”等业务结果，同时单独记录用户接受与检查结果。未知可以等待后续关联，不能为了生成技能而补成成功。

### 4.3 噪声与有价值信息的处理口径

| 内容 | 建议处理 | 说明 |
| --- | --- | --- |
| 寒暄、陪聊、无明确任务的泛泛交流 | 不形成技能候选 | 没有稳定任务程序 |
| 天气、时间、单个名词解释等一次性查询 | 通常不生成 | 有问题不等于有值得保存的新方法 |
| 专业问答中包含稳定流程或组织规范 | 保留为待判断经验 | 不能因为形式是问答就过滤 |
| “继续”“再改”“不对” | 关联前一次尝试 | 这些词本身不是新任务 |
| AI 道歉、进度播报、自言自语、无证据的完成声明 | 不作为方法与成功证据 | 保留必要顺序，不提炼为空泛规则 |
| 重复消息、相同内容的自动重试 | 去重并保留重试事实 | 不增加独立任务次数 |
| 偶发网络、平台 Bug、服务超时 | 归入环境诊断 | 不自动变成业务 skill 的永久规则 |
| 有明确原因且验证有效的故障规避 | 保留条件化经验 | 说明版本、环境、办法和恢复结果 |
| 用户任务本身就是排查故障 | 作为正常任务分析 | 不因涉及 Bug 就当噪声 |
| 失败后得到有效修正 | 保留失败与修正的对应关系 | 这是重要的规避经验来源 |
| 失败、中断，尚无可信解决办法 | 保留诊断或待验证材料 | 不编造成功方法 |
| 仅个人表达风格偏好 | 优先放入个人偏好 | 不必建立一个完整 skill |
| 已有技能已经覆盖且没有新信息 | 记录使用结果 | 不重复新建 |
| 系统自己生成、封装、评分的会话 | 与自然用户需求分开 | 避免模型把自己的输出反复当成新证据 |

“不生成 skill”只是去向判断，不代表原始内容对用户没有价值，也不代表应该删除原始记录。

### 4.4 从轨迹到技能，中间应多一次经验判断

建议先得到一份短小的经验说明：**在什么条件下，为完成什么目标，应采用什么方法；要避开什么错误；来源是什么。** 再决定其去向：

- 存量能力没有覆盖，且有明确复用价值：形成新 skill 候选。
- 现有 skill 缺一个条件、步骤或规避办法：形成修改建议。
- 只是个人口味或特例：保留个人偏好或个人分支。
- 结果和方法仍不清楚：暂存待判断，不急于封装。
- 没有新增信息：不生成。

这一步能让“新建一个技能”从默认动作变成多个合理选择之一。

## 五、使用 skill 后，怎样形成真正的演化

建议的闭环是：**关联使用版本 → 收集结果与纠正 → 判断问题来源 → 提出修改 → 检查影响 → 用户采纳或组织提审 → 继续使用。**

### 5.1 先分清问题应该改在哪里

| 使用后的情况 | 合理处理 |
| --- | --- |
| 选中了不适合当前任务的 skill | 调整适用范围或选用方式 |
| skill 写了正确步骤，但实际没有执行 | 检查加载与执行，不能只重复往正文加规则 |
| skill 漏掉必要步骤或业务条件 | 针对缺口提出修改 |
| 用户新增个人偏好 | 进入个人覆盖或分支，避免影响整个组织 |
| 工具故障、权限缺失、环境变化 | 处理环境或依赖条件，不直接认定业务方法失效 |
| 人工接管后才完成 | 保留人工提供的关键修正，不把全部成果记给原 skill |
| 正常完成，没有新信息 | 更新使用记录，不产生无意义新版本 |
| 没有足够反馈 | 保留未知，暂不修改 |

### 5.2 一次修改应该让人看懂什么

团队和用户应能看到：本次基于哪个版本、为什么修改、改变哪条规则、证据来自哪里、影响哪些场景。旧版的有效内容和人工修订需要保留；当反馈来自旧版时，也要检查当前版本是否已经修复。

例如，某汇总 skill 没有区分一类特殊业务，用户多次手动修正后确认了规则。合理更新是加入该类别的条件分支，并检查普通类别仍能正常处理；如果只是一个人的格式偏好，则不应直接修改组织通用版。

现有人工版本与回退能力可以继续利用，但还需要把“版本—使用—反馈—修改原因”连接起来。**有版本号不等于在进化；能够解释这次为什么变、改好了什么，才形成可持续维护的闭环。**

## 六、补充洞察：除了三个主要问题，还应关注什么

以下是结合当前机制得到的分析，具体影响程度还需在落地过程中核查。

| 洞察 | 对当前系统的影响 | 建议关注点 |
| --- | --- | --- |
| 越反复返工，对话越长 | 低效过程可能更容易命中深度或长任务通道 | 长度用于触发分析，不直接证明价值 |
| 最近 5 条不一定是 5 件事 | 同一任务的修改可能占满建模样本 | 按独立任务挑选代表样本，保留不同结果与边界 |
| 相同输入输出，不代表方法相同 | 同为“表格→报告”的任务可能有相反业务规则 | 聚类考虑目标、约束与适用条件；允许分支 |
| 哈希确定，不代表任务理解稳定 | 上游模型换一种任务表述，仍可能拆成不同 key | 区分标识稳定与语义归类质量 |
| 脱敏可能损伤关联关系 | 原文件、目标文件都变成 [path]，无法理解修订对象 | 在允许范围内保留“源文件 A/目标文件 B”等稳定关系 |
| 多次压缩容易丢掉例外条件 | 工作流留下主干，却丢失“何时不能这么做” | 摘要保留关键约束、反例和来源 |
| 忽略不等于没用，安装不等于有效 | 当前用户操作不足以解释候选质量 | 逐步区分重复、不准确、仅个人适用、暂时不需要 |
| 整体重写可能抹掉人工经验 | 新样本不一定含旧版全部有效约束 | 修改应可比较，保留人工更改和旧版 |
| 个人交付可能依赖共享工作流 | 问题不只在最终技能可见范围 | 核对 B/C 端样本、计数、聚类与产物的作用域 |
| 自动生成并非没有成本 | 指纹、重复建模、重试、审核和维护都消耗资源 | 先关注无效候选在哪里产生，避免只优化最后一次生成 |

原说明还提到校验逻辑双份维护、隐藏封装消耗配额、草稿可见性过滤和位置水位等事项，可作为实现核查清单。其中水位清理后究竟会重复还是漏处理，不能仅凭描述下结论。

## 七、建议按什么顺序落地

不是一次性重做整条系统。优先补齐会影响后续所有判断的能力，再连接使用后的学习。

| 顺序 | 优先补齐什么 | 团队应该能看到的结果 |
| --- | --- | --- |
| 1. 统一任务与结果口径 | 关联同一任务的尝试、反馈与产物；区分运行完成和业务完成 | 能看懂一件事如何从初稿走到最终结果，半成品不再混成成功经验 |
| 2. 整理可沉淀的经验 | 区分噪声、偏好、诊断、新经验；保留失败修正和适用条件 | 候选能解释具体复用什么、为何有用、来自哪里 |
| 3. 收紧新建决策 | 所有触发通道都经过价值判断，并先与存量技能比较 | 相近经验优先补充已有能力，不因一次长对话就堆出多个技能 |
| 4. 接入使用后反馈 | 不再整体跳过已用 skill 的会话，记录版本、行为、结果与纠正 | 能追踪哪个版本在哪类任务中遇到什么问题 |
| 5. 形成修改与采纳闭环 | 可理解的修改建议、保留人工约束、检查影响、个人/组织采纳和回退 | 技能能随使用改进，出现不适用时能定位和恢复 |

数据作用域和用户选择贯穿上述各步。落地时先讲清“这是谁的经验，准备用在哪里”，再讨论个人到组织的扩大复用。

近期团队最需要对齐的不是更多阈值，而是三个具体对象：**一条任务记录长什么样、一份值得保存的经验长什么样、一次已有技能修改长什么样。** 用现有真实案例逐个对齐这些对象，能够帮助产品、算法和工程讨论同一件事。

## 八、量化先作为探索：落地后值得观察什么

当前不设实验方案或指标达标门槛。建议先积累能解释问题的记录，再逐步判断哪些指标有意义。

| 想了解的问题 | 可以逐步观察的信号 |
| --- | --- |
| 是否减少了低价值产出 | 展示了多少候选，哪些被认为有用，拒绝原因是什么 |
| 是否恢复了重要经验 | 半成品是否还被当成功，纠正和失败规避是否被保留 |
| 是否真的被复用 | 入库后是否遇到适用任务、是否再次使用、是否仍需重复说明 |
| 是否减轻了人的负担 | 审核候选、修改产物和维护技能各花了多少时间 |
| 演化是否解决问题 | 更新原因、问题是否再次出现、旧能力是否被影响 |
| 组织共享是否有帮助 | 新用户能否使用，哪些角色需要不同规则 |
| 成本花在哪里 | 分析、封装、重试、审核与维护的实际消耗 |

之前提出的三个量化方向继续保留，但目前只作为核算思路：

- **净节省人工时间**：原流程人工时间减去使用后的操作、审核和维护时间，避免重复计数。
- **每成功任务总成本**：执行、失败重试、生成、验证、演化和审核总成本除以成功任务数；未成功投入也要算进去。
- **版本退化率**：旧版成功而新版失败的任务，占旧版成功任务的比例；使用可比任务才有解释意义。

“生成多少、安装多少、调用多少、更新多少版本”能够描述系统活动，但不能单独说明系统有用。当前先用这些记录帮助团队发现问题，不必提前形成完整论文评估体系。

## 附录：已有研究给团队的参考

### A. 工业价值可以怎样表达

| 案例 | 已有工作报告了什么 | 对落地的启发 |
| --- | --- | --- |
| [When Rules Fall Short，WWW 2026 Industry](https://arxiv.org/html/2601.11634v1) | 新问题视频观看占比相对下降 14.9%；发现到策略更新周期 25.8 天降到 7.7 天；报告 GPU 成本 | 自动发现最终要连接到后续结果，也要看总投入 |
| [Data-Driven Function Calling Improvements，WWW 2026 Industry](https://arxiv.org/html/2604.05387v1) | 350 个端到端问答对，分别观察工具执行、最终答案和人工偏好 | 中间步骤正确与最终交付正确需要分开理解 |
| [GenMentor，WWW 2025 Industry](https://arxiv.org/html/2501.15749v1) | 企业部署、20 名员工参与，观察易用性与满意度；[作者发表说明](https://github.com/GeminiLight/gen-mentor) | 用户体验可作为价值证据，但满意不直接等于节省工时 |

这些案例说明工程价值可以体现为质量、人工时间、交付周期、成本和组织复用，不必强行换算成营收。数字属于外部工作，不是我们的目标值。

### B. 哪些已有工作值得借鉴

| 工作 | 与当前方向的关系 |
| --- | --- |
| [AutoSkill](https://arxiv.org/html/2603.01145v2) | 会话提炼、检索、版本合并、个人与共享存储，是系统闭环的重要近邻 |
| [SkillClaw](https://arxiv.org/html/2604.08377v1) | 多用户轨迹、验证更新与共享库同步 |
| [FederatedSkill](https://arxiv.org/html/2606.03143v1) | 分享修改经验，同时考虑不同用户的差异 |
| [SkillEvo](https://arxiv.org/html/2608.13120v1) | 多轮反馈驱动演化，以及退化和膨胀控制 |
| [EvoSkill](https://arxiv.org/html/2603.02766v1) | 从执行失败发现修改机会，并筛选候选 |
| [SAPO](https://arxiv.org/abs/2606.08755) | 关注候选 skill 相对原有能力的边际价值 |
| [ReasoningBank](https://arxiv.org/abs/2509.25140) / [Trace2Skill](https://arxiv.org/html/2603.25158v1) | 从成功、失败经历及轨迹局部经验中学习，提醒我们重视失败分析与有来源的修改 |

更早的参考包括 [Agent Workflow Memory](https://arxiv.org/abs/2409.07429)、[SkillWeaver](https://arxiv.org/abs/2504.07079)、[ACE](https://arxiv.org/abs/2510.04618) 和 [ExpeL](https://arxiv.org/abs/2308.10144)。[SkillsBench](https://arxiv.org/abs/2602.12670v4) 与 [SkillFlow](https://arxiv.org/abs/2604.17308) 也提醒我们：技能存在、被调用，与它实际提供收益，是不同问题。

现阶段借鉴这些工作来帮助落地。未来再结合真实系统积累，判断我们在企业会话的任务识别、纠错经验保留和持续演化上形成了哪些独特方法与发现；不提前把功能清单当成创新结论。
