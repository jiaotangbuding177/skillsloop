# 在现有系统中发现任务与采集任务轨迹

团队落地方案 v1 · 2026-09-18

## 1. 方案结论与改动位置

建议保留现有后台处理、周期评估、封装队列和个人/组织采纳流程，在原来的观察与聚类之间加入“任务整理”层，并把采集入口从单一成功回合扩展为关键事件。

当前：成功且未用 skill 的问答 → 回合指纹 → 任务类型聚类 → 路径建模 → 门禁 → 封装。

建议：**会话关键事件 → 具体任务与尝试关联 → 有依据的经验 → 同类任务归并 → 新建/修改/暂存决策 → 原有封装与采纳。** 已用 skill 的任务也进入同一任务整理层，再分流到演化。

最重要的分工：**埋点负责记录发生了什么，任务整理负责解释这些事件属于什么，候选筛选负责决定值不值得沉淀。** 不在回合结束时直接认定业务成功，也不在采集前要求已知任务 ID。

本方案依据现有链路说明及[任务与轨迹定义](005_valuable_tasks_and_trajectories.md)，属于拟议设计。没有读取系统源码，事件名和字段名为建议名称，不表示已有接口或已实施改动。

## 2. 先分清三个对象

| 对象 | 示例 | 用途 |
| --- | --- | --- |
| 任务实例 task | 为 9 月经营会制作本月客户分析 | 一件具体工作，包含初稿、重试与修订 |
| 尝试 attempt | 初稿 v1；按分类规则修正得到 v2 | 保留同一目标下采取过的不同方案及结果 |
| 任务类型 task family | 按公司口径制作月度客户分析 | 汇总独立实例，判断复用需求与已有技能覆盖 |

现有 clusterKey 可以继续承担任务类型的候选归类，不能当作某次具体任务的 ID。同一任务的多轮改稿仍只算一个实例。一次任务可以包含子任务，但父子层不能相加制造重复频次。

## 3. 埋点方案：哪些时刻、在哪里、记录什么

### 3.1 第一版需要覆盖的事件

服务端持久化、执行器、工具网关和技能加载器是事实来源。前端负责采集用户明确点击的反馈及其目标；不依赖前端“正在生成”之类展示状态推断实际执行。

| 建议事件 | 埋点位置与时机 | 专有内容 | 解决的问题 |
| --- | --- | --- | --- |
| user_message.recorded | 用户消息成功保存后；编辑另记修订 | 消息 ID/版本、回复对象、附件对象与版本、可分析内容引用 | 最初目标、后续批评与新增要求都能保留；即使后续执行失败也存在 |
| run.started | 执行任务被正式接纳或启动时 | run ID、触发消息、父运行/重试来源、执行上下文 | 区分从未运行、正在运行和运行丢失 |
| run.finished | 成功、失败、取消、超时等结束路径统一记录 | 技术状态、错误类别、最终消息引用、用时、可得成本 | 失败不再通过“不记录”表达；正常结束不标业务成功 |
| assistant_output.recorded | 可见回复或交付版本保存后 | 消息版本、关联 run、输出/交付引用 | 保存答案与交付过程；不逐 token 埋点 |
| tool_call.finished | 工具网关或执行器收到结束结果时 | 调用 ID、工具/版本、父 run、重试链、结果状态、错误码、必要输入输出摘要引用 | 区分真实执行、口头承诺、工具异常和恢复 |
| artifact.version_recorded | 文件/报告等产物创建或改写被确认后 | 对象 ID、不可变版本/内容摘要校验值、前版、产生它的调用或消息 | 知道用户批评和接受的是哪一版 |
| skill.usage_recorded | 推荐/选择/加载等真实发生处 | skill ID、实际内容版本或哈希、阶段、关联 run/调用 | 保留用了什么；区分选择和实际加载，不能自动认定有效应用 |
| feedback.recorded | 用户明确反馈被接收时 | 反馈类型、目标消息/产物版本/任务、来源 | 让认可、不满意、具体纠正能落到正确对象 |
| check.recorded | 已有检查器、业务审批或人工检查产生结果时 | 检查对象版本、检查类型、范围、结果、执行者/来源 | 分开文件存在、格式正确、业务核对与用户接受 |

说明：自然语言“不对，按原分类重算”首先是 user_message 事实，后续由任务整理层识别反馈；不要同时当作两次独立用户反馈计数。feedback.recorded 主要承接结构化按钮、审批和明确反馈入口，派生的语义反馈应引用原消息。

工具或外部程序无法提供产物版本、检查结果时，如实标记缺失。没有文件的任务仍可通过回答版本、来源引用和用户反馈建立轨迹；不能为了补字段让模型虚构执行记录。

### 3.2 每条事件共有的字段

| 字段组 | 建议保留内容 | 要点 |
| --- | --- | --- |
| 事件身份 | event_id、event_type、schema_version | 幂等与后续字段演进 |
| 来源身份 | source_record_id、source_revision、origin | origin 区分自然用户、技能生成、模拟评估、定时任务 |
| 范围 | isolation_scope_id、user_id、project/workspace 引用、采集策略版本 | B 端组织与 C 端个人的有效范围由服务端确定，不能沿用不真实的全局组织边界 |
| 会话关联 | conversation_id、message_id、run_id；有则提供 tool_call_id | task_id 初始可空，后续通过关联表补齐 |
| 时间与关系 | occurred_at、ingested_at、caused_by_event_id、来源顺序号（可用时） | 处理晚到与乱序；时间接近不等于业务相关 |
| 内容引用 | 脱敏快照/对象版本引用、覆盖与截断标记 | 不仅存一个之后可能取不到内容的可变路径 |
| 执行环境 | 实际模型、工具、skill 版本（在相应事件中保留即可） | 区分业务规则变化和环境变化 |

不需要所有事件都装满所有字段。公共字段表达身份与归属，专有字段表达具体事实；长文本、附件和工具输出放在受控内容存储，事件记录引用。

### 3.3 内容保留到什么程度

- 保留用户目标、纠正、新增约束及可见回答的可分析版本；现有消息存储可靠可取时复用引用，否则按现有允许范围保存脱敏版本快照。
- 工具记录先保存名称、结果、错误和关键对象引用，按需读取与任务有关的参数及输出，避免整段工具日志无差别进入模型。
- 产物保留可识别版本和与本次修订相关的差异或检查摘要。全量文件读取不是第一版的前提，也不能在缺少内容时声称已完成业务核验。
- 去标识后保留关系，例如“源表 A”“输出表 B”，不要把所有对象折叠为同一个 [path]；标明哪些字段被裁剪或缺失。
- 不采集隐藏内部思维链。系统自己的封装与模拟不计自然需求频次，但保留来源标记方便排除。
- 沿用并核对既有授权与保留策略。来源被删除或撤回时处理相关快照与派生引用，不用复制内容绕过用户删除决定。

### 3.4 采集过滤需要如何改变

保留开关和范围限制；移除“只有 run 成功才留记录”“使用任何 skill 就整个跳过”两个学习过滤条件。失败和技能使用由下游分流处理。

原来隐藏封装会话不作为自然使用证据的原则继续保留。定时业务任务是否纳入单独决定，来源标记先区分清楚，不把系统生成活动混进用户需求。

## 4. 怎样从事件里发现任务

### 4.1 先记录，后关联

用户消息保存时，不等待模型识别任务才能落点。先用已有 conversation/message/run 标识记录事实，后台任务整理器再建立 event → task → attempt 关系。一个事件可关联多个任务或子任务；不确定时保留待归属。

第一版优先做**同用户、同会话内的任务关联**。跨会话仅在用户明确引用旧任务、选择继续旧任务，或存在可信任务标识时续接；共享文件只能作为线索，不能单凭文件相同自动合并。组织任务类型归并与跨人拼接某次任务是两回事。

### 4.2 后台每次看什么

可以沿用现有约每 60 秒后台处理节奏，按有新增事件的会话增量整理。触发来自新用户消息、运行终止、产物/检查更新及明确反馈；工具细碎事件先聚合，不每次返回都调用模型。

一次整理的输入包括：

1. 当前会话的活跃与最近暂存任务卡：目标、对象、约束、当前尝试和结果证据。
2. 上次处理后新增的消息、关键执行事件与产物变化。
3. 新消息明确指向的旧消息、旧版本或旧任务；即使不在最近窗口内，也按引用补取。
4. 当前实际使用的 skill 版本，以及已有的用户接受、检查结果和缺失标记。

不重读全部历史，也不只取最近五条。任务卡是可更新的索引，原始证据引用保留；摘要压缩不能抹去尚未解决的批评和约束。

### 4.3 每条新输入应作什么判断

模型用于理解目标及语义关系；运行状态、消息身份、产物版本等由系统事实提供。模型输出必须带来源事件，不能创造没有输入依据的文件、检查或成功标签。

| 整理结果 | 例子 | 对任务的操作 |
| --- | --- | --- |
| 新任务 | “帮我整理本月客户分布” | 建立目标、对象和已知验收条件 |
| 继续已有任务 | “接着处理剩余地区” | 关联原任务，补充后续行动 |
| 纠正已有尝试 | “上版把两类客户合并错了” | 指向被否定版本，记录纠正；实际重做时产生新尝试 |
| 新增/改变要求 | “再加一页管理层摘要” | 更新目标或约束版本，保留旧版本；不倒推旧方案错误 |
| 明确接受/拒绝 | “这一版可以了” | 更新对应版本的接受证据，不自动扩大为客观全部正确 |
| 同时多个目标 | “重算分类，另外写一封邮件” | 拆出目标片段，关联原任务与新任务；共用来源不重复统计 |
| 背景/材料 | 用户上传参考表，没有新目标 | 挂到相关任务或暂存上下文 |
| 非任务/无关噪声 | 寒暄、重复进度播报 | 不创建任务；必要时保留顺序 |
| 无法判断 | “这个不对”且指向不明 | 标记待归属；补上下文，不强行认定最近任务失败 |

模型判断置信程度只能帮助分流，不能把一个自报高分当事实。第一版遇到多义内容可以暂缓沉淀；不必为了学习系统频繁打断用户正常工作。

### 4.4 什么情况下算同一个任务

优先看：用户明确续接或回复关系 → 交付对象及版本 → 目标与有效约束是否延续 → 语义与时间线索。

- 同一报告换语气、补数据、修错误，通常延续同一任务。
- 同一会话开始另一个可独立交付、独立验收的目标，可以新建任务。
- 同类工作换到新的业务周期或新的独立业务对象，通常是新实例，再归入同任务类型。
- 涉及多个对象的批量工作可保留父子关系，不能按文件数、工具数直接增加任务数。
- 分错后允许拆分或合并，并保留修改前后的映射和原因；更新依赖这些任务的统计与候选，不能只改任务名。

## 5. 任务卡与尝试记录需要呈现什么

这些是逻辑对象，后续可映射到现有表，不要求本轮新建对应数据库。

| 逻辑对象 | 最小内容 |
| --- | --- |
| 任务卡 | task_id、范围、目标、对象、约束及版本、用途、来源、父任务、生命周期、业务结果、接受/检查证据、当前修订号 |
| 尝试记录 | attempt_id、task_id、所针对目标版本、来源运行/行动、输出版本、被批评位置、后续替代关系、技能参与情况 |
| 事件关联 | event_id、task_id、attempt_id（可空）、消息片段、关联角色、来源与整理版本 |
| 经验候选 | 触发条件、具体方法/约束/反例、支持事件、证据类型、未知项、建议去向、来源任务修订号 |

一次技术重试不必成为新的业务尝试；重试关系记录在运行或调用层。只有形成替代方案、重新交付或明确重做路径时，才创建新的尝试；一个尝试也可跨多个运行。

任务卡上分开两组状态：

- **工作是否还在继续：** 活跃、暂存、关闭；后续可重开。
- **业务结果是什么：** 未知、部分完成、完成、失败；另记用户接受与客观检查分别是什么。

运行结束不关闭整个任务；会话闲置只意味着暂存，结果仍可未知。用户明确放弃表示终止，不自动证明所有方法失败；明确接受某版本提供接受证据，事实正确性仍看相应检查。

## 6. 什么时候提炼经验，什么时候进入聚类

采集与任务识别可以持续进行，提炼不必每条消息都触发。建议在出现有信息量的变化时整理一份经验候选：

- 用户明确接受了某个交付版本。
- 有与任务目标相关的检查结果。
- 具体纠正得到响应，且有可查的变化或结果。
- 用户明确给出长期业务规范：作为规范来源，不伪装成功执行。
- 任务暂存时：只汇总已知经验和缺失，不能因暂存自动生成技能。

每份候选依据固定的任务修订号与事件集合。后续批评或迟到结果到来时，重新整理受影响经验，候选标记待重审；已经入库的则提出修改建议，不静默覆盖。

然后才将同类的任务或经验归并到原来的聚类层：

1. 归类依据目标、输入输出、程序和关键约束，现有指纹作为线索。
2. 频次改为独立 task_id 的次数；统计观察到的需求与有依据的成功分别是多少。
3. 建模样本按独立任务与条件挑选，避免五条都来自同一次改稿。
4. 频次、深度、价值和长任务仍可触发查看，但都经过经验可用性与存量比较。
5. 分流为新建 skill、修改已有 skill、个人规范/偏好、待分析或不生成。

如果为了保持兼容暂时仍向旧封装层提供 workflow JSON，建议把经整理的经验及条件映射进去，另附来源与结果状态。旧的短步骤表示无法承载的关键边界，不应在适配时再次丢掉。

## 7. 用一段对话串起埋点与任务发现

以下为构造示例。

| 实际过程 | 埋点记录 | 后台理解 |
| --- | --- | --- |
| 用户：“按公司分类做本月客户分析” | user_message M1 | 新任务 T1，目标 G1 |
| 执行器开始运行 R1 | run.started，关联 M1 | T1 的首次尝试 A1 |
| 工具读表、生成初稿 V1 | tool_call.finished、artifact.version_recorded | 关联 A1 与 V1 |
| 系统回答完成 | assistant_output、run.finished=正常 | A1 执行结束，业务结果仍待定 |
| 用户：“V1 把 A、B 类合并错了” | user_message M2，引用 V1 | T1 的纠正，否定对应部分，不新建“改稿任务” |
| 系统重算形成 V2 | 新运行与产物事件 | 新尝试 A2，修订 A1，保留分类约束 |
| 分类核对通过，用户：“这样可以” | check 指向 V2；用户消息/明确反馈 | V2 有检查和接受证据，经验来源清楚 |
| 用户：“另外写一封通知邮件” | user_message M3 | 新任务 T2；不混进 T1 的经验 |

最终需求统计是 T1 一次客户分析、T2 一次邮件任务；R1 正常结束和后续重算不会把 T1 算成多次成功。

若 R1 中途失败，已有 M1、run.started 和失败结束仍然留下目标及失败路径。若 A2 用了 S@v3，skill 事件将反馈与该版本关联，后续可以判断是补充 S，而非默认新建技能。

## 8. 如何接入现有链路

| 现有位置 | 建议变化 | 可继续复用 |
| --- | --- | --- |
| run.completed 观察入口 | 增加消息保存、全部结束状态、工具/产物、反馈、skill 事件 | 原有开关、后台处理框架 |
| observations / snapshots | 承接事实及可追溯版本；不直接写业务成功 | 脱敏存储与保留机制，经核对后使用 |
| 60 秒归类 worker | 先整理事件到任务；对变更任务输出经验，再做任务类型归类 | 定时唤醒、增量队列 |
| task_clusters / workflow | 输入从回合短摘要改为有来源的任务经验 | 聚类与工作流存储角色 |
| 用户证据水位 | 改为已处理事件/任务修订的明确记录，不只依赖列表位置 | 用户与任务类型独立进度 |
| 周期评估 | 统计独立任务，区分新建与修改 | 周期调度、决策留痕 |
| 封装与确认 | 消费经筛选的经验；修改候选携带旧版本和变更依据 | 独立封装队列、草稿、个人/组织采纳 |

入库身份不因模型改写标题而改变。关联结果使用版本记录，失败重跑不得重复增加任务或候选。运行重试是真实事件，事件重投是传输重复，两者需要区分。

采集可靠性需要补一个基础保障：优先在业务记录保存时留下可重投的采集凭据，再异步处理；暂时不能原子保存的来源，增加源记录对账与补采。仅用 fire-and-forget 且无恢复路径会使任务缺口不可见。对已经 started 却长期无终态的运行，依据执行器事实补齐状态，无法确认则标记缺失，不猜测成功。

## 9. 分三步落地

**第一步：先保证能还原发生了什么。** 补齐消息与运行全状态、skill 版本、输出/产物引用；已有工具网关和检查结果一并接入。同会话识别任务、修订和接受关系。此时即使不能读取所有附件，也能先阻止把五次改稿算成五个任务，但必须承认业务验证仍不完整。

**第二步：形成可用于生成的经验。** 补齐关键产物变化和反馈指向，输出任务卡与经验候选；把聚类、频次和门禁输入切换为任务级证据。新建前比较存量技能，复用原有封装与确认。

**第三步：接回使用后演化。** 已用 skill 任务提供内容缺口、适用范围或执行问题的修改依据；保留人工更改，沿用个人/组织采纳与回退。再逐步扩展有明确依据的跨会话续接。

切换期间原回合链路与任务链路可以用于排查对照，但不能同时独立生成相同候选；明确某个范围由哪条链路产生正式候选。历史只有问答的记录可以保守整理，缺失的工具过程、版本和反馈不能补造。

## 10. 团队对齐时需要的三个可见结果

1. 打开一项任务，能看到它从哪条需求开始、经历哪些尝试、哪个版本被纠正或接受，以及还有什么不知道。
2. 打开一份经验候选，能说清在什么条件下复用哪条方法、来源在哪里、为何新建或修改。
3. 打开一次 skill 修改，能追到实际使用版本、触发反馈与受影响规则。

当前不设实验门槛。后续实现前需要核对已有消息、run、工具、产物和技能加载接口能提供哪些字段，以及实际授权与存储边界。本方案不假设当前已经具备所有埋点接口，未进行代码修改或数据接入。
