从对话到技能：Skill 涌现链路深度研究报告

每个员工与 AI 的日常对话，如何被系统自动「看」成证据、归纳成任务、沉淀成可复用的个人技能？本报告以科研/产业视角（非代码级）拆解整条链路：读入什么、经过哪些中间态、调用了多少次大模型、以及当前设计里最值得警惕的三个缺陷。

研究对象：InsightWeaver 技能自动涌现系统 研究视角：架构思路级 · 科研 / 产业向 完成日期：2026-09-18 事实来源：全链路深度解析材料（全文核验）
◆

一句话结论：这是一条「用真实对话当证据、用多通道门禁判断时机、用确定性命名的沙箱封装保证可控、用草稿态加人工确认把最终决策权留给用户」的完整涌现闭环。但它终止于「生成并交付」——没有把技能上线后的表现回灌到产物里，因此尚未闭环到「自我进化」；同时存在一个数据边界（C 端跨客户共用聚类池）和两个业务口径（无任务概念、无失败判定）级缺陷。

02

问题一：系统读入了什么信息

数据面

最容易被误解的一点：系统不以「会话」为单位读取，也不读完整对话记录。它读的是「回合」——一次一问一答，且只取其中两条消息。一个 5 个来回的会话，会被拆成 5 条独立证据。

2.1 先澄清业务口径：四个层次、四种单位，不可混用

整条链路上，「以什么为单位」在不同环节是不同的。把四层混为一谈，是理解这条链路最常见的错误。

层次单位载体含义
证据一个回合（一问一答）观察记录表原子单位。一次会话 5 个来回 = 5 条证据。
归类企业 × 任务类型任务聚类表同企业内同类任务无论谁做的，归到同一聚类；标题、路径模型在此共享。
决策人 × 任务类型用户进度表这个人在这类任务上攒了多少证据、上次封装到哪、是否被拒绝过。
产物人 × 任务类型个人技能配置最终交付到这个人的技能库，一份技能。
两个由此推出的业务结论

归类是跨人的、决策是私人的：企业内所有人的对话都在贡献「我们这儿存在这样一类任务」的全景判断；但技能逐个人独立生成，A 封装成功不阻塞 B，B 也不会因为 A 的对话直接拿到技能。
「企业」在 C 端不等于「客户」：这是第 2.6 节的核心风险，也是本报告优先级最高的一条发现。

2.2 每个回合只读两条消息：用户提问 + 最终回答

记录阶段只写入结构化标识（企业、用户、回合、会话、消息 ID、回合规模信号），不复制原文；到分析阶段才按两个消息 ID 精确取回「用户提问」与「最终回答」这两条消息——不是按会话全量读取，也不会读中间轮次。即使聊天后来被软删除，建模样本仍可从冻结快照取用。

读取对象说明
用户提问本回合 user 消息原文（脱敏截断后入分析）
最终回答本回合 assistant 最终消息原文（脱敏截断后入分析）
结构化标识企业 / 用户 / 回合 ID / 会话 ID / 消息 ID / 会话规模 / 回合字数
不读取工具调用明细、中间过程消息、文件内容、失败与取消回合、hidden 会话、定时任务会话

2.3 满足三个条件才会被采集（外加两条结构性排除）

「是否所有企业、所有人的会话都被采集」——范围上基本是，但不是无条件的全量，要同时满足：

条件含义
① 开关已开启B 端由企业管理员/所有者开启；C 端由用户个人偏好开启。关闭即彻底不采集。
② 回合成功完成失败、取消、中断、超时均不留任何记录。
③ 未使用任何技能本轮若选了技能，整个回合跳过。
结构性排除hidden/系统编排会话不进入此路径；定时任务走独立通道，不产生本地消息对。

第 ③ 条的业务意图值得单独说明：它让涌现只学习「还没有技能、但人们反复在手工做的事」——已经被技能解决的领域不会被重复投入。副作用是：重度使用技能的用户，产生涌现证据的速度天然更慢。

2.4 入分析前的处理：四类脱敏 + 截断 + 双向净化

处理规则作用
邮箱脱敏邮箱格式 → [email]防个人信息外泄
手机号脱敏大陆手机号 → [phone]同上
URL 脱敏链接 → [url]同上
路径脱敏文件路径 → [path]防内部结构泄露
空白折叠 + 截断换行/连续空格 → 单空格；总长上限 12,000 字符控制建模成本与噪声
双向净化入模型前脱敏一次；模型输出落库前再脱敏一次防模型回吐敏感原文

保留策略：观察记录保留 90 天；看板按最近 30 天聚合；部署前的历史对话不回填。

2.5 分析产出只保留「泛化短语」，不留原文

指纹与工作流都被要求输出泛化后的短语——禁止复述姓名、手机号、邮箱、组织名、文件名、路径、网址或业务原文。系统提示同时声明：「只依据给定请求与结果提取事实，不判断是否应该创建 Skill」。

2.6 数据边界：C 端「一个企业」不是一家公司（P0 级风险）

系统把「企业」作为聚类池的隔离边界（唯一键 = 企业 × 任务类型）。这在 B 端是设计意图——一家真实公司内共享任务类型。但 C 端存在一个硬编码事实：所有 C 端用户共用同一个全局组织 ID，且所有人被自动挂载为这一个组织的成员。

P0 · 跨客户数据混用

C 端用户的脱敏对话可能成为另一个不相干用户技能模型的素材；「出现 5 次」的门槛在 C 端是全体用户合计 5 次，几乎瞬间满足；同一聚类下不同用户会拿到同名技能；聚类工作流会被「最近任意用户样本」持续覆盖。文档口径未提及此边界，很可能不是刻意设计。最小修复：建模取样本时只取该用户自己的样本。

序号中间态说明与关键约束

状态迁移

3.3 时间节奏：一个「涌现」最快的诞生路径

时间层说明
触发（同步）回合跑完 → 计费结算 → 发「完成」事件前，请求内启动埋点；void 甩出不阻塞用户。
写入（异步）紧接着落库观察记录与快照；用户收到「完成」的同时后台在写。
归类（60s）后台 worker 轮询待处理记录，做指纹提取与聚类（每轮 ≤20 条）。
评估与封装评估按上海零点周期闹钟（B 端默认 1 天 / C 端默认 7 天，可夹在 1–30 天）；封装由独立队列每 30s 轮询。
关键节奏事实：观察是实时的，「够不够格生成技能」的判断只在周期末做

不存在「攒够 5 次立刻涌现」——最快也要等到下一个评估周期末。上一轮 60s 的 worker 只负责归类，不负责判断时机。

路径建模		系统提示（只建模、不创建、不发布）+ 聚类内最近 5 条脱敏样本（跨用户）工作流 JSON：短标题（≤12 字）/ 目标 / 输入输出契约 / 步骤（≤8）/ 工具类别（≤8）/ 置信度
LLM#3
封装主调用		工作流 JSON（6 字段）+ 市场信息草稿（5 段中文）+ skill-creator 的 SKILL.md 全文与文件树 + 确定性 skillKey + 安装/校验指令安装到个人工作区 skills/<skillKey>/ 的完整技能包（核心为 SKILL.md：frontmatter + 正文 + 强制「市场信息」章节），并返回技能名称与摘要
LLM#4
市场修复		原 SKILL.md + 质量校验失败问题清单 + 市场信息草稿（禁止改 key、禁止删正文）修正后的 SKILL.md（仅市场信息章节变化），随后重新读回、重新校验

4.2 调用次数怎么算：一个技能的典型成本

口径数值
单条观察（数据侧）指纹提取 1 次 LLM；每轮 worker 批量处理 ≤20 条
单个聚类（归纳侧）路径建模 1 次 LLM（每次重新建模触发一次）
单个候选（生成侧）封装主调用 1 次 + 市场修复 ≤1 次 → 主链路 ≤2 轮
最坏情况封装失败重试上限 3 次（MAX_ATTEMPTS=3）→ 单候选最坏 6 轮 LLM；幂等键按证据批生成，重试不重复建候选
一次技能诞生的典型总成本N 条观察 × 指纹 + 1 次建模 + 1–2 次封装 ≈ N + 2~3 次 LLM 调用
设计要点：为什么「创建」必须单独一轮调用

归纳轮（LLM#1/#2）没有任何创建权限——它们只产出 JSON 草稿；生成轮（LLM#3/#4）在 hidden 沙箱里执行，只挂 skill-creator 一个技能、关闭全部副作用、不写会话历史、不产生新观察（系统不会观察自己）。权限隔离 + 确定性命名 + 三段验证，共同保证「LLM 的自由发挥」被约束在可控范围内。

05

问题二：目前链路的缺陷是什么

风险面 · 按优先级

缺陷分两类：产品口径问题（不是 bug，但需要决策，优先级最高）与工程风险（实现层的取舍）。此外还有一项能力级缺口：没有实现「技能自己的进化」。

5.1 三个必须决策的产品口径问题

P0 · 数据边界

C 端跨客户共用聚类池

所有 C 端用户共用同一个全局「企业」，聚类池跨客户共享。用户 A 的脱敏对话可能成为用户 B 技能模型的素材；「5 次」门槛在 C 端全体合计、几乎瞬间满足；聚类工作流被「最近任意用户样本」持续覆盖；不同用户拿到同名技能。

最小修复：建模取样本时只取该用户自己的样本；或把聚类键收紧为含 userId。
P1 · 任务口径

没有「任务」概念，多轮打磨被拆散

一次多轮打磨的任务被拆成 N 条独立证据，第一轮的中间产物被当作成品建模；一次任务能刷满「出现 5 次」门槛；长会话会误触提前建模快车道；改稿指令可能自己长成「润色助手」类技能。

会话内合并 + 门槛加会话维度 + 引入任务完成信号（用户满意/闲置结束/产物落盘）。
P2 · 成败口径

没有失败判定：失败靠「不记录」体现

数据模型预留成功/部分成功/失败三档，但没有任何代码写失败。答非所问、用户看完重问一遍——只要技术上跑完，就被计为一次成功证据。「忽略」按钮是唯一的、事后的反馈通道。

为失败找到生产者：下轮表达不满、「不对/重新来」、短时间内反复重做、会话被放弃。

5.2 能力级缺口：链路终止于「生成」，尚未闭环到「进化」

没有 Skill 自己的进化

看板「持续进化」指标硬编码为 0（注释明确写「Darwin 未交付」）；skill_evolution 只是一个已预留的计费分类常量，没有任何产出方。现有能力只有：同聚类同用户再次封装会覆盖同名技能（整体重写，不是差量进化）、组织提审的人工版本管理（版本号/快照/回滚）、以及未接线的执行上下文契约。

已有能力它是什么为什么不是「进化」
同 key 重生成新证据再次达标 → 同名 skillKey 整体覆盖无 diff、无版本对比、无保留人工修改的合并；新版本可能更差且无提示
聚类版本计数lastPackagedVersion 每次封装 +1纯计数器，没有任何代码读它做决策
个人技能修订历史用户手动回滚到历史版本人工机制，不是系统按反馈自动改进
组织提审版本号提审时版本号 +1，支持回退式重提人工驱动，不感知运行效果

要实现「进化」至少缺四块：运行反馈采集（目前只有使用次数，没有技能维度的成败率/满意度）、差分与合并引擎（旧版 vs 新证据推导版的结构化 diff）、版本化产物与灰度（同名即同物，无法并存两版）、进化专用执行通道（计费前缀已预留但无消费方）。

5.3 工程层的设计取舍与风险

取舍现状风险
聚类键确定性哈希不用 LLM 聚类键，改用具名元组哈希「可控的过度合并」，让门禁能收敛——以牺牲细粒度切分为代价
水位位置切片按成功列表位置切「新证据」，非时间切片若观察被 90 天清理导致顺序前移，理论上旧证据可能被重新计为新证据（当前窗口 30 天 < 保留 90 天，暂不触发）
质量校验双份TS 与 Python 各存一份，靠注释约定同步改一侧忘另一侧 → 「KM 说通过、后端说失败」的静默不一致
hidden 会话计费hidden 会话仍消耗企业「对话次数配额」+ Token 计费若产品预期「系统自动行为不占用户配额」，需确认口径
草稿可见性单字段isVisible 单一字段 + 3 处读取侧过滤新增「列出个人技能」出口时漏加过滤 → 草稿泄漏
文档与实现不一致文档称「不保存 Prompt 与最终回答」，实际快照表存了脱敏截断后的提问与回答全文（最长 90 天）对外说明前需修订文档口径

5.4 改进路线图（按性价比排序）

  • 止血：给门禁加会话维度
    「5 次回合」改为「5 个不同会话/不同天里的任务」——低改动，立即消除「一件事做 5 遍刷门槛」与长会话误触快车道。
  • 建模样本按用户隔离（C 端数据边界最小修复）
    只取该用户自己的样本——不牺牲聚类共享收益，直接切断跨客户文本取用。
  • 会话内合并 + 失败判定生产者
    同一会话连续轮次合成一条观察、以最后产出为最终产物；为 PARTIAL/FAILURE 找到写入方（不满表达、重做、放弃）。
  • 引入任务完成信号
    用户明确满意 / 会话闲置结束 / 产物落盘下载，作为「够格当样本」的判据——这是根治「中间产物当真品」的方案。
  • 进化闭环（Darwin）
    反馈采集 → 差分合并 → 版本灰度 → 进化执行通道；让链路从「生成并交付」演进到「生成-使用-反馈-改进」。
06

产业与科研视角：这条链路回答了什么问题

范式思考

把这条链路放到行业坐标系里看，它代表的是一种正在成型的范式：让系统从「人的自然使用行为」中自动归纳可复用技能，而不是等人显式地「教」它。理解这一点，才能判断它的设计取舍与缺口。

6.1 三种技能获取范式的对比

范式显式教学隐式涌现（本链路）反馈驱动进化
技能来源用户/专家主动编写技能包从成功对话中自动归纳从使用效果与反馈中改进
证据人的意图与知识行为数据（回合 + 结果）运行表现（成败/满意度/产物质量）
关键机制创作规范 + 人工质量把关聚类 + 门禁 + 沙箱封装反馈回流 + 差分合并 + 灰度
主要风险覆盖慢、维护贵证据污染、边界越权（本报告 P0–P2）反馈信号稀疏、回灌失控
本链路状态部分存在（组织提审复用通用链路）已上线（默认 active）未实现（Darwin 预留未交付）

6.2 可迁移的设计原则（从本链路抽象）

原则本链路的做法
证据与决策分离归类是跨人的、决策是私人的——「我们这儿存在这类任务」和「你要不要拥有这个技能」是两个不同的问题，用不同单位承载。
多通道门禁优于单一频次频次 / 深度 / 价值 / 单次长任务四通道 OR——只靠「出现次数」会漏掉高价值低频任务，也会被刷量污染。
确定性锚点约束 LLM聚类键、技能 key、标题长度全部由系统确定性生成/裁剪——LLM 只做「理解与生成」，命名与身份不交给模型。
创建权限隔离归纳轮无创建权限；生成轮在 hidden 沙箱（单技能白名单 + 关闭副作用）里执行，且系统不会观察自己。
草稿态 + 人工确认生成即草稿（isVisible=false），确认才可见——把「系统替你生成」与「你决定拥有」之间留出人的决策点。
可归因的否决每次评估写完整诊断快照——「为什么没涌现」可事后复盘，而不是黑盒沉默。

6.3 三点产业观察

  1. 「涌现」的商业价值在成本结构上成立：数据侧成本（指纹 1 次/观察）随使用量线性增长，但生成侧成本被门禁压得很低——只在真正值得时封装。这个结构让「从零到一建技能」的边际成本趋近于零，是它能默认开启（active 模式）的原因。
  2. 数据边界是这类系统的合规红线：「用行为数据自动生成个性化产物」天然有跨用户取用的诱惑与风险。C 端全局共享聚类池（P0）提示了一个普遍问题：功能上的聚类边界 ≠ 法律上的客户边界，产品在扩展数据共享范围前必须显式回答「谁的数据进了谁的技能」。
  3. 「生成」与「进化」之间的差距，是下一代产品的分水岭：当前链路证明「从对话到技能」已可闭环；但技能上线后的表现没有回流，导致技能只能被整体重写、不能成长。谁先补上「反馈 → 差分 → 灰度」这条回路，谁就把「涌现」从一次性资产变成了持续增值的资产。
