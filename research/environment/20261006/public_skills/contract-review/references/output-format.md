# Word 批注输出规范 · Output Format

> 审查意见从"JSON 结构"到"Word 原生批注"的转换规范。包含样式、作者、颜色、长度、格式等硬性要求。

---

## 输出文件命名

```
reviewed-{原文件名}-{YYYYMMDD-HHmm}.docx
```

**示例**：
- 原文件：`采购合同-v2.docx`
- 输出文件：`reviewed-采购合同-v2-20260806-1650.docx`

---

## 批注结构（每条必含）

每条 Word 批注由以下要素构成：

### 1. 标识头（必带）

```
【风险等级】条款编号 - 问题标题
```

| 风险等级 | 标识前缀 | 颜色 |
|---|---|---|
| 高 | 【高风险】 | `#cf222e` |
| 中 | 【中风险】 | `#9a6700` |
| 低 | 【低风险】 | `#d0d7de` |
| 💰 金额异常 | 【金额异常】 | `#bf8700` |
| ⚔️ 条款冲突 | 【条款冲突】 | `#8250df` |
| ⚠️ 合规 | 【合规】 | `#cf222e` |
| 📝 🆕 文本瑕疵 | 【文本瑕疵】 | `#8c959f` |

### 2. 问题本质（必带）

> 简洁描述条款问题（≤ 100 字）

### 3. 法条引用（高风险必带，中风险建议）

> 《[法律全称]》第 [X] 条  
> （如《民法典》第 506 条）

### 4. 量化损失（高风险必带）

> 损失预估：按合同金额 X 万计算，最坏情况需支付 Y 万

### 5. 修改建议（必带）

> 建议修改为：[具体修改后内容]  
> 修改理由：[说明修改的法理依据]

### 6. 检索时点（高风险必带）

> 检索时点：YYYY-MM-DD（调用 fyopen-lawsearch 的日期）

## 🆕 文本瑕疵批注特殊规范

**与法律风险批注的关键区别**：

| 维度 | 法律风险批注 | 文本瑕疵批注 |
|---|---|---|
| 计入风险等级统计 | ✅ 是 | ❌ 否 |
| 必带法条引用 | ✅ 高风险必带 | ❌ 不必带 |
| 必带损失预估 | ✅ 高风险必带 | ❌ 不必带 |
| 必带检索时点 | ✅ 高风险必带 | ❌ 不必带 |
| 颜色 | `#cf222e / #9a6700 / #d0d7de` | `#8c959f`（中性灰） |
| 标识前缀 | 【高/中/低风险】 | 【文本瑕疵】 |

**模板**：

```
【文本瑕疵】第 X 条 - [问题标题]

文本类别：[标点 / 排版 / 错别字 / 语义歧义] / [子类]
问题原文：[摘录 ≤ 50 字]
问题描述：[≤ 100 字]
修改建议：[具体修改方向]

（注：文本瑕疵为文本质量维度，不构成法律风险等级，仅作严谨性提示）
```

**使用注意**：
- 文本瑕疵与法律风险**独立呈现**——Word 中分两栏或两节展示
- 文本瑕疵的"高/中/低"等级仅表示对合同可读性的影响程度，与法律风险高/中/低**无对应关系**
- 文本瑕疵严重时（如主谓不一致导致条款失效），应在 Step 1+ 单独标记为法律风险

## 批注样式规范

### 作者 / 缩写 / 日期

| 字段 | 值 |
|---|---|
| **作者** | `admin` |
| **缩写** | `AD` |
| **日期** | `YYYY-MM-DDTHH:MM`（ISO 8601，UTC+8） |

### 字体

- 默认 Microsoft YaHei UI / 苹方 / Noto Sans SC
- 字号：10-11pt
- 行距：单倍行距
- 颜色：默认（黑色）

### 颜色映射（高亮/标注）

| 风险等级 | 颜色代码 | 用途 |
|---|---|---|
| 高 | `#cf222e` | 段落背景色或文字色 |
| 中 | `#9a6700` | 段落背景色或文字色 |
| 低 | `#d0d7de` | 段落背景色或文字色 |

> **注意**：颜色通过 `officecli mark` 命令应用到段落，批注本体仍为黑色字体。

## 批注长度规范

| 等级 | 长度限制 | 超出处理 |
|---|---|---|
| 高 | ≤ 500 字 | 拆为多条批注（"问题" + "建议"） |
| 中 | ≤ 300 字 | 同上 |
| 低 | ≤ 150 字 | 单条批注 |

## 批量插入命令模板

### 方式 1：单条插入（适合少量批注）

```bash
officecli add reviewed.docx '/body/p[3]' --type comment \
  --prop text="【中风险】第 5 条 - 违约金比例失衡..." \
  --prop author="admin" \
  --prop initials="AI" \
  --prop date="2026-08-06T16:50"
```

### 方式 2：批量原子操作（适合 ≥5 条批注）

```bash
officecli batch reviewed.docx --commands '[
  {
    "command": "add",
    "path": "/body/p[3]",
    "type": "comment",
    "props": {
      "text": "【高风险】第 5 条 - ...",
      "author": "admin",
      "initials": "AI",
      "date": "2026-08-06T16:50"
    }
  },
  {
    "command": "add",
    "path": "/body/p[7]",
    "type": "comment",
    "props": {
      "text": "【中风险】第 8 条 - ...",
      "author": "admin",
      "initials": "AI",
      "date": "2026-08-06T16:50"
    }
  }
]'
```

### 方式 3：Python 脚本封装（推荐）

```bash
python "scripts/annotate_docx.py" \
  --input "原合同.docx" \
  --output "reviewed-原合同-20260806-1650.docx" \
  --comments-json "审查意见.json"
```

**审查意见 JSON 结构**：

```json
{
  "comments": [
    {
      "paragraph_index": 3,
      "level": "high",
      "title": "违约金比例失衡",
      "essence": "约定违约金 30% 远超行业惯例",
      "law": "《民法典》第 585 条",
      "loss_estimate": "按 100 万合同计算，超额风险 10 万",
      "suggestion": "建议下调至 20% 并增加调整机制条款",
      "modify_text": "任何一方违约的，应按未履行部分合同金额的 20%...",
      "search_date": "2026-08-06"
    }
  ]
}
```

## 段落定位（path 寻址）

officecli 用 `/body/p[N]` 定位段落，N 为段落序号（1-based）。

### 定位策略

1. **首选**：按条款编号搜索
   ```bash
   officecli query reviewed.docx 'p:contains("第 5 条")'
   ```
   返回匹配段落序号

2. **次选**：按关键词搜索
   ```bash
   officecli query reviewed.docx 'p:contains("违约金")'
   ```

3. **兜底**：按章节定位
   - 读取 outline：`officecli view reviewed.docx outline`
   - 推断段落序号区间

## 使用方法

主 agent 在 Step 7 阶段：
1. 整理审查意见为 JSON 结构
2. 调用 `scripts/annotate_docx.py`（内部封装 officecli）
3. 调用 `scripts/validate.py` 自检
4. 交付 `reviewed-{filename}.docx`
