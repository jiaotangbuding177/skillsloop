# 实战补充：8 个必踩的坑

> 本文件**不属于原插件**，是实际交付一条 99.8 秒中文解说视频（1080×1920 竖屏 / edge-tts 配音 /
> 66 条跟随字幕）时踩到的坑与解法。原插件 86 个文件对这些基本没有覆盖，建议一起分发。

---

## 1. 确定性伪随机（Remotion 头号陷阱，原插件 0 覆盖）

**症状**：本地预览正常，正式渲染时粒子乱跳、位置漂移，每次渲染结果都不一样。

**原因**：用了 `Math.random()`。Remotion 是**多进程并发**渲染，每帧由不同进程绘制，
`Math.random()` 在每个进程里的序列不同，导致同一帧在不同进程得到不同结果。

**解法**：统一用确定性 LCG，全局禁用 `Math.random()`。

```ts
export const makeRandom = (seed: number) => {
  let s = seed >>> 0;
  return () => {
    s = (s * 1664525 + 1013904223) >>> 0;
    return s / 0x100000000;
  };
};

// 用法：const rnd = makeRandom(42);  const x = rnd() * width;
```

**检查方法**：全局搜索 `Math.random`，一个都不该有。

## 2. 新版 Chromium 移除了旧 headless 模式

**症状**：`Failed to launch the browser process! Old Headless mode has been removed`

**原因**：Chromium 新版删掉了 `--headless=old`，Remotion 默认还在用旧模式。
另外官方 headless-shell 的下载地址（`storage.googleapis.com`）在国内大概率超时。

**解法**：改用系统 Chromium + `--headless=new`，在 `remotion.config.ts` 里：

```ts
import { Config } from "@remotion/cli/config";
Config.setBrowserExecutable("/usr/bin/chromium");
Config.setChromeMode("chrome-for-testing");   // 关键：走 --headless=new
```

> 只设 `setBrowserExecutable` 不设 `setChromeMode` 是没用的，两个都要。
> `npx remotion browser ensure` 在这套配置下会误报 "Has browser"，别信它。

## 3. 中文字体：别联网下载

**症状**：渲染出来是豆腐块 □□□，或者渲染卡在字体加载。

**解法**：优先用系统已装的中文字体，不联网。

```bash
fc-list :lang=zh        # 先确认系统有什么中文字体
```

```ts
export const FONT = '"Noto Sans CJK SC", "Noto Sans SC", "PingFang SC", sans-serif';
```

## 4. edge-tts 装不进系统 Python（PEP 668）

**症状**：`error: externally-managed-environment`

**解法**：建 venv，别用 `--break-system-packages`（会污染系统）。

```bash
python3 -m venv /workspace/tts-env
/workspace/tts-env/bin/pip install edge-tts
```

## 5. edge-tts 的 SubMaker 产出 0 字节 SRT

**症状**：`submaker.get_srt()` 写出来的文件是空的，字幕全丢。

**解法**：别用 `SubMaker`，改用 CLI 的 `--write-subtitles`（产出句子级时间戳）：

```bash
edge-tts --voice zh-CN-YunxiNeural --rate "+50%" \
         --text "旁白文本" \
         --write-media out.mp3 --write-subtitles out.srt
```

拿到句子级 SRT 后，通常还要**按字宽二次切分**成 15 字以内的短句，时间按字数比例分配。
（本项目 `gen_subs.py` 里有完整实现，含中英文混排的空格修复。）

## 6. 微软 TTS 接口间歇性限流

**症状**：随机抛 `NoAudioReceived`，同样的参数重试就好了。
表现为非单调失败——`+50%` 失败但 `+90%` 成功，看起来像速率上限，其实是限流。

**解法**：所有 TTS 调用包一层重试退避，**批量生成必须加**，否则 8 段里总有 1-2 段挂掉。

```python
for attempt in range(6):
    try:
        await edge_tts.Communicate(text, voice, rate=rate).save(path)
        break
    except Exception:
        if attempt == 5: raise
        await asyncio.sleep(1.2 * (attempt + 1))
```

## 7. `interpolate` 的 inputRange 必须严格递增

**症状**：`inputRange must be strictly monotonically increasing but got [586,606,802,802]`

**原因**：最后一段的起止帧算出来相等（常见于"最后一个元素不淡出"的封装函数）。

**解法**：封装的区间函数里加零长度分支：

```ts
const block = (from: number, to: number) => {
  const outDur = to - from;
  if (outDur <= 0) {
    return interpolate(f, [from, from + 1], [0, 1], { extrapolateLeft: "clamp", extrapolateRight: "clamp" });
  }
  // 正常三段式：淡入 → 保持 → 淡出
};
```

## 8. 响度：TTS 原始输出太轻

**症状**：在电脑上听着还行，手机外放明显偏轻。

**原因**：edge-tts 原始输出约 **-24 LUFS**，远低于平台标准。

**解法**：做两遍 EBU R128 归一化到 **-16 LUFS / -1.5 dBTP**（抖音/视频号/小红书的通用档位）。
用 `linear=true` 只加恒定增益，**不压缩动态**，人声不发闷。

```bash
# 第一遍：测量
ffmpeg -i in.mp3 -af loudnorm=I=-16:TP=-1.5:LRA=7:print_format=json -f null /dev/null
# 第二遍：把测得的 measured_* 填回去，linear=true
ffmpeg -i in.mp3 -af "loudnorm=I=-16:TP=-1.5:LRA=7:measured_I=...:linear=true,apad" \
       -t <视频时长> -c:a aac -b:a 320k out.m4a
```

完整可复用脚本见本项目 `normalize_audio.sh`。

## 附：音频驱动时间轴的架构建议

解说视频**不要**先定画面时长再塞旁白，反过来做：

```
TTS 生成 → 读 SRT 时长 → 反推 TOTAL_FRAMES 与各场景切分 → 画面按此时长编排
```

好处是：改文案后重跑脚本，画面和声音自动重新对齐，永远不会错位。

**注意配套的一致性维护**（这是最容易漏的一步，漏了不报错、只会让节奏变怪）：
场景组件里如果硬编码了 `const D = <帧数>` 或时间缩放系数，必须跟着新时间轴一起改。
