# 039 真实会话任务识别与轨迹恢复的LLM升级设计

## 用户问题及主线

用户质疑当前Demo以规则识别任务、恢复轨迹难以覆盖真实会话，提出让这几块使用LLM，要求基于038合同案例提出真正可落地复用的优化。该工作服务于企业会话→任务证据→方法族→skill候选的主线。本轮按科研设计处理，未修改Demo或调用外部模型；“全部使用LLM能力”解释为语义判断由LLM提出，原始事实、权限、状态与版本仍由宿主核验。

## 本轮依据与新增观察

- 已重读项目入口/章程/状态、038案例、当前Demo的`core.py`、`learning.py`、`runtime.py`、`store.py`和相关研究报告。
- 对038两条生成会话的8个用户回合补做无模型预检：移除038测试视图中**人工补充的replyTo**后，当前Demo只恢复1条轨迹且仅含首轮，其他7轮全部未关联任务。038表中“原句导入”实际保持用户原句，但带人工replyTo，需在后续解释时明示；保留原报告结果，新增本轮更正。
- 带人工replyTo时T1四轮关联、T2漏识别；仅诊断性给T2首句加“请”后两条任务均恢复，却生成两个单轨迹NEW。词法相似度0.211<0.72。三个断点分别是请求识别、修订关系和方法族聚合。
- 当前`evidence()`把任意`CORRECT`当FAILURE；真实案例的谈判要求、晚到业务事实与交付格式修正不能以这条规则混同为整项业务失败。

## 设计判断和产物

形成[039升级方案](../reports/039_llm_task_graph_and_family_design.md)：同用户稳定会话小批次一次LLM输出任务图、修订归因和方法族提议；宿主查ID、顺序、附件存在性、结果证据、owner/权限与预算；UNKNOWN/UNRESOLVED显式保留。建议复用Demo现有records/events/runs三表，重构`_record→tick→discover`语义边界，并保持skill-creator与组织审核。T1/T2同族仅是待验证假设，不能预设一定应合成一个泛用合同skill。

资源判断：规则识别/聚类当前0次LLM，新增独立解释调用必然增加该环节资源。离线探索模式可先验证语义收益；产品预算模式需把解释、家族选择与Patch提议并入原learn批次，控制外层派发，但内部请求与tokens是否不增加仍未知，必须测量。历史无skills数据只走NEW/延期，不将AI文字声明或“请使用技能”会话当UPDATE。

## 未知及下一步

尚未验证真实模型能否按此schema稳定恢复任务，也没有准确率、成本、技能质量或未来收益结果。建议先用038三会话及同用户近邻负例做小规模模型检查，再看81会话自然分布和同预算对照。原合同DOCX缺失限制法律实质验收；模型处理企业原文前仍需确认可用范围与脱敏。本轮无业务代码修改、无付费模型调用、无skill生成。
