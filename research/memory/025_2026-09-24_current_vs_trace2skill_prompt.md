# 025｜当前实现、Trace2Skill 与简单 Prompt 的边界

日期：2026-09-24。

## 用户问题

用户要求明确当前实现和 Trace2Skill 的差距，以及它与简单 prompt 的区别。

## 证据与核对

- 读取项目章程、状态、README、019原型边界和024真实验收。
- 读取 Trace2Skill v5 原文第2节：冻结技能生成带成功／失败标签轨迹；成功／失败分析器并行提出 patch；层次 merge 并 apply。
- 当前真实验收是构造销售案例，证明 OpenClaw、官方 skill-creator、个人v1/v2、组织审核、Bob消费、文件和权限检查可运行；不是企业效果实验。

## 已确认观察

1. 当前 demo 是企业技能生命周期原型，已经包含任务恢复、NEW/UPDATE/SUPPORT分流、技能封装、个人／组织发布、版本与权限、使用反馈回流。
2. 当前 demo 尚未实现 Trace2Skill 的完整核心：带业务正确性标签的轨迹池、独立失败因果分析、并行逐轨迹 patch 池、层次 many-to-one merge、独立消费任务评估。
3. 当前系统与 Trace2Skill 的重合部分是技能目录格式、从成功／失败经验改进、保留基准版本；这些不能单独作为原创。
4. 简单 prompt 只能提出一次文本生成要求，缺少任务边界、证据、状态、授权、版本、使用回执和演化闭环；当前系统把 prompt 作为模型子步骤，而非整个算法。
5. 当前没有证据证明无效 skills 已减少、有效能力已保留或总模型成本不增加。024的35次模型请求和498,204报告tokens仅是一次构造案例的运行观测，成本未知。

## 研究判断（未验证）

- 差异化研究空间应放在开放企业会话的可修订任务证据、技能使用后的增量路由、个人／组织授权边界和资源约束的联合处理，而不是声称发明“轨迹变技能”。
- 若后续实现 Trace2Skill式 patch 合并，应称“受其启发／包含其核心机制的企业适配”，不称论文复现，除非严格复现输入、阶段和评估。

## 未解决问题

- 如何从真实企业任务获得可复核的业务结果标签，并区分技术故障、业务失败和未知结果。
- 多条企业轨迹何时足以合并为一个 patch，如何在不增加总资源的目标下批量合并。
- 个人采纳和组织审核后的跨成员收益、维护负担与版本退化率。
