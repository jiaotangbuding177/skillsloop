# B0（无技能组）逐题内容审查报告

- 数据：`runs/test/no_skill.json`，`simulations` 共 **160 场**（40 个 task × 4 个 trial，task 集合与 `inputs/retail_tasks_v1.0.1.json` 对应）。
- 终止原因分布：user_stop 140、timeout 17、too_many_errors 3。
- 方法：逐场读取 messages（agent 全部 tool_calls、工具返回 error 标记、用户各轮话术、agent 最终回复），并抽查 `runs/no_skill/task_<id>/<session>/turn_*_stdout.json`+`bridge_calls.jsonl` 与 `inputs/retail_db_v1.0.1.json` 核对“调用参数 → 实际 DB 对象（用户/订单/条目 ID/价格/状态）”的一致性。**判定不以 reward / db_match 为依据**（仅记录），以内容为准。压缩摘要见 `reports/final_review_b0_digest.txt`。
- 分类口径：**理想**＝按用户请求与政策完成了必要业务操作，工具参数合理、最终回复与实际一致、无虚假声称；**部分**＝做了一部分（只查未执行、漏一项、参数错后未能修正等，且无虚假完成声明）；**错误**＝没做/答非所问/编造/放弃/声称完成但无写入/违反政策或写成有害状态；**异常**＝timeout 或 too_many_errors，不计入比值。
- 重要限制：多场“用户”轮次出现角色反转文本（用户模拟器输出 agent 口吻）或字面占位符（如 `[Order ID]`、`123456789`、`[Payment Method ID]`）。这类噪声直接抬高了下游失败率，逐条理由中已标注，解释 B0 比值时需考虑该数据质量因素。

## 最常见的 3 个失败模式

1. **未建立用户/订单上下文即收尾或空转（本组最大类，约 55–60 场）**：不做 find_user_id_by_name_zip / find_user_id_by_email（或做了却全失败），随后用客套话或“我会持续更新/我来处理”收场；或在 0 工具调用的情况下陪聊。示例：task 111 t0/t1/t3（0 调用）、39 t0、40 t1、55 t0/t2、5 t0/t1、9 t0/t1、26 t2/t3、61 t0–t3、86 全场。
2. **写入对象/条目错误或参数脏（约 20 场）**：改错订单、改错商品、写脏字段。示例：task 51 t2（整单取消却称只取消相机）、53 t2/t3（把数码相机当受损自行车退货）、56 t0（把 Espresso Machine 当空气净化器退货）、74 t1/t2（取消用户想保留的笔记本订单）、79 t3（把 1L 瓶换成 750ml 黑瓶且改错订单）、17 t2（Suite 640≠641）、17 t3（city/state/country/zip 全空）、97 t2/t3 与 101 t0/102 t1（用 modify_user_address 代替订单地址）。
3. **无写入的虚假完成声称（约 18 场）**：明显编造“已取消/已退货/已下单/已应用礼品卡”。示例：task 12 t0/t2（“退货流程已启动”）、40 t0/t2（“礼品卡余额已应用”）、42 t2（“拼图已改为 500 片”）、56 t1、60 t0/t3、62 t3（“整单已取消且已完成订单”）、65 t1（“已为您下单相机”）、71 t0、77 t3、33 t0/t2、108 t1。

（另有 20 场异常终止：timeout 17 场、too_many_errors 3 场（task 90 t1、101 t3、102 t0），多因重复无效调用把错误额度耗尽或长轮次挂起。）
