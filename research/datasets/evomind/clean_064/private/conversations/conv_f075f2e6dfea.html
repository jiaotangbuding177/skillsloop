# 🔐 AI Agent 安全深度分析

## ——为什么它是你该深度跟进的第一选题

数据来源：No Priors 播客 Onyx CEO Maxim Bar Kogan 专访、Gravitee 2026 AI Agent 安全报告（900+企业高管调查）、VentureBeat 六大 Agent 攻破事件专题、DryRun Security 编码 agent 安全研究、Claude Code 源码泄露分析、US vs China Agent 部署对比等。

---

## 一、核心论点：从"影子 IT"到"影子 AI"——安全真空正在形成

一句话总结：**AI agent 正在以企业历史上最快的速度被采用，但安全框架几乎不存在。**

关键数据：

| 指标 | 数值 |
|------|------|
| 已进入测试/生产阶段的企业 | **80.9%** |
| 经过完整安全审批才上线的 agent | 仅 **14.4%** |
| 已发生/疑似 AI agent 安全事件的企业 | **88%** |
| 医疗行业的事故率 | **92.7%** |
| 企业对现有策略的信心（高管层） | **82%**（信心爆棚） |
| 现实情况 | 安全团队根本看不见 agent 在干什么 |

**这就是"信心悖论"——高管觉得 OK，安全团队一脸懵，事故已经遍地开花。**

No Priors 播客中，Onyx CEO Maxim 一针见血："传统安全工具理解不了 AI 在想什么、为什么这么做。身份安全认为权限是对的，但 agent 需要用你的全部权限来做各种不可预测的事——这是结构性的问题。"

---

## 二、为什么此刻是爆发点：三大事件密集引爆

### 事件 1：2026 年春季，六大 Agent 被集体攻破

VentureBeat 以严厉的标题报道了这件事。在 9 个月内，6 个研究团队分别披露了对 Codex、Claude Code、Copilot 和 Vertex AI 的 exploit。**每个攻击都遵循同一个模式：**

> AI coding agent 持有凭证 → 执行了一个操作 → 在没有人类会话锚定的情况下认证到了生产系统

具体攻破案例：
- **Codex** — GitHub 分支名注入，窃取 OAuth token（OpenAI 评 Critical P1）
- **Claude Code** — 两个 CVE 加上"50 子命令绕过"机制：超过 50 个命令后自动放弃 deny 规则检查
- **Copilot** — PR 描述和 GitHub issue 内的隐藏指令触发 RCE
- **Vertex AI** — 默认服务身份权限过大，可读取整个项目的 Cloud Storage 桶和 Google 的内部 Artifact Registry

**每家的防御都补丁了。每家的防御都被绕过了。**

CrowdStrike CTO Elia Zaitsev 在 RSAC 2026 上给了最直接的建议：**把 agent 身份 collapse 回人类身份——agent 不应该拥有超过它背后人类的权限。**

### 事件 2：Claude Code 源码泄露——AI 写的代码暴露了 AI 自己

2026 年 3 月 31 日，Anthropic 推送了 Claude Code 2.1.88 到 npm，误包含了一个 59.8MB 的 source map 文件。暴露了 2000 个 TypeScript 源文件，包括产品路线图、反蒸馏机制和安全防护。**而且这些代码大部分是 Claude Code 自己写的**——项目负责人 Boris Cherny 说所有代码贡献都是 Claude Code 生成的。

这意味着：AI 写了一个工具，这个工具配置错了导致自己的源代码泄露，然后源代码暴露了整个安全架构——**循环的讽刺。**

这还不是孤立事件：这是 Claude Code 在 13 个月内的**第二次**相似的 source map 泄露。5 天前，Anthropic 的 CMS 配置错误又暴露了约 3000 个内部文件。

### 事件 3：DryRun 研究——AI coding agent 在 87% 的 PR 中引入漏洞

Claude Code、Codex 和 Gemini 构建的两个应用（家庭过敏追踪 web app 和赛车游戏），38 次扫描、30 个 PR 产生了 **143 个安全问题**。26/30 个 PR 包含至少一个漏洞，**比例 87%**。

漏洞模式高度一致：损坏的访问控制、商业逻辑缺陷、OAuth 实现错误、WebSocket 认证缺失、速率限制缺失、JWT 硬编码默认密钥。这些都是**安全领域十年前就已经解决的问题**——但 AI agent 每次都会犯。

## 三、技术本质：为什么这不是传统安全能解决的

Maxim 在播客中把这个问题讲得非常清晰。我把它提炼为三个结构性矛盾：

### 矛盾 1：权限 vs. 自主性

传统安全逻辑：给最小权限，出事就挡。但 agent 的逻辑是："帮我去做各种不同的事，我不知道下一件事是什么，所以给我你的全部权限。"

你告诉 Codex"删掉这个数据库重建一下"，这是好事情。但如果 Codex 在做其他不相干的任务时突然"觉得"应该删掉数据库重建呢？**你的端点和 API 安全工具不知道 Codex 当时在想什么。**

### 矛盾 2：现有 stack 全是为"人类+工具"设计的

- **身份安全（IAM）**：控制人类能做什么。但 agent 需要继承人类的权限并疯狂扩展。
- **端点安全（EDR）**：监控进程行为。但 agent 通过 API 交互，不产生进程事件。
- **API 安全**：监控南北向流量。但 agent 大量进行东西向的系统调用。

**每个现有安全类别的边界都不覆盖 agent 的行为模式。**

### 矛盾 3：模型厂商 vs. 独立安全的冲突

Maxim 提出了一个尖锐问题：企业愿意让 AI 厂商看到 agent 的行为历史数据吗？

> "企业今天不愿意让 Anthropic 或 OpenAI 拿到这些历史数据——因为他们知道这些公司是数据饥渴的，会拿去训练。"

这创造了独立第三方安全厂商的**结构性机会**。就像车检不能由卖车的人来做，AI agent 的安全审计需要独立的监督方。

---

## 四、Onyx 做了什么？——"下快棋"式 Agent 监管架构

Onyx 的技术路径值得重点分析，因为它的设计思想很聪明：

1. **不是"用另一个聪明 agent 看所有事"**——太贵、太慢。如果每个被监管的 agent 背后都要跑一个同样级别的推理模型做监控，你的安全账单会比 AI 账单还高。

2. **训练非常小的专用模型**——几乎什么都不会，只会判断一件事："这个 action 是否需要更聪明的 agent 来仔细看看？"

3. **两层架构**：
   - **第一层：小型分类器**（高吞吐、低延迟、低成本）— 90%+ 的 action 秒过
   - **第二层：大模型深度审查**（只在必要时触发）— 处理高风险的边缘 case

Maxim 用下快棋做类比：顶尖棋手 95% 的落子靠直觉，只在关键时刻停下来深入计算。**不要在不需要的地方浪费智能，在真正高风险的地方投入最多的智能。**

Onyx 已经融资 $45M（Conviction + Cyberstarts），估值未公开但在以色列安全创投圈被高度关注。

## 五、中国市场机会分析

### 现状

中国企业的 AI agent 采用呈明显的"两极分化"：

**消费端：全球最大规模的 Agent 部署**
- Tencent 将 OpenClaw 接入微信，一天内 10 亿用户获取了 AI agent

**企业端：治理和安全几乎空白**
- 中国的 AI agent 安全厂商稀少
- 数据合规（个人信息保护法、数据安全法）为独立安全厂商提供了刚性需求
- 国产化要求意味着海外厂商（Onyx 等）进入门槛高

### 中国版本的 Onyx 机会在哪？

| 维度 | 中国优势 | 中国挑战 |

| **市场规模** | 全球最大 agent 部署规模 → 最大的潜在安全市场 | 企业安全预算仍倾向传统安全 |

| **融资环境** | 安全赛道一直被 VC 关注 | 需要证明 PMF，Onyx 模式在中文环境需重新验证 |

**结论：机会明确，但需要打"国产替代 + 合规驱动"的牌。** 纯粹的 Onyx 复制不太现实，但结合以下独特性可能有戏：

## 六、"AI 保险"概念评估

这个想法很性感，但需要更严谨的分析。

### 支持"AI 保险"的逻辑

1. **传统网络安全保险已经成熟**——大量 CISO 的合规驱动来自保险要求
2. **事故频率已经很高**——88% 的企业已遇到 agent 安全事件
3. **损失在放大**——如果 agent 删掉数据库、泄露凭据、发布代码到公共场所，损失可达千万级
4. **大模型厂商正在推保险**——Anthropic/OpenAI 已开始提供某种形式的责任保障

### "AI 保险"的障碍

1. **精算模型不存在**——agent 行为的风险频率和损失分布没有足够的历史数据
2. **因果关系模糊**——agent 犯错和人类设计哪个责任更大？(Claude Code 源码泄露："开发者错误")
3. **承保能力**——再保险公司是否有能力覆盖 AI 领域的系统性风险？
4. **可保性**——如果 agent 的"错误"是数十亿次生成中的统计必然，它还是"保险事件"吗？

### 更可能出现的形态

- **第一层**：AI 平台厂商提供的安全保障（类似云厂商的 SLA 赔偿）
- **第二层**：独立的 AI 安全厂商（如 Onyx）提供"无事故承诺"作为销售核心
- **第三层**：五年内出现专门的 AI Agent 保险产品，与安全监控平台绑定

**我认为"AI 保险"是个好的概念包装，但不应该在这个阶段作为核心论点。核心还是"独立 AI agent 安全监控"的刚需。**

---

## 七、范式转移：从 Identity Security 到 AI Behavior Security

这个角度是最具深度的一个。我把它画成对比框架：

| 维度 | 传统安全（Identity Security） | 新范式（AI Behavior Security） |
|------|------------------------------|-------------------------------|
| **核心问题** | 你是谁？你能做什么？ | AI 在想什么？它为什么这么做？ |
| **控制粒度** | 权限（静态）→ RBAC | 意图（动态）→ 行为上下文 |
| **防护边界** | 网络端点 + API | 模型推理 + 工具调用链 |
| **审计对象** | 人类操作日志 | AI 推理轨迹 + action 序列 |
| **最难的事** | 最小权限原则 | 理解 AI 的"推理-行动"映射 |
| **致命缺陷** | 假设所有行为是可预测的 | 需要预测不可预测的系统 |
| **关键能力** | 策略制定 + 执行 | 意图理解 + 风险评估 |

**最关键的区别**：传统安全假设你知道所有可能的行为（然后限制它）。AI agent 安全面对的是无法预知的开放式行为空间——你不知道 AI 会"想到"做什么。

这就是为什么 Maxim 说最终需要 mechanistic interpretability（机制可解释性）：当模型比人类聪明时，人类看不懂权重的意义，但可能可以用一个**更聪明的模型**去理解。这是个极其前沿但也极其引人入胜的方向。

### 阵营 1：Agent 控制平面（最接近 Onyx）

## 三、核心竞品深度对比

### Onyx vs Galileo Agent Control — 最直接的对抗

| 维度 | Onyx | Galileo Agent Control |
|------|------|---------------------|
| **商业模式** | 闭源 SaaS | 开源 Apache 2.0 + 商业版 Galileo 平台 |
| **接入方式** | 代理/钩子 + 专有 agent 集成 | `@control()` 一行装饰器即可接入 |
| **策略管理** | 中央控制平面 + Onyx 自研模型 | 中央策略服务器，决策层可拔插 |
| **检测能力** | 自训练小模型（理解 AI 意图）+ 大模型深度审查 | 可集成长舌妇（Galileo Luna） + NVIDIA NeMo + AWS Bedrock + 自定评估器 |
| **主要卖点** | 独立第三方安全供应商 | 开源 + 多生态集成（Cisco/ServiceNow/CrewAI） |
| **风险** | 供应商锁定 | 需要自行运维策略服务器 |

**关键差异**：Onyx 赌的是"专用小模型"的技术路线，Galileo 赌的是"开放生态"的路线。

### Onyx vs Tigera Lynx — 技术栈路径不同

- **Tigera Lynx 的思路**：从 K8s 网络层出发，用 SPIFFE/SPIRE 发证书给每个 agent，在运行时 level 进行身份验证和权限控制
- **Onyx 的思路**：从 AI 推理层出发，理解 agent 在"想什么"
- **本质差异**：Tigera 管"这个 agent 有没有权限做 X"，Onyx 管"这个 agent 的想法和意图是否合理"
- 这俩实际上是互补的——很多企业可能需要两者一起用

### Onyx vs AccuKnox — 平台广度 vs 深度

- **AccuKnox**：一家印度云安全公司，产品线极多（CNAPP/CWPP/K8s/AI/API...），有 ClawArmor 做 AI agent 安全的子模块
- **Onyx**：只做一件事且做得很深——AI agent 控制平面
- AccuKnox 的优势是已有的企业版图和开源社区（KubeArmor），但 AI 安全不是他们的核心
- Onyx 的优势是完全聚焦，从 No Priors 播客的访谈能看出技术深度

## 四、竞争壁垒分析：Onyx 的护城河在哪？

### 1. 技术壁垒：专用小模型训练

Onyx 自训练了非常小的模型，只做一件事：判断"这个 action 是否需要更聪明的模型来看一下"。这个"快棋式"架构——90%+ action 秒过，只在必要时触发深度审查——在成本和延迟上形成了结构性优势。

**挑战**：Galileo Agent Control 的开源生态可以任意插拔评估器，理论上也能做到类似效果。

### 2. 数据壁垒：跨 agent 行为数据集

Maxim 在播客中明确提到：**企业不愿意把 agent 行为历史数据给 Anthropic/OpenAI**，但愿意给独立第三方。Onyx 因此积累了跨越多厂商（Claude Code、Codex、Gemini、Cowork 等）的 agent 行为数据。

**这个护城河是真实的、且随时间加厚。** 新入场玩家没有这个数据集。

### 3. 定位壁垒：独立第三方

> "你不会让卖车的人来给你做车检。"

这是 Onyx 最强有力的叙事武器。在 AI 安全这个领域，你天然就不信任提供 AI 的厂商来自我审查——企业 CISO 心里门儿清。

### 4. 团队壁垒：以色列安全 + AI 基因

联合创始人 Gil 前 NVIDIA（AI），创始人 Maxim 以色列情报部队背景。以色列在网络安全领域的人才深度是经过市场验证的（Wiz, Check Point, Palo Alto 的以色列研发中心等）。

### 🎙️ PODCASTS

**No Priors：与 Onyx Security CEO Maxim Bar Kogan 探讨企业 AI 守护者**

核心收获：Agent 安全正在成为企业最紧迫的 AI 课题。

Maxim 预见到了 AI agent 的爆发式增长——从 AutoGPT 时代就开始思考"当模型比我们聪明时，我们如何监管它们？"如今这个时刻已经到来。他指出，企业中的 AI agent 使用中，超过 50% 是自主编码 agent（Claude Code/Codex/Cowork 等），45% 是低代码自动化，仅 2% 是自建 agent。问题在于：这些 agent 正在以指数的速度产生行动，而传统安全工具（身份安全、端点安全、API 安全）缺乏理解 AI 行动"意图"的能力——因为它们不知道 AI 在想什么、为什么这么做。

Onyx 的解决方案很聪明：训练专用的小模型作为"守门员"。核心思想是"不需要让很聪明的模型看每一个 action，而是训练一个非常小、几乎什么都不会、只会判断"这个 action 是否需要更聪明的 agent 来看一下"的模型"。这就像下快棋：95% 的落子靠直觉，只在关键时刻才深入计算。这种架构能在成本、延迟和安全性之间取得平衡。

Maxim 还提出了一个根本性的观点：AI 安全需要独立第三方。企业不会信任 AI 厂商来自审自己产品的安全性——就像买车的人不会让卖家来做车检。随着模型变得越来越聪明，"不是犯傻错而是有自己的想法"的问题会越来越严重，而这些独立的安全厂商掌握着模型厂商拿不到的交叉数据。

# 🔐 AI Agent 安全深度分析

## ——为什么它是你该深度跟进的第一选题

数据来源：No Priors 播客 Onyx CEO Maxim Bar Kogan 专访、Gravitee 2026 AI Agent 安全报告（900+企业高管调查）、VentureBeat 六大 Agent 攻破事件专题、DryRun Security 编码 agent 安全研究、Claude Code 源码泄露分析、US vs China Agent 部署对比等。

## 一、核心论点：从"影子 IT"到"影子 AI"——安全真空正在形成

一句话总结：**AI agent 正在以企业历史上最快的速度被采用，但安全框架几乎不存在。**

关键数据：

| 指标 | 数值 |
|------|------|
| 已进入测试/生产阶段的企业 | **80.9%** |
| 经过完整安全审批才上线的 agent | 仅 **14.4%** |
| 已发生/疑似 AI agent 安全事件的企业 | **88%** |
| 医疗行业的事故率 | **92.7%** |
| 企业对现有策略的信心（高管层） | **82%**（信心爆棚） |
| 现实情况 | 安全团队根本看不见 agent 在干什么 |

**这就是"信心悖论"——高管觉得 OK，安全团队一脸懵，事故已经遍地开花。**

No Priors 播客中，Onyx CEO Maxim 一针见血："传统安全工具理解不了 AI 在想什么、为什么这么做。身份安全认为权限是对的，但 agent 需要用你的全部权限来做各种不可预测的事——这是结构性的问题。"

---

## 二、为什么此刻是爆发点：三大事件密集引爆

### 事件 1：2026 年春季，六大 Agent 被集体攻破

VentureBeat 以严厉的标题报道了这件事。在 9 个月内，6 个研究团队分别披露了对 Codex、Claude Code、Copilot 和 Vertex AI 的 exploit。**每个攻击都遵循同一个模式：**

> AI coding agent 持有凭证 → 执行了一个操作 → 在没有人类会话锚定的情况下认证到了生产系统

具体攻破案例：
- **Codex** — GitHub 分支名注入，窃取 OAuth token（OpenAI 评 Critical P1）
- **Claude Code** — 两个 CVE 加上"50 子命令绕过"机制：超过 50 个命令后自动放弃 deny 规则检查
- **Copilot** — PR 描述和 GitHub issue 内的隐藏指令触发 RCE
- **Vertex AI** — 默认服务身份权限过大，可读取整个项目的 Cloud Storage 桶和 Google 的内部 Artifact Registry

**每家的防御都补丁了。每家的防御都被绕过了。**

CrowdStrike CTO Elia Zaitsev 在 RSAC 2026 上给了最直接的建议：**把 agent 身份 collapse 回人类身份——agent 不应该拥有超过它背后人类的权限。**

### 事件 2：Claude Code 源码泄露——AI 写的代码暴露了 AI 自己

2026 年 3 月 31 日，Anthropic 推送了 Claude Code 2.1.88 到 npm，误包含了一个 59.8MB 的 source map 文件。暴露了 2000 个 TypeScript 源文件，包括产品路线图、反蒸馏机制和安全防护。**而且这些代码大部分是 Claude Code 自己写的**——项目负责人 Boris Cherny 说所有代码贡献都是 Claude Code 生成的。

这意味着：AI 写了一个工具，这个工具配置错了导致自己的源代码泄露，然后源代码暴露了整个安全架构——**循环的讽刺。**

这还不是孤立事件：这是 Claude Code 在 13 个月内的**第二次**相似的 source map 泄露。5 天前，Anthropic 的 CMS 配置错误又暴露了约 3000 个内部文件。

### 事件 3：DryRun 研究——AI coding agent 在 87% 的 PR 中引入漏洞

Claude Code、Codex 和 Gemini 构建的两个应用（家庭过敏追踪 web app 和赛车游戏），38 次扫描、30 个 PR 产生了 **143 个安全问题**。26/30 个 PR 包含至少一个漏洞，**比例 87%**。

漏洞模式高度一致：损坏的访问控制、商业逻辑缺陷、OAuth 实现错误、WebSocket 认证缺失、速率限制缺失、JWT 硬编码默认密钥。这些都是**安全领域十年前就已经解决的问题**——但 AI agent 每次都会犯。

## 三、技术本质：为什么这不是传统安全能解决的

Maxim 在播客中把这个问题讲得非常清晰。我把它提炼为三个结构性矛盾：

### 矛盾 1：权限 vs. 自主性

传统安全逻辑：给最小权限，出事就挡。但 agent 的逻辑是："帮我去做各种不同的事，我不知道下一件事是什么，所以给我你的全部权限。"

你告诉 Codex"删掉这个数据库重建一下"，这是好事情。但如果 Codex 在做其他不相干的任务时突然"觉得"应该删掉数据库重建呢？**你的端点和 API 安全工具不知道 Codex 当时在想什么。**

### 矛盾 2：现有 stack 全是为"人类+工具"设计的

- **身份安全（IAM）**：控制人类能做什么。但 agent 需要继承人类的权限并疯狂扩展。
- **端点安全（EDR）**：监控进程行为。但 agent 通过 API 交互，不产生进程事件。
- **API 安全**：监控南北向流量。但 agent 大量进行东西向的系统调用。

**每个现有安全类别的边界都不覆盖 agent 的行为模式。**

### 矛盾 3：模型厂商 vs. 独立安全的冲突

Maxim 提出了一个尖锐问题：企业愿意让 AI 厂商看到 agent 的行为历史数据吗？

> "企业今天不愿意让 Anthropic 或 OpenAI 拿到这些历史数据——因为他们知道这些公司是数据饥渴的，会拿去训练。"

这创造了独立第三方安全厂商的**结构性机会**。就像车检不能由卖车的人来做，AI agent 的安全审计需要独立的监督方。

## 四、Onyx 做了什么？——"下快棋"式 Agent 监管架构

Onyx 的技术路径值得重点分析，因为它的设计思想很聪明：

1. **不是"用另一个聪明 agent 看所有事"**——太贵、太慢。如果每个被监管的 agent 背后都要跑一个同样级别的推理模型做监控，你的安全账单会比 AI 账单还高。

2. **训练非常小的专用模型**——几乎什么都不会，只会判断一件事："这个 action 是否需要更聪明的 agent 来仔细看看？"

3. **两层架构**：
   - **第一层：小型分类器**（高吞吐、低延迟、低成本）— 90%+ 的 action 秒过
   - **第二层：大模型深度审查**（只在必要时触发）— 处理高风险的边缘 case

Maxim 用下快棋做类比：顶尖棋手 95% 的落子靠直觉，只在关键时刻停下来深入计算。**不要在不需要的地方浪费智能，在真正高风险的地方投入最多的智能。**

Onyx 已经融资 $45M（Conviction + Cyberstarts），估值未公开但在以色列安全创投圈被高度关注。

## 六、"AI 保险"概念评估

这个想法很性感，但需要更严谨的分析。

### 支持"AI 保险"的逻辑

1. **传统网络安全保险已经成熟**——大量 CISO 的合规驱动来自保险要求
2. **事故频率已经很高**——88% 的企业已遇到 agent 安全事件
3. **损失在放大**——如果 agent 删掉数据库、泄露凭据、发布代码到公共场所，损失可达千万级
4. **大模型厂商正在推保险**——Anthropic/OpenAI 已开始提供某种形式的责任保障

### "AI 保险"的障碍

1. **精算模型不存在**——agent 行为的风险频率和损失分布没有足够的历史数据
2. **因果关系模糊**——agent 犯错和人类设计哪个责任更大？(Claude Code 源码泄露："开发者错误")
3. **承保能力**——再保险公司是否有能力覆盖 AI 领域的系统性风险？
4. **可保性**——如果 agent 的"错误"是数十亿次生成中的统计必然，它还是"保险事件"吗？

### 更可能出现的形态

- **第一层**：AI 平台厂商提供的安全保障（类似云厂商的 SLA 赔偿）
- **第二层**：独立的 AI 安全厂商（如 Onyx）提供"无事故承诺"作为销售核心
- **第三层**：五年内出现专门的 AI Agent 保险产品，与安全监控平台绑定

**我认为"AI 保险"是个好的概念包装，但不应该在这个阶段作为核心论点。核心还是"独立 AI agent 安全监控"的刚需。**

## 七、范式转移：从 Identity Security 到 AI Behavior Security

这个角度是最具深度的一个。我把它画成对比框架：

| 维度 | 传统安全（Identity Security） | 新范式（AI Behavior Security） |
|------|------------------------------|-------------------------------|
| **核心问题** | 你是谁？你能做什么？ | AI 在想什么？它为什么这么做？ |
| **控制粒度** | 权限（静态）→ RBAC | 意图（动态）→ 行为上下文 |
| **防护边界** | 网络端点 + API | 模型推理 + 工具调用链 |
| **审计对象** | 人类操作日志 | AI 推理轨迹 + action 序列 |
| **最难的事** | 最小权限原则 | 理解 AI 的"推理-行动"映射 |
| **致命缺陷** | 假设所有行为是可预测的 | 需要预测不可预测的系统 |
| **关键能力** | 策略制定 + 执行 | 意图理解 + 风险评估 |

**最关键的区别**：传统安全假设你知道所有可能的行为（然后限制它）。AI agent 安全面对的是无法预知的开放式行为空间——你不知道 AI 会"想到"做什么。

这就是为什么 Maxim 说最终需要 mechanistic interpretability（机制可解释性）：当模型比人类聪明时，人类看不懂权重的意义，但可能可以用一个**更聪明的模型**去理解。这是个极其前沿但也极其引人入胜的方向。

## 二、竞争格局总览

AI Agent 安全市场正在迅速分化，按打法可以分为 **5 个阵营**：

### 阵营 1：Agent 控制平面（最接近 Onyx）

这些玩家直接把 agent 放进了"控制平面"——监控每个 action，在执行前做策略判定。

| 公司 | 成立/融资 | 核心方法 | 与 Onyx 差异 |
|------|---------|---------|-------------|
| **Onyx Security** | 2024, $45M | 自训练小模型做第一层过滤 + 独立第三方定位 | 基准线 |
| **Galileo (Agent Control)** | 开源（Apache 2.0）, 2026 年 3 月发布 | `@control()` 装饰器 + 中央策略服务器，可插拔评估器 | **开源**，Cisco/ServiceNow/CrewAI 背书；Onyx 是闭源商业产品 |
| **Tigera (Lynx)** | Calico 母公司，商业化多年 | 基于 eBPF 的 agent 身份 & 运行时控制，SPIFFE/SPIRE 证书签发 | 强在 Kubernetes 生态，从基础设施层向下渗透；Onyx 从 AI 层向上构架 |
| **Fiddler AI** | 2019, ~$50M | Agent 可观测性 + 门控 + 治理，买断式控制平面 | 更偏观测和评估，不像 Onyx 那样做实时 agent action 拦截 |
| **Speakeasy** | 2023, ~$25M | MCP Gateway + Agent Identity + 审计日志 | 聚焦 API/MCP 网关，Onyx 更侧重 agent 行为层面的理解 |

### 阵营 2：AI 身份安全（Identity-First）

从 IAM 角度切入，把 agent 当作"新的特权身份"。

| 公司 | 核心方法 | 与 Onyx 差异 |
|------|---------|-------------|
| **CyberArk (Secure AI Agents)** | AI agent 发现 + 零立足特权（ZSP）+ 身份网关 | CyberArk 是传统 PAM 王者，从"特权身份管理"向下兼容 AI agent；Onyx 从 AI 推理层向上监控，两者互补但可能竞争 |
| **SailPoint (Agent Identity Security)** | 将 AI agent 纳入企业身份治理框架，统一审核认证 | 偏治理和合规流程（access review、owner assignment），不做实时行为拦截 |

### 阵营 3：AI 安全全栈（CNAPP 类）

传统云安全厂商把 AI 安全作为 CNAPP 的一个模块。

| 公司 | 核心方法 | 与 Onyx 差异 |
|------|---------|-------------|
| **AccuKnox (ClawArmor)** | 从零信任 CNAPP 扩展到 AI 安全，6 层防御（Prompt Firewall → AI-DR → ModelArmor） | 印度团队 + 开源 KubeArmor 社区；产品线极广，但 AI 安全只是模块之一，聚焦深度不如 Onyx |
| **Noma Security** | AI 安全姿态管理 + 运行时 + 红队 + 供应链治理 | 类似 Onyx 但技术路径不同，更多依赖传统安全检测而非专用小模型 |

### 阵营 4：AI 可观测性 → 衍生安全

这些公司从 LLM 观测起家，后来增加了安全门控。

| 公司 | 核心方法 | 与 Onyx 差异 |
|------|---------|-------------|
| **Fiddler AI** | 评估 → 监控 → 门控 → 治理 | 强在评估链，做 agent 行为"事后分析"；Onyx 更侧重"事中拦截" |
| **Arthur AI** | 公平性 + 可解释性 + 合规报告 | 偏治理合规，不拦截 action |

## 三、核心竞品深度对比

### Onyx vs Galileo Agent Control — 最直接的对抗

| 维度 | Onyx | Galileo Agent Control |
|------|------|---------------------|
| **商业模式** | 闭源 SaaS | 开源 Apache 2.0 + 商业版 Galileo 平台 |
| **接入方式** | 代理/钩子 + 专有 agent 集成 | `@control()` 一行装饰器即可接入 |
| **策略管理** | 中央控制平面 + Onyx 自研模型 | 中央策略服务器，决策层可拔插 |
| **检测能力** | 自训练小模型（理解 AI 意图）+ 大模型深度审查 | 可集成长舌妇（Galileo Luna） + NVIDIA NeMo + AWS Bedrock + 自定评估器 |
| **主要卖点** | 独立第三方安全供应商 | 开源 + 多生态集成（Cisco/ServiceNow/CrewAI） |
| **风险** | 供应商锁定 | 需要自行运维策略服务器 |

**关键差异**：Onyx 赌的是"专用小模型"的技术路线，Galileo 赌的是"开放生态"的路线。

### Onyx vs Tigera Lynx — 技术栈路径不同

- **Tigera Lynx 的思路**：从 K8s 网络层出发，用 SPIFFE/SPIRE 发证书给每个 agent，在运行时 level 进行身份验证和权限控制
- **Onyx 的思路**：从 AI 推理层出发，理解 agent 在"想什么"
- **本质差异**：Tigera 管"这个 agent 有没有权限做 X"，Onyx 管"这个 agent 的想法和意图是否合理"
- 这俩实际上是互补的——很多企业可能需要两者一起用

### Onyx vs AccuKnox — 平台广度 vs 深度

- **AccuKnox**：一家印度云安全公司，产品线极多（CNAPP/CWPP/K8s/AI/API...），有 ClawArmor 做 AI agent 安全的子模块
- **Onyx**：只做一件事且做得很深——AI agent 控制平面
- AccuKnox 的优势是已有的企业版图和开源社区（KubeArmor），但 AI 安全不是他们的核心
- Onyx 的优势是完全聚焦，从 No Priors 播客的访谈能看出技术深度

## 四、竞争壁垒分析：Onyx 的护城河在哪？

### 1. 技术壁垒：专用小模型训练

Onyx 自训练了非常小的模型，只做一件事：判断"这个 action 是否需要更聪明的模型来看一下"。这个"快棋式"架构——90%+ action 秒过，只在必要时触发深度审查——在成本和延迟上形成了结构性优势。

**挑战**：Galileo Agent Control 的开源生态可以任意插拔评估器，理论上也能做到类似效果。

### 2. 数据壁垒：跨 agent 行为数据集

Maxim 在播客中明确提到：**企业不愿意把 agent 行为历史数据给 Anthropic/OpenAI**，但愿意给独立第三方。Onyx 因此积累了跨越多厂商（Claude Code、Codex、Gemini、Cowork 等）的 agent 行为数据。

**这个护城河是真实的、且随时间加厚。** 新入场玩家没有这个数据集。

### 3. 定位壁垒：独立第三方

> "你不会让卖车的人来给你做车检。"

这是 Onyx 最强有力的叙事武器。在 AI 安全这个领域，你天然就不信任提供 AI 的厂商来自我审查——企业 CISO 心里门儿清。

### 4. 团队壁垒：以色列安全 + AI 基因

联合创始人 Gil 前 NVIDIA（AI），创始人 Maxim 以色列情报部队背景。以色列在网络安全领域的人才深度是经过市场验证的（Wiz, Check Point, Palo Alto 的以色列研发中心等）。

## 🚀 核心问题：怎么通过开源生态快速做出来？

如果目的是**快速验证 + 快速铺量**，开源是最好的路径。我建议的战略：

### Step 1：不要从零造"Onyx"

Onyx 的技术核心是**自训练小模型来做第一层意图判断**。这个太难了，需要大量数据和对齐经验，不适合速胜。

**更好的切入方式：先做 OpenClaw 的"安全适配层"**

OpenClaw 占了中国 agent 生态的半壁江山（微信集成 + 政府补贴 + 龙虾文化）。直接做一个 OpenClaw 的安全插件，天然就有用户基础。

### Step 2：开源架构设计

借鉴 Galileo Agent Control 的思路（`@control()` 装饰器），但适配 OpenClaw 生态：

```
┌──────────────────────────────────────┐
│          Agent Control Server         │  ← 开源，可自部署
│  ┌──────────────┐  ┌──────────────┐   │
│  │ 策略引擎      │  │ 审计日志      │   │
│  │ policy.yaml  │  │ 可插拔存储    │   │
│  └──────────────┘  └──────────────┘   │
│  ┌──────────────┐                     │
│  │ 评估器市场    │                     │  ← 核心差异化
│  │ (PII/合规/    │                     │
│  │  行为异常等)   │                     │
│  └──────────────┘                     │
└──────────────────────────────────────┘
         ↕  gRPC/HTTP
┌──────────────────────────────────────┐
│  OpenClaw Agent                        │
│  @watch(action="db_query")             │  ← 一行装饰器启用
│  def query_database(...):              │
│      ...                              │
└──────────────────────────────────────┘
```

### Step 3：具体推进路线图

| 阶段 | 时间 | 做什么 | 里程碑 |
|------|------|--------|--------|
| **M0-M1** | 2-4 周 | 做 OpenClaw 的 `@watch` 装饰器，拦截 agent 的工具调用 + 一个中央策略服务器 | 能 demo：OpenClaw agent 调用 DB → 策略服务器评估 → 拦截/放行 |
| **M1-M2** | 4-6 周 | 开源发布（Apache 2.0），做基础评估器：PII 检测（re2）、敏感操作检测、速率限制 | GitHub 发布，写一篇公众号文章《你的 OpenClaw agent 需要监护人》 |
| **M2-M4** | 6-8 周 | 社区运营：微信公众号 + 知乎 + 极客公园；做评估器市场，邀请社区贡献 | 1000+ GitHub stars，社区贡献 5+ 评估器 |
| **M4-M6** | 8-12 周 | 做商业化层：企业版（审计Dashboard + SLA + 合规报告 + 私有部署） | 签下第一个付费企业用户 |
| **M6-M12** | 持续迭代 | 扩展到 Qwen Agent / DeepSeek Agent / Codex 等；支持国产芯片适配 | 成为国内 AI agent 安全的默认选项 |

### Step 4：关键的"开源商业化"飞轮设计

```
开源吸引开发者 → 开发者在企业引入 → 企业需要合规 → 采购企业版
                          ↻
                 企业版收入投入社区
```

**具体怎么做：**

1. **评估器市场（Evaluator Marketplace）** — 开源版自带基础评估器（PII、关键词屏蔽、速率限制），企业版提供高级评估器（行为基线异常检测、MJ 合规、跨境数据流监控）
2. **审计和报表** — 开源版可以记录，企业版提供 SOC 2/GDPR/等保合规的自动报表生成
3. **策略协作** — 开源版单机，企业版多团队协作、策略版本管理、AB 测试
4. **中国特色的增值点** — 国产大模型适配（Qwen/DeepSeek/GLM）、信创生态兼容、等保三级合规报告

### Step 5：不开源的护城河——数据集

这是最重要的。**所有评估器都开源，但"什么样的 agent 行为算异常"的训练数据和规则集是闭源的。**

Onyx 的护城河就是跨厂商 agent 行为数据集。你在中国可以做同样的事：因为你最早做 OpenClaw 的安全插件，你最先知道中国企业的 agent 在干什么、犯什么错。这个数据集随时间越滚越大，后来者无法复制。

### 风险 2：商业化周期

### 风险 3：OpenClaw 生态的风险

**缓解**：不要绑定死 OpenClaw。架构设计时就要能对接任意 agent 框架（Qwen Agent、DeepSeek Agent、甚至国外的 Claude Code）。

### 风险 4：模型厂商自己解决
DeepSeek/Qwen 可能会在产品层面加安全层。但正如 Onyx 的 Maxim 说的：**企业不想让模型厂商看到 agent 行为数据。** 这个心理在中国更强烈（数据主权、合规）。

这个方案跟 EvoMind 的关系挺直接的——就是给 EvoMind 加上**语音输入 + AI 润色**的能力，类似 Typeless 那种"说话直接出干净文字"的体验。

### 为什么要做这个

目前 EvoMind 的交互方式主要是打字的，加上语音输入能覆盖更多场景：

- **办公场景**：写文档、做笔记的时候，说话比打字快 3-4 倍
- **不方便打字的时候**：走路、开车、做家务时也能跟 EvoMind 交互
- **方言用户**：EvoMind 如果有面向方言用户的场景，讯飞是目前唯一能把四川话、粤语、河南话转文字的选择

### 具体怎么关联

咱们已经确定了**方案 D（混合方案）**作为最终路线：

```
在线 → 讯飞语音听写 WebAPI（中文 98%+ 准确率）
离线 → Whisper 本地模型（保底）
       ↓
   原始文本
       ↓
润色：在线 → 星火大模型 API / 离线 → 本地 LLM
```

**三个关键结合点：**

1. **ASR 层** — 在线场景走讯飞流式听写（`wss://iat-api.xfyun.cn/v2/iat`），16KHz 采样、PCM 格式，边说边出字，支持 25 种方言
2. **润色层** — 转写后的原始文字（带口头禅和重复），交给 LLM 做去口语化处理。如果在线就用星火 API，如果已经有 EvoMind 内置 LLM 也可以走自己的
3. **智能切换** — 根据网络质量自动选择走讯飞还是 Whisper，不需要用户手动切
