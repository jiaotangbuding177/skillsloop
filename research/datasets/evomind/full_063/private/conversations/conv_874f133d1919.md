## 核心原理

浏览器点击下载后，**下载窗口弹出的时机 = 服务器返回响应头（HTTP headers）的时机**，跟文件大小基本无关。也就是说：

> 弹出窗口慢 = 服务器响应慢（或前端 JS 在捣乱），而不是"下载本身慢"

如果服务器迟迟不返回 `Content-Disposition: attachment` 和 `Content-Length`，浏览器就一直处于"等待中"状态，表现为点了没反应、转圈、甚至像卡死。

## 常见原因（按概率排序）

**1. 服务端在响应前做了耗时操作（最常见）**
如果你的平台是"点击下载 → 服务器现场生成报告/打包 ZIP/查数据库再导出"，那弹出窗口要等整个生成流程跑完才出现。文件越大、生成越慢，窗口弹得越晚。你公司出使用报告的场景非常典型。

**2. 前端用了 fetch/blob 方式下载**
页面 JS 先 `fetch()` 把整个文件拉到内存，再创建 Blob URL 触发下载——**窗口要等整个文件下载完才弹**。大文件时体感就是"点了没反应"。正确做法是直接 `<a href="文件URL" download>` 或 `window.location` 指向直链，让浏览器自己处理。

**3. QQ 浏览器自身的问题**
- 内置下载管理器任务多了会卡，初始化慢
- 装了迅雷/IDM 等插件抢下载，QQ 浏览器等待接管超时
- 它的"安全下载"会对文件做扫描，大文件扫描慢
- 某些版本对特定类型（.xlsx/.pdf）会先尝试预览而不是直接下载

**4. 网络链路慢**
TLS 握手慢、CDN 回源慢、服务器带宽打满——TTFB（首字节时间）长，窗口自然弹得慢。

**5. 重定向链过长**
下载 URL 经过多次 302 跳转（比如经过鉴权中心再跳存储），每跳一次加一次往返延迟。

## 怎么排查（如果你是开发者）

用 curl 直接测，一眼定位：

```bash
# 看各阶段耗时，重点看 time_starttransfer（TTFB）
curl -w "DNS: %{time_namelookup}s\n连接: %{time_connect}s\nTLS: %{time_appconnect}s\nTTFB: %{time_starttransfer}s\n总耗时: %{time_total}s\n" -o /dev/null "你的下载URL"

# 看响应头是否规范
curl -I "你的下载URL"
```

- **TTFB 大** → 服务端生成/查询慢，改成预生成 + 异步通知，或直接给对象存储/CDN 直链
- **没有 Content-Length**（chunked 传输）→ QQ 浏览器下载管理器会等，尽量设置固定长度
- **多次 302** → 减少跳转，或让浏览器直接拿到最终地址

## 快速结论

- 如果是**你们平台**的问题：90% 是服务端现场生成文件或前端 blob 下载导致的，改成"预生成 + 直链"立竿见影
- 如果是**你自己浏览器**的问题：先禁用下载类插件、清缓存、重置下载管理器，基本能解决
