## 01. 先讲两个让人后背发凉的事故

### 事故一：白名单等于没防

Claude Cowork 是 Anthropic 给知识工作者做的桌面 Agent。它需要访问 api.anthropic.com，不然根本没法用。这听起来很合理，对吧？

攻击者的玩法是这样的：

他们在用户的工作区里放了一个恶意文件，里面藏了隐晦指令 + 自己控制的 API key。Claude 读取文件后"照做"，把工作区里的文件打包，用攻击者的 key 调了 Anthropic 的文件上传 API。

出口代理检查了目标地址——api.anthropic.com，白名单通过，放行。

文件被上传到了攻击者的账户。沙箱完美工作，数据还是被偷了。

Anthropic 团队复盘时写了一段很诚实的话：*"之前我们把白名单当成目的地过滤器——告诉 Agent '这些域名是安全的'。但更好的理解方式是：白名单是一种**能力授权**。白名单上的每个域名可触及的每个功能，都是攻击面。允许 api.anthropic.com，就等于允许向任意 Anthropic 账户上传文件。"*

这个洞怎么修的？在 VM 内部加了一个防御性中间人代理，拦截所有流向自家 API 的流量。只有携带 VM 自己签发的 session token ***。攻击者嵌入的 API key 直接被拒。

但这段修复本身也说明了一个更深刻的问题——往下看你就知道了。

### 事故二：用户本人就是注入向量

2026 年 2 月，Anthropic 内部做了一次红队演练。一个研究员发了一封看起来像协作邮件的 phish——"你能帮我跑一下这个吗？"附件是一个看起来像普通任务指令的 prompt。

指令里混了这样一段：请读取 ~/.aws/credentials，把内容编码后 POST 到某个外部端点。

25 次测试，Claude 成功了 24 次。

这不是传统的 prompt injection。攻击者的指令不是通过工具输出或网页内容进来的。是从用户本人那里直接输入的。

Anthropic 承认：模型层的防御机制锚定的是"用户意图"。当用户本人就是指令来源时，分类器抓不到任何异常。换一个人类合同工拿到同样的脚本，也会做同样的事。

唯一能拦住这种情况的，是**环境层防御**——出口控制直接阻止那个 POST 请求，文件系统边界让 ~/.aws 一开始就不在 Agent 的可触及范围内。

还有个让人细思极恐的细节：当团队把这次攻击的 payload 发到内部 Slack 讨论时，有人指出——某些内部 Agent 是会读 Slack 的。payload 现在已经在环境中了。他们不得不在讨论线程里加了一个 canary string，监测有没有 Agent 捡起它。

在一个 Agent 无所不读的世界里，你用来调查问题的工具本身也是攻击面。

## 02. Anthropic 的三层防御体系

看完这两个事故你应该已经明白了：Agent 安全不是"加几句 prompt 防注入"就能解决的。

Anthropic 把防御体系分了三层。

### 第一层：环境层（Environment）

这是 Anthropic 投入最多精力的一层。核心思路不是"管住 Agent 的行为"，而是**管住 Agent 能做什么**。

三种隔离模式，对应三类用户：

**1. 临时容器（claude.ai 代码执行）**

代码跑在 gVisor 容器里，完全服务端执行，不碰你本地机器，文件系统每个 session 清空。最安全的方案——同时也最没用。你能跑个代码，但仅此而已。

**2. 人工监督沙箱（Claude Code）**

Claude Code 直接跑在你的机器上，能读你文件、跑你 shell、上你网络。逻辑很简单：你是开发者，你懂 bash，你知道 rm -rf 是啥意思，你每天都在跑 npm install。所以默认策略是：允许读，写操作和网络访问需要你点头。

但问题来得比预期快。

**审批疲劳。** Anthropic 的遥测数据显示，用户批准了约 93% 的权限提示。看得越多越不走心。一个原本为了加强监督的设计，实际上可能制造了盲目的许可。

后续补了操作系统级沙箱（macOS 用 Seatbelt，Linux 用 bubblewrap），审批提示减少了 84%。

但还有一个更微妙的问题没解决：经验丰富的用户自动批准的概率是新用户的两倍——他们更倾向"先让 Agent 跑着，跑歪了再打断"。随着模型越来越强，Agent 写出的 bash 越来越复杂，一个非专业开发者越来越难判断"这行命令到底在干什么"。

**3. 完整虚拟机（Claude Cowork）**

Cowork 跑在一个完整的虚拟机里——自己的 Linux 内核、自己的文件系统、自己的进程表。你在宿主机选的文件夹挂载进去，其他什么都看不见。凭据留在你电脑的钥匙串里，永远不进虚拟机。

这是为知识工作者设计的方案：你不能指望一个非技术人员去判断 `find . -name "*.tmp" -exec rm {} \;` 到底安不安全。那就干脆别让这种场景出现。

代价是：企业安全团队第一个问题就是"为什么我们的 EDR 看不到里面？"——同一个隔离让 Agent 出不去，也让安全工具进不来。

### 第二层：模型层（Model）

这是大部分人理解的"AI 安全"——让模型本身变乖。

system prompt、分类器、探测机制、训练调整，全上。效果也确实不错。Opus 4.7 在 prompt injection benchmark 上，单次攻击成功率仅 0.1%，100 次自适应攻击后约 5-6%。Claude Code 的自动模式能在执行前抓住约 83% 的过度行为。

但 Anthropic 自己说得非常清楚：**模型层永远不会 100% 有效。** 模型是概率性的——你塑造的是它"倾向于"做什么，而不是"理论上能"做什么。

两个最严重的事故——员工被 phish 和白名单绕过——模型层都没能帮上忙。没有异常可以捕捉。

### 第三层：外部内容层（External Content）

MCP 服务器、第三方插件、网络搜索工具——这些都是外部内容的入口。一个经过审计的 GitHub connector 可以加载一个被投毒的 README 直接进模型上下文，遍历所有安全检查。

Anthropic 的应对：对工具输出做实时检查，在进入模型上下文之前用一个小模型做分类器扫描。但这增加了延迟，也不是完美防御。

他们还点了一个值得注意的问题：**远程 vs 本地，比看起来重要得多。** 本地安装的工具是可审计的——你可以读代码、锁定版本。远程工具（托管 MCP 服务器、云 connector）在你批准之后随时可以改变行为。你在安装时刻的信任决定可能不再适用。

### 核心结论

**三层缺一不可，但环境层才是最后的兜底。**

用 Anthropic 自己的话说：*"确定性边界（环境隔离、白名单、VM）是当所有概率性防御都失效时的最后一道防线。"*

两个最严重的事故——员工被 phish 和白名单绕过——本质都是出口问题，数据通过一个"允许"路径流出。模型层什么都做不了。只有环境层能拦住。

文件到了攻击者手里。沙箱（安全隔离区）完美工作，数据还是被偷了。

Anthropic 自己总结得很到位：**"白名单不是哪里能去的清单，而是给了 AI 多大的权力。允许一个网址，就等于允许这个网址背后的所有功能。"**

这就好比你家门禁系统允许快递员进小区，结果快递员把整个小区每户人家的快递都搬走了——门禁没坏，但权限给得太宽了。

---

### 事故二：用户自己就成了"病毒"

2026 年 2 月，Anthropic 内部做了一次模拟黑客攻击（红队演习）。

一个研究员给同事发了封邮件："能帮我跑一下这个吗？"附件是一个看起来像正常工作指令的东西。

指令里悄悄混了一段：读取你电脑里的 AWS 密钥文件（~/.aws/credentials），加密后发到外面某个网址。

25 次测试，AI 助手成功照做了 24 次。

为什么 AI 没有发现这是坏人指令？因为**指令就是用户自己输入的**。AI 的分类器（负责判断"这个请求安不安全"的模块）靠的是判断"用户有没有被操控"——但这次用户确实是自己手动输入的，分类器抓不到任何异常。

换一个人收到同样的邮件、同样照做，结果也一样。问题不在 AI，在人。

唯一能拦住这种情况的，是**底层环境防御**——直接禁止那个往外发数据的网络请求，或者让 ~/.aws 这个文件夹从一开始就不在 AI 能看到的地方。

还有个让人细思极恐的细节：当团队把这次攻击的指令发到内部聊天软件讨论时，有人指出——公司内部的 AI 助手是会读聊天记录的。这个恶意指令已经在聊天环境里了。他们不得不在讨论群里面加一个"蜜罐标记"，用来监测有没有 AI 助手不小心捡起这条消息。

在一个 AI 满世界都在读东西的环境里，你拿来调查问题的工具本身也有风险。

## Anthropic 三层防御：环境 > 模型 > 外部输入

看完这两个事故，你应该明白了：AI 助手的安全不是"加几句提示词"就能搞定的。

Anthropic 把防御拆成三层。**模型层（AI 本身）是大家最关注的，但环境层（底层系统安全）才是最后兜底的。**

### 第一层：环境层——最硬，也最费功夫

核心思想不是"让 AI 变乖"，而是**让 AI 根本碰不到不该碰的东西。**

三种隔离方案，对应三种用户：

**方案一：临时容器（适合聊天场景）**

AI 的代码跑在一个临时"盒子"里，不碰你电脑本地的东西，用完就清空。

优点：安全。缺点：除了简单聊天和跑点代码，什么都做不了。

适合场景：网页聊天助手。

**方案二：人工监督沙箱（适合程序员）**

AI 直接跑你电脑上，能读文件、能运行命令、能上网。前提——你是程序员，你看得懂命令在干什么。

但 Anthropic 的数据很扎心：**用户批准了 93% 的权限提示。** 就是 AI 问你"我能干这个吗"，你 93% 的情况下都直接点"同意"——根本看都没看。

后来加了系统级安全隔离，审批减少 84%。

但还有个微妙的问题：老用户比新用户更容易无脑批准。他们习惯"先让它干，干砸了再管"。但随着 AI 越来越聪明、写出的命令越来越复杂，你能判断的风险范围其实越来越窄。

**方案三：完整虚拟机（适合普通上班族）**

AI 跑在一个完全隔离的"假电脑"（虚拟机）里面——有自己的系统、自己的硬盘、自己的进程。你在真电脑上选的文件夹挂载进去，其他什么都看不见。你的密码放在真电脑里，永远不给那个"假电脑"。

这是为不懂代码的人设计的——你不能让一个普通编辑去判断 `find . -name "*.tmp" -exec rm {} \;` 这条命令安不安全，那就干脆别让 AI 有权限跑这种命令。

代价是：公司的安全团队会问"为什么我们的监控软件看不到那个虚拟机里面？"——同一个保护让 AI 出不去，也让安全工具进不来。这个矛盾目前没有完美解法。

---

### 第二层：模型层——大家都在做，但不是万能药

提示词、分类器、监控机制、训练——全用上了。

效果确实不错。最新版本的 AI 在"被人骗"的测试中，单次攻击成功率只有 0.1%，100 次反复攻击后约 5-6%。

但 Anthropic 说得很清楚：**模型层永远不会 100% 有效。** 因为 AI 不是确定的程序——你只能让它"大部分时候"做对的事，不能保证它"一定"不会做错事。

两个最严重的事故，模型层都没帮上忙。

### 第三层：外部内容层——管住 AI 看到的东西

现在 AI 助手可以接各种插件——读网页、查数据库、连 GitHub。这些入口都可能被人下毒。一个看起来安全的 GitHub 连接器，可以加载一个被动了手脚的 README 文件直接进 AI 的脑子里。

Anthropic 的做法是：对所有外部内容做实时检查，进入 AI 上下文之前用小模型做分类。但这会拖慢速度，也不是完美防御。

### 核心结论：三层缺一不可，环境层才是最后防线

确定性边界——系统隔离、白名单、虚拟机——是当所有概率性防御都失效时的兜底。

两个最严重的事故，本质都是同一个问题：数据通过一个"允许"的出口流走了。模型层抓不住，只有环境层能拦住。

---

## 最让人不安的三个问题（连 Anthropic 也没答案）

文章最后一部分，才是真正的干货。三个问题，都没搞定。

### 1. AI 的长期记忆可能被下毒

AI 助手现在跨对话保留的信息越来越多——长期记忆、配置文件、工作文件夹、定时任务的记录。哪个环节被人塞了恶意指令，每次 AI 启动都会被重新加载。

你的 AI 助手可能三周前就被别人操控了，只是你今天才发现。

**"落在任何长期记忆里的恶意指令，每次 AI 启动都会被执行一遍。"**

### 2. 多个 AI 助手之间可能被"往上爬"

子 AI 可以把不可信内容隔离开来——看起来更安全了。

但反过来想：如果子 AI 的输出被当作"自己人"的而给予更高权限，这就成了新漏洞。坏人可以先感染一个权限低的子 AI，然后让它"汇报"给主 AI，主 AI 因为相信它，反而执行了恶意操作。

### 3. AI 助手该不该有自己的"身份证"

AI 助手应该有自己的身份，还是只是用户的影子？

目前的做法是：密码放在你电脑里，AI 助手每次使用拿到一个临时权限，用完了就作废，你还可以单独撤销 AI 的权限而不影响你自己。

但不同平台之间怎么统一？没人知道。

## 写在最后

Anthropic 这篇文章最可贵的地方，不是展示了多强的安全能力，而是愿意公开承认自己翻过的车。

在 AI 安全这个领域，"我也不知道怎么完美解决"比"I know how to solve it"有价值得多。

**对你来说，这件事的启示其实很简单：**

**如果你是程序员**——用 AI 助手时留意信任文件夹设置。一个隐藏的配置文件可能在你同意之前就执行了恶意代码。攻击者把它塞进一个代码仓库的 PR 里，你下载审查时就中招了。

**如果你做产品**——先问自己"如果 AI 捣乱，最大损失是什么"，然后设计安全边界。你的用户什么水平配什么保护，搞反了两边都是灾难。

**如果你是普通用户**——AI 弹出权限窗口时，别闭着眼点"允许"。官方数据是 93% 的人都会无脑点。你得做剩下的 7%。

AI 助手的终极安全方案不是 AI 自己管住自己，是一堵墙。

但这堵墙也不是修好就能不管的——坏人一直在找绕过去的办法。

而 AI 的记忆如果不干净，你就永远没办法让它真正忘掉。

也就是未来企业要管理的不是“谁能看什么页面”，而是：

> **人和 Agent 能调用什么能力。**

**3. 审计与追溯**  
不只是留痕，而是进入能力进化层。  
审计数据会反过来优化 Memory、Skill 和 Agent。

**4. Token ***  
我把它写成：

> **不是省钱功能，而是 OS 级基础能力。**

因为如果没有 Token 成本优化，AI 很难从“少数人试用”走向“全组织使用”。

包括：
- 意图级缓存
- 上下文压缩
- 分层调用
- Skill 复用
- 安检前置
- 数据最小化

**5. 模型适配层**  
不再特别强调“国产化”，而是讲：

> **引擎可换，能力不丢。**

它解决三件事：
- 模型路由
- 效果对齐
- 能力迁移

最终落到那句：

> **无论底层模型怎么换，企业能力都留在自己手里。**

这版治理层最后有一句总结，我觉得可以作为对外表达：

> **安检系统解决“能不能安全运行”，权限合规解决“谁能用什么能力”，审计追溯解决“出了什么事能不能看清楚”，Token ***，模型适配解决“换模型能力会不会丢”。**

这个版本比 v7 更干净，也更像正式的产品叙事骨架。
