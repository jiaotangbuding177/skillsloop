## 🔴 核心诊断：为什么还是工程味？

**灵魂拷问**：这篇论文如果去掉"实现了一个什么系统"，还剩什么学术贡献？

一个学术论文的核心是**回答一个可证伪的研究问题**，而不是**描述一个系统的设计和实现**。优化版在以下四层都存在"工程伪装成学术"的问题：

---

### 1. 研究问题：HOW 而非 WHY/WHAT

| 初版/优化版提出的"关键问题" | 问题类型 |
|---|---|
| 如何确保流程与密码学双重约束可靠有效 | 工程实现问题 |
| Git平台ACL权限模型的适用边界 | 勉强接近学术问题 |
| 异步工作流下语义冲突的有效检测 | 工程实现问题 |
| 服务端验证的性能与可扩展性 | 性能调优问题 |
| 原型系统在真实场景中的可用性验证 | 可用性测试问题 |

五个"关键问题"中，**四个半是工程问题**。学术论文需要的研究问题是：
- "人类审核机制对知识库质量的影响是否显著？在什么条件下显著？"
- "不同约束强度下，AI协作效率与知识库可靠性之间的trade-off关系是什么？"
- "异步协作中，人类审核延迟与知识库演化速度之间的关系模型是什么？"

这些问题才有**可证伪性**——实验结果可能支持也可能不支持假设，而不是"我做的系统运行正常不崩"。

---

### 2. 文献综述：罗列系统，不构建对话

当前综述的组织方式是"谁做了什么系统"：

> "Arndt等人提出了Quit Store……Wu提出了Git Context Controller……Kandpal等人提出Git-Theta……"

学术文献综述应该组织为"学界对某个问题有一系列逐步深化的认知"：

> "在该方向上的研究经历了三个阶段。第一阶段（2016-2019）将版本控制思想应用于结构化数据……其局限在于……第二阶段（2020-2024）开始关注非结构化内容的版本管理……其未解决的问题是……第三阶段（2025至今）在LLM背景下重新审视协作冲突……"

**建议**：围绕一个核心张力来组织文献。"AI参与知识共建"这个场景中的核心张力是 **效率 vs 控制**——一端是完全放开让AI直接写入（RAG、Agent协作），另一端是完全人工审核（传统Wiki）。现有工作在这个光谱上的位置是什么？本研究的定位是什么？这样综述就有了一条理论主线，不再是系统罗列。

---

### 3. 方法设计：缺少可证伪的假设

当前的第3章"研究方法"是：

> "文献研究法……系统设计法……实验研究法……案例研究法"

这是万金油模板，放到任何一篇硕士论文都能用。真正需要的是：

**从一个具体的研究假设出发，展开实验设计。** 例如：

> **H1**: 在异步协作场景下，引入human-commit审核机制后，知识库的事实性错误率显著低于无审核的AI自主写入模式。
> **H2**: 但human-commit审核机制会带来平均审核延迟，该延迟与知识库规模呈正相关，与审核者熟悉度呈负相关。
> **H3**: 双重约束（流程+密码学）相比单层约束（仅密码学），对AI绕过行为的阻止率有显著提升。

有了假设，实验设计自然就有了——每个假设对应一组对照实验，有自变量（审核机制的有无/强度）、因变量（错误率/延迟/绕过率）、对照组和统计检验。

---

### 4. 实验方案：功能验证 ≠ 实验验证

当前的"功能正确性测试方案"本质上是软件测试：

> "验证人类审核机制（确保AI无法单方面提交）、权限裁决机制（确保权限映射正确）、语义冲突检测（确保能识别预定义类型的语义冲突）"

这里的逻辑是"确保XX正确"——这是验收，不是研究。**研究实验的逻辑是"XX是否成立"**：

| 工程验收 | 学术实验 |
|---------|---------|
| 确保AI无法单方面提交 | AI尝试绕过审核的成功率是多少？不同约束策略下的差异？ |
| 确保权限映射正确 | 权限粒度从仓库级到文档级的降级对可用性的影响？ |
| 确保能识别语义冲突 | 语义冲突检测的精确率和召回率？与纯文本diff的增量收益？ |

---

## 🎯 可行的学术化改造路径

不改选题和方向，只换框架。三条路径可以选一条，或组合使用：

### 路径A：走"机制有效性验证"路线

**核心研究问题**：权限约束机制在人与AI协作知识库场景中的有效性如何？

**可证伪假设**：
- H1：双重约束（流程+密码学）相比无约束的AI自由写入，知识库内容的事实性错误率降低X%
- H2：引入human-commit后，知识库演化速度（提交频率）下降不超过Y%，即约束没有过度抑制AI的生产力
- H3：异步语义冲突检测相比纯文本冲突检测，能额外识别Z%的实质性矛盾

**实验设计**：受控实验，同一知识库建设任务，三组对照（无约束 vs 单层密码学约束 vs 双重约束），同一个任务让不同组完成，测量准确率、效率、冲突检出率。

**学术贡献**：首次在人与AI协作知识库场景中，对约束机制的"效率-可靠性"trade-off提供量化证据。

---

### 路径B：走"约束模型形式化"路线

**核心研究问题**：人与AI协作知识库中的参与写入动作如何形式化建模？不同约束策略的理论性质是什么？

**方法**：定义human-commit的形式模型（状态机/Petri网/进程代数），给出并证明关键性质（安全性——AI永远不能独立完成提交；活性——人类审核不会永久阻塞知识库演化）。

**实验**：形式化模型的实例化验证——用一个简化的原型验证模型的核心性质在实现中是否保持。

**学术贡献**：为AI协作知识库提供可形式化验证的约束模型，其安全性有理论保证而非仅靠工程隔离。

---

### 路径C：走"约束强度对协作效果的影响"路线

**核心研究问题**：不同约束强度（审核粒度、审核延迟、权限精度）如何影响人与AI协作知识库的质量和效率？

**方法**：把human-commit的约束强度作为自变量（而非二进制开关），设计多个约束等级。例如：
- 等级0：AI自由写入，无审核
- 等级1：AI提交后人类批量审核
- 等级2：AI提交后人类逐条审核
- 等级3：AI只能写入草稿区，人类需主动拉取审核

**实验**：用同一知识库建设任务，测量不同约束强度下的最终知识库质量（人工评分）、建设效率（完成任务的时间）、用户满意度（SUS量表）。

**学术贡献**：给出"约束强度-协作效果"的经验曲线，为工程实践提供参数选择依据。

---

## 路径B的核心改造：从"做系统"到"建模+证明+验证"

### 三段式研究目标

| 层次 | 做什么 | 输出 |
|:---:|------|------|
| 建模层 | 知识库写操作用状态机/迁移系统定义，区分人/AI的权限 | 形式模型 + 操作语义 |
| 证明层 | 用CTL/LTL证明三个安全性质 | AI隔离性、审核不阻塞性、可审计性 |
| 验证层 | 模型映射到Knoin系统，双向一致性检验 | 模型-实现缺口分析 |

### 五个关键问题

```
Q1：建模粒度选择（太粗丢语义，太细状态爆炸）
Q2：AI隔离性证明的完备性（模型是否覆盖所有真实攻击面）
Q3：Liveness与安全性的协调（会不会卡死在等审核）
Q4：形式模型到Git工作流的保性映射（哪些Git特性需要禁掉）
Q5：约束模型的表达力边界（哪些安全性能保证，哪些不能）
```

### 为什么这条路去掉了工程味

- **研究问题变了**：不是"怎么实现human-commit"，而是"human-commit的安全性在什么条件下成立、能不能被形式证明"
- **方法变了**：不是"文献研究法+系统设计法+实验研究法"万金油，而是"形式化建模→性质证明→一致性验证"
- **贡献变了**：不是"我做了一个能跑的系统"，而是"我定义了一套可证明安全的约束模型，并验证了它的可实现性"
- **失败也有价值**：如果证明发现"在Git上不可能完全满足S1+S2"——这个**阴性结论本身就可以发论文**

## 路径C：把"审不审核"变成"审到多少最划算"

### 灵魂改造

| | 原版/优化版 | 路径C |
|------|-----------|------|
| 核心问题 | 怎么实现一个约束机制 | **约束到什么强度性价比最高** |
| 自变量 | 无（做出来就完了） | 四个约束等级 L0→L3 + L2次参数N |
| 因变量 | 系统跑不跑得通 | 知识库错误率 + 协作效率 + 认知负荷 |
| 结论 | "系统实现了预期功能" | "L2-N3是最优区间，再收紧得不偿失" |

### 四个等级设计

```
L0: AI随便写，零审核      ← 自由端
L1: AI写完通知你           ← 轻量约束
L2: AI不能提交，你批一批   ← ← 核心实验区（批次大小可调N=1/3/5/10）
L3: AI每改一个字都等审批   ← 严格端
```

把L2的批次大小N做成连续参数，就有了画曲线的数据点。

### 四个可证伪假设

| H | 断言 | 关键检验 |
|:--|------|---------|
| H1 | 约束越紧，错误率越低 | ANOVA + Tukey HSD |
| H2 | 约束越紧，效率越低 | 同上 |
| **H3** | **存在一个最优等级——再收紧一笔效率损失大于质量提升** | **边际替代率曲线** ← 核心贡献 |
| H4 | 事实型内容对约束最敏感，规范型最不敏感 | 交互效应检验 |

H3是论文的黄金切入点——不是简单说"约束有用"，而是**找出性价比拐点**。即使实验结果发现"L1就够了，L2和L3多此一举"，这也是有价值的发现（说明轻量约束已足够）。
