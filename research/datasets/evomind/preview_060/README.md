# EvoMind 三条真实会话预览

本批只整理三条真实企业历史会话，供确认数据组织方式；不是新编对话，也不是完整数据集。没有运行任务识别、轨迹恢复或技能生成。

## 先看这里

- [三条会话网页总览](private/index.html)：完整正文、用户／AI分组、原消息编号和来源行号。
- [合同审阅会话](private/conv_f586a09e7356.md)：37条消息，4条用户消息、33条AI消息。
- [短会话](private/conv_25c0d5cc4fd4.md)：8条消息，4条用户消息、4条AI消息。
- [存在排序冲突的会话](private/conv_9f975ffa392f.md)：77条消息，28条用户消息、49条AI消息。

共122条消息：36条用户消息、86条AI消息。正文保持原样，平台前缀、技能请求、连续AI消息、附件相关表述均保留。没有根据内容补写消息，也没有添加“任务不明确”“任务失败”等语义标签。

## 如何组织

[JSON数据](private/evomind_conversations.json)最外层以会话编号为键。每个会话保留原消息清单、完整原始记录和来源行号，同时提供便于阅读的回合视图。[JSONL数据](private/evomind_conversations.jsonl)每行一条会话，共三行。

回合视图只是显示分组：用户发言后接连续AI消息；连续用户发言放在同一组里。没有把每条AI消息强制凑成一问一答，也没有建立已验证的回复指向。展示回合数不等于任务数或轨迹数。

## 顺序如何看

主视图保留原导出文件行序，作为不丢信息的暂存展示，**不是已核验的事件时间线**。编号均为数字形式的会话另提供“数字编号候选顺序”供比较；编号的上游含义尚未证实，不默认它一定正确。两种视图引用同一批消息，不算两份样本。

第三条会话尤其需要对照：原文件顺序形成19个展示分组，数字编号候选形成25组；存在1对严格的用户时间／编号方向冲突，以及2对同时间的编号下降。这些数值说明排序依据尚不一致，不说明发生了多少个错误任务或缺失回复。

原包的消息日期不可用。新包的用户消息时间按会话编号和消息编号精确匹配补入，AI消息未补造时间。正文中的时间表述也没有被当作事件时间。

## 来源与核验

正文来自 `zkys-raw-export-20260925/zclaw_messages.jsonl`，会话信息来自同包 `zclaw_sessions.jsonl`；用户时间及对应原始记录来自 `zkys-skill-mining-20260925/user_messages.json`。不使用人工恢复轨迹作为输入。

本批三条会话均为trusted记录、状态均为done，没有观察到同会话客户端／trusted双副本。这一结论仅限本批，不外推全库。附件二进制未随当前数据提供，不因此剔除会话；保留已有附件元信息，不推断附件内容或业务验收结果。

[核验清单](manifest.json)记录来源及输出哈希、消息数量和检查结果：原文件未变、所有原消息保留、各视图正文与来源完全一致、JSON与JSONL一致。没有调用大模型。

[整理脚本](build_preview.py)可在项目根目录使用 `python research/datasets/evomind/preview_060/build_preview.py` 重新生成本批预览。原始来源路径须可访问。全量会话的重复副本处理和最终顺序口径尚未在本批定案。
