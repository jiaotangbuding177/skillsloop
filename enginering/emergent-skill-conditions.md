# 涌现 Skill 的生成条件

> 回答一个问题：**什么样的条件下，系统才会给我生成一个 Skill？**
> 全部数值取自当前代码（`apps/api/src/skill-emergence/`、`apps/api/src/skill-analytics/`），非估算。

---

## 0. 速查：五道关，任何一关不过都拿不到 Skill

| 关 | 名称 | 核心条件 | 谁决定 |
| --- | --- | --- | --- |
| ① | **采集** | 有一轮**成功完成**且**未使用任何 Skill** 的对话 | 你的使用方式 |
| ② | **归类 + 建模** | 同类任务攒够次数，被提炼成「可复用流程」 | 系统后台（每 60 秒） |
| ③ | **门禁** | 四条通道（频次/深度/价值/单次长任务）**任一达标** | 你的证据量 + 任务本身的形态 |
| ④ | **封装** | skill-creator 生成 `SKILL.md` 并通过质量校验 | 系统（含一次自动修复） |
| ⑤ | **确认** | 你在涌现页点「纳入个人」 | 你 |

**最容易被误解的一点**：第 ② 关和第 ③ 关是**两套不同的门槛**。
2 次同类对话就够「建模」（让任务变成可评估的候选），但要让门禁合格通常需要 5 次。
所以「评估了 4 个聚类，合格 0 个」是正常状态，不是故障。

---

## 1. 全流程一览

```
你正常用 AI 工作台干活
        │
        │  每一轮对话结束的瞬间（实时）
        ▼
┌─────────────────────────────────────────────┐
│ ① 采集：判断这轮要不要作为证据留下来          │
│    ✓ 成功完成  ✓ 本轮没用任何 Skill           │
│    ✗ 失败/中断/取消  ✗ 系统会话  ✗ 定时任务    │
└─────────────────────────────────────────────┘
        │  一问一答 + 脱敏后的文本快照
        ▼
┌─────────────────────────────────────────────┐
│ ② 归类：这是什么类型的任务？                  │
│    → 归入某个「任务聚类」（企业内共享）        │
│    后台 worker，每 60 秒一轮，单轮最多 20 条   │
└─────────────────────────────────────────────┘
        │  同类任务攒够次数后
        ▼
┌─────────────────────────────────────────────┐
│ ② 建模：把这类任务提炼成「可复用流程」         │
│    → 聚类状态变为 path_analyzed（可评估）     │
└─────────────────────────────────────────────┘
        │
        │  上海时间每天零点（或管理员手动触发）
        ▼
┌─────────────────────────────────────────────┐
│ ③ 门禁：四条通道 OR，任一达标即合格            │
│    A 频次   B 深度   C 价值   D 单次长任务     │
│    （前面还有冷却/在途/重复/无新证据四道拦截） │
└─────────────────────────────────────────────┘
        │  合格
        ▼
┌─────────────────────────────────────────────┐
│ ④ 封装：skill-creator 生成 SKILL.md           │
│    失败可重试，最多 3 次                       │
└─────────────────────────────────────────────┘
        │  质量校验（不合格会自动修复一次）
        ▼
┌─────────────────────────────────────────────┐
│ ⑤ 等待你确认：AWAITING_CONFIRM                │
│    纳入个人 → INSTALLED（完成）               │
│    也可直接提交组织审核 → SUBMITTED            │
└─────────────────────────────────────────────┘
```

**端到端最短耗时**：聊完 → 等 ≤60 秒（归类建模）→ 手动触发评估 → 等封装跑完（几十秒到几分钟）。

## 2. 逐关条件

### 关 ① 采集：什么对话会变成证据

四条**同时**满足才会记一条：

| 条件 | 说明 |
| --- | --- |
| 该轮**成功完成** | 失败、中断、取消、超时 → 不留记录 |
| 该轮**未使用任何 Skill** | 你这一轮选了技能 → 整轮跳过 |
| 不是系统/隐藏会话 | 系统编排、定时任务不计 |
| 开关已开启 | B 端由企业管理员开；C 端你自己在个人设置里开 |

**为什么排除「用了 Skill 的轮次」**：涌现只学「还没有技能、但人们反复在手工做的事」。
已经被技能解决的领域不重复投入。

**粒度是「回合」不是「会话」**：一次会话 5 个来回 = 5 条证据。

留下的是：标识 + 规模信号 + **脱敏截断后的问答文本**（邮箱/手机号/网址/路径替换为占位符，压成单行，上限 12,000 字符）。保留 **90 天**。

---

### 关 ② 归类与建模：什么时候形成「可评估的聚类」

**归类**（每 60 秒自动跑）：把每条证据判成一个任务类型，归入「企业 × 任务类型」的聚类。

**建模**：把同类证据提炼成可复用流程（步骤、分支、工具类别）。触发条件**满足其一**：

| 通道 | 条件 | 通俗解释 |
| --- | --- | --- |
| 常规 | 同类任务 **≥5 次**，且跨 **≥2 个自然日** | 标准的「高频 + 不是一天堆出来的」 |
| 快车道 ① | **≥2 次** | 两次就够建模 |
| 快车道 ② | **≥1 次** 且（该会话消息数 **≥10** 或 该轮问答合计 **≥2500 字**） | 一次很实在的对话就够 |

> 快车道是为对抗「同一类任务被拆成好几个聚类、谁都凑不满 5 次」而设的。

**建模失败的退避**：每次失败按 `尝试次数 × 5 分钟` 退避，连续 3 次失败后聚类标记为 `path_failed` 不再重试。

**建模取样本**：该聚类最近 **5 条**证据（不按用户过滤——企业内共享）。

---

### 关 ③ 门禁：真正决定「能不能出 Skill」的一关

**评估时机**：上海时间每天零点，按「用户 × 企业」逐个跑。周期由 `intervalDays` 决定，夹在 1–30 天（B 端默认 **1 天**，C 端默认 **7 天**）。管理员可手动立即触发一轮，不改变周期。

**统计口径**（先理解这三条，否则看不懂门槛）：

- 窗口：最近 **30 天**
- 只算 **SUCCESS** 的证据（失败/未完成的回合本来就不采集）
- 如果有「水位」（上次封装到哪），改用**水位之后的新证据**计数 → 这就是「同一技能可以再生成一版」的机制

#### 先过四道拦截（按顺序，命中即停，不进通道）

| 拦截 | 条件 | 界面显示 |
| --- | --- | --- |
| 冷却中 | 你拒绝过这个技能，**7 天内** | 冷却中 |
| 在途草稿 | 该聚类已有一份未处理的草稿 | 已有待处理草稿 |
| 重复 | 已存在同名技能 | 已存在同名技能 |
| 无新证据 | 有水位且新证据为 0 | 暂无新证据 / 已覆盖 |

#### 再过四通道 OR（按顺序短路，命中任一即合格）

| 通道 | 条件 | 适合什么任务 |
| --- | --- | --- |
| **A 频次** | 计数 **≥5** | 「我又干了第五次同样的事」 |
| **B 深度** | 计数 **≥2** 且 工作流可复用 且（步骤 **≥5** 或 分支 **≥2** 或 有效工具调用 **≥4**） | 有明确步骤/条件判断的流程 |
| **C 价值** | 计数 **≥2** 且 有结构化价值信号（分支 **≥1**） | 有判断分支的任务 |
| **D 单次长任务** | 池内**恰好 1 条** 且 工作流可复用 且（步骤 **≥8** 或 工具调用 **≥6** 或（单轮字数 **≥8000** 且 步骤 **≥5**）） | 一次就干得很完整的长任务 |

其中两个关键前置定义：

- **工作流可复用** = `workflow.reusable === true` **或** 步骤数 **≥3**
- **有结构化价值信号** = `structuredValueSignal === true` **或** 分支数 **≥1**

**A 通道是唯一没有形态前提的通道**——只要次数够，不管任务结构如何都会合格。

四条都不满足 → `insufficient_signal`（证据不足）。

#### ⚠️ 一个必须知道的既有约束：工作流形态是冻结的

聚类**一旦建模，它的形态（步骤数/分支数）就不再更新**——没有代码会重新建模一个已建模的聚类。

后果：如果一个聚类建模时形态不够（比如只有 1 个步骤、0 个分支），那么**B/C/D 三个通道永远无法达标**，只能靠 **A 通道攒到 5 次**。
这不是「多聊几轮就能解决」的问题，诊断文案会如实告诉你。

---

### 关 ④ 封装：生成 SKILL.md

合格后立刻建候选并入封装队列（队列每 30 秒轮询，单轮最多 10 个任务；入队时会直接执行）。

- 执行者：`skill-creator`（一个只挂载该技能的专用隐藏会话）
- 输入：结构化工作流 JSON + 确定性的「市场信息草稿」
- 重试：最多 **3 次**，租约 10 分钟，超限标记为 `dead`（可在涌现页手动重试）
- 校验：生成后后端会验证「技能确实存在于你的个人工作区」+「SKILL.md 可读」+ 质量过关
- 产出：安装到你的个人工作区 `skills/<skillKey>/SKILL.md`

**skillKey 由后端确定性生成**（`emerged-<任务类型哈希前24位>`），不交给模型起名。

---

### 关 ⑤ 质量校验与确认

`SKILL.md` 必须满足：

| 检查 | 要求 | 不过的后果 |
| --- | --- | --- |
| `## 市场信息` 章节 | 必须存在 | **整体失败** |
| 5 个必填小节 | 适合人群 / 核心亮点 / 典型输入·需求 / 输入预填模板 / 预期输出·成果 —— **都不能为空** | **整体失败** |
| 占位文案 | 不得是 `TODO`/`TBD`/`待填写`/`占位`/`placeholder`，或 <80 字的括号段落 | **整体失败** |
| 标题 | 必须存在 | **整体失败** |
| 标题字数 | **2–12 个汉字** | 放行，展示名被软裁剪 |
| 标题风格 | 不得是学术长标题（命中「驱动的」「基于的」「范式」「建模」「归因分析」等） | 放行，软裁剪 |

市场信息类问题会触发**一次自动修复**（只补 `## 市场信息`，不改目录名、不删正文），修复后仍不过才整体失败。

通过后候选人状态为 **AWAITING_CONFIRM**（草稿态，对你不可见），等你在涌现页决定：
**纳入个人**（→ INSTALLED，进入你的技能库）/ **提交组织审核**（→ SUBMITTED）/ **忽略**（→ REJECTED，触发 7 天冷却）。

## 3. 为什么没出 Skill：对照表

这是排查时最有用的一张表。**在涌现页点「立即触发」，界面会直接按这张表告诉你原因。**

| 界面结论 | 含义 | 你该做什么 |
| --- | --- | --- |
| **还没采集到任何对话** | 一轮符合条件的对话都没有 | 正常用 AI 工作台完成几轮工作对话 |
| **已采集 N 轮，但没有一轮被判定为「成功完成」** | 对话都以失败/中断结束 | 完整走完几轮对话，不要中途打断 |
| **有 N 条对话等待后台归类** | 归类 worker 还没轮到 | 等约 1 分钟后重试 |
| **有 N 个聚类已归类但尚未建模** | 次数不够建模门槛 | 再完成几次同类任务（2 次即可提前建模） |
| **有 N 个聚类建模失败** | 建模连续失败 3 次 | 查 API 日志，必要时调大分析超时 |
| **评估 N 个 · 信号不足 N** | 走到了门禁但四通道都没达标 | 看下面逐聚类的四通道明细 |
| **某聚类：证据不足 + 频次 3/5** | A 通道只差 2 次 | 继续用同样方式完成 2 次同类任务 |
| **某聚类：证据不足 + 工作流步骤不足（当前 2，需 ≥3 步）** | 工作流形态不可复用，且形态已冻结 | 把这件工作的标准做法讲清楚（分几步、有哪些判断条件），让系统归入**新的**任务类型重新建模 |
| **某聚类：该任务缺少结构化价值信号** | 任务没有分支/条件判断 | 同上：补充判断逻辑的描述 |
| **某聚类：本通道不适用** | 单次长任务通道只在「恰好 1 次对话」时评估 | 无需处理（其他通道仍有效） |
| **冷却中** | 你拒绝过这个技能，7 天内不再评估 | 等冷却结束，或联系管理员 |
| **已有待处理草稿** | 这个聚类已经有一份草稿在等你 | 先去涌现列表处理那份草稿 |
| **暂无新证据** | 上次封装后没有新的同类对话 | 正常使用，攒够新证据会自动出下一版 |
| **分析总开关已关闭** | `SKILL_EMERGENCE_ANALYSIS_ENABLED=false` | 联系管理员开启 |
| **封装链路已关闭** | `SKILL_EMERGENCE_PACKAGING_ENABLED=false` | 联系管理员开启 |
| **后台 worker 正在跑同一轮，本次跳过** | 撞上自动任务 | 等几秒重试（**不是**失败） |
| **本轮执行出错，请查看 API 日志** | DB 故障等 | 查 API 日志 |

## 4. 时间维度：什么时候会被评估

| 环节 | 频率 | 参数 |
| --- | --- | --- |
| 采集 | **实时** | 每轮对话结束即记 |
| 归类 + 建模 | 每 **60 秒**轮询，单轮最多 **20 条** | `SKILL_EMERGENCE_ANALYSIS_INTERVAL_MS` |
| 门禁评估 | **上海时间每天零点**；周期 = `intervalDays`（B 端默认 **1 天**，C 端默认 **7 天**，范围 1–30） | — |
| 封装队列 | 每 **30 秒**轮询，单轮最多 **10 个** | `SKILL_EMERGENCE_PACKAGING_INTERVAL_MS` |
| 证据保留 | **90 天**（看板聚合按 30 天） | — |

**关键结论**：系统不是「攒够就立刻涌现」，而是**周期末统一判断**。
业务上的涌现频率上限 = 周期长度（B 端最快每人每天一次）。

**手动触发可跳过等待**：涌现页的「立即触发」会强制跑完一轮全链路，且**不推进周期**（不影响下次自动评估时间）。

## 5. 想尽快拿到一个涌现 Skill：实操路径

**最快路径（单次长任务通道 D，一次对话即可）**：

1. 确认开关：企业（或你的个人设置）已开启自动涌现；`SKILL_EMERGENCE_MODE=active`
2. 完成**一次足够充实**的对话：
   - 单轮字数 **≥8000 字**，且过程有 **≥5 个明确步骤**，或
   - 过程有 **≥8 个步骤**，或
   - 有 **≥6 次有效工具调用**
   - 并且该任务**确实有步骤结构**（不是零散问答）
3. 等 **≤60 秒**让归类建模跑完
4. 涌现页点「**立即触发**」，不等到零点
5. 看「门禁评估」行是否出现 `评估 1 个`；随后列表出现候选
6. 点「纳入个人」

**更省事的路径（频次通道 A，但需要 5 次）**：

把同一类任务重复做 **5 次**（比如连续 5 天的日报），跨至少 2 个自然日。这条路径不看任务形态，只看次数，是最稳的一条。

**要避免的**：
- 每次都用不同方式描述同一件事 → 被归成不同聚类，谁都攒不够
- 涉及具体人名/项目名的细节 → 会被脱敏，也更容易被归成不同类
- 边做边改的零散追问 → 每个回合独立判定，可能自成一类

## 6. 自查方法

涌现页的「立即触发」会返回三层信息，**从粗到细定位卡点**：

1. **三行阶段摘要** — 归类建模 / 门禁评估 / 封装各自跑了什么、有没有撞锁或出错
2. **链路漏斗** — `成功对话 N 轮 → 已归类 N 条 → 已建模 N 个聚类 → 本轮评估 N 个`
   漏斗在哪一级断掉，卡点就在那里
3. **逐聚类明细**（可展开）— 每个已建模聚类的结论、四通道的「实际 / 门槛 / 差什么」、以及一句可执行的下一步

另外两个辅助入口：
- 平台超管后台 → 基础设置 → 「主动触发涌现」（按企业批量评估全成员）
- 数据库侧：`skill_emergence_evaluations` 表留了完整的判定快照（每次评估的 `freqOk`/`depthOk`/`valueOk`/`singleLongOk` 与各项计数），可用于事后归因

## 附：环境开关清单

测试或排障时可能用到（出现异常的常见原因）：

| 变量 | 含义 |
| --- | --- |
| `SKILL_EMERGENCE_MODE` | `active`（默认，真正建草稿）/ `shadow`（只写评估记录不建候选） |
| `SKILL_EMERGENCE_ANALYSIS_ENABLED` | 归类 + 建模 worker，`false` 即停 |
| `SKILL_EMERGENCE_PACKAGING_ENABLED` | 封装链路熔断开关 |
| `SKILL_EMERGENCE_SCHEDULER_ENABLED` | 上海零点调度器，`false` 即停自动评估 |
| `SKILL_EMERGENCE_ANALYSIS_INTERVAL_MS` | 归类 worker 间隔（默认 60000） |
| `SKILL_EMERGENCE_PACKAGING_INTERVAL_MS` | 封装队列间隔（默认 30000） |
