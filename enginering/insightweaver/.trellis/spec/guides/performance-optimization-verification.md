# Performance Optimization Verification

加载/性能优化类任务的两条硬性验证纪律（源自 2026-08-13 loading-perf P3 verify 实测回退教训）。

## 规则 1：瀑布数据分段归因，目标必须量化对照

**问题**：PRD Goal "首页可交互时间 <1s" 实测 7.9s——方案设计时未用真实网络瀑布数据分段归因各阶段耗时，目标与实测脱节，build 阶段无法拦截。

**要求**：
- 设计阶段先采集目标页面的网络瀑布数据（Performance API resource timing / DevTools waterfall），按阶段列出占比：登录门控 / 目标接口 / 水合依赖 / 渲染
- PRD 验收标准写「实测基线 → 目标值」对照表，每项改动标注预计削减的秒数
- verify 阶段浏览器回归必须重采瀑布数据，与基线逐段对照，不达标的项要么回修要么明确记录偏差原因
- 冷启动（本地无数据）与热启动（有缓存/有本地数据）两个路径都要测

## 规则 2：改变数据加载语义时，枚举所有消费方状态组合

**问题**：bootstrap 改为 `loadSessions({ limit: 1 })` 后，遗漏「面板展开状态 × 企业切换」组合——展开面板在企业切换后只剩 1 条会话（`isHistoryExpanded` 跨切换保持，全量加载只挂在 toggle handler 上）。

**要求**：任何"少拉/延迟拉/本地优先"类改动，逐一枚举消费路径组合：
- 消费方 UI 状态（面板展开/收起、搜索开关）在 scope/enterprise 切换时的保持性
- 各消费方触发加载的时机（挂载、点击、事件）是否覆盖新语义
- 多写入方对同一 state 的"最后写入者"规则（bootstrap limit:1 vs 面板全量 vs 搜索），禁止依赖时序巧合
- 组合测试：展开状态切企业、搜索状态切企业、加载中切企业

## 规则 3：加载态骨架契约（2026-08-13 追加）

**问题**：性能优化把数据提前渲染后，加载态与终态的视觉差异更突出——侧边栏从"迷你"跳变为"完整"、主区从全屏加载提示跳变为工作台。

**要求**：
- 加载中的 DOM 结构必须与最终布局**同构**：结构层（栅格/面板/侧边栏区块）从首帧（SSR）就渲染，加载态只允许在数据填充层显示骨架灰条
- 布局级门控（如 `showSuperLobsterWorkspaceSidebar` 的 `!isBootstrapping`）禁止在结构层生效——结构层用"bootstrap 完成后且明确禁用"才收起
- 骨架与真实内容的切换优先用 CSS 驱动（如 `:has()` 观察 portal 内容），不依赖 React 重渲染时机（实测 MutationObserver 回调中的 setState 在 commit 微任务中被延后/丢失，portal 挂载滞后 0.6-4s）
- 骨架纯灰块无文案（避免 i18n 消息加载前 key 回退文本）
- **常量结构先行渲染（2026-08-15 追加，优于灰块骨架）**：当加载区域的顶层结构是常量（不需等 API，如文件树的个人工作区/共享工作区两个根节点）时，加载期**直接渲染真实组件**（同一份 JSX + 空数据）+ 外层 `inert` 属性（禁鼠标+键盘+焦点+a11y 树）——加载态 = 终态本身 + 交互禁用，零视觉跳变。⚠️ pointer-events:none 只禁鼠标不禁键盘，必须配 `inert`（CR 发现的 Tab+Enter 竞态：加载期键盘操作触发写入与初始加载落地竞态）。bootstrap 中（无基础数据）仍用灰块骨架
- 验收：加载全程采样主区/侧边栏容器 rect，零突变
