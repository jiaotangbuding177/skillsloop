# Internationalization (i18n)

## Overview

The application uses **next-intl v4** for internationalization with two locales:
- **`zh`** (Chinese) - default locale, no URL prefix
- **`en`** (English) - prefixed as `/en/` in URLs

The locale configuration is shared with other packages via `@insightweaver/shared`.

## Configuration

### Routing Config

**File:** `apps/web/src/i18n/routing.ts`

```typescript
import { defineRouting } from 'next-intl/routing';
import { DEFAULT_APP_LOCALE, APP_LOCALES } from '@insightweaver/shared';

export const routing = defineRouting({
  locales: [...APP_LOCALES],          // ['zh', 'en']
  defaultLocale: DEFAULT_APP_LOCALE,  // 'zh'
  localePrefix: 'as-needed',          // zh has no prefix, en gets /en/
  localeCookie: {
    name: 'NEXT_LOCALE',
    maxAge: 60 * 60 * 24 * 365,       // 1 year
  },
});
```

The `localePrefix: 'as-needed'` setting means:
- Chinese pages: `/dashboard`, `/admin/users`, `/billing`
- English pages: `/en/dashboard`, `/en/admin/users`, `/en/billing`

### Next.js Config

**File:** `apps/web/next.config.mjs`

Uses `createNextIntlPlugin` to integrate next-intl with Next.js:

```javascript
import createNextIntlPlugin from 'next-intl/plugin';

const withNextIntl = createNextIntlPlugin('./src/i18n/routing.ts');

const nextConfig = { /* ... */ };
export default withNextIntl(nextConfig);
```

## Middleware Integration

**File:** `apps/web/src/middleware.ts`

The middleware creates an intl middleware instance:

```typescript
import createIntlMiddleware from 'next-intl/middleware';
import { routing } from '@/i18n/routing';

const intlMiddleware = createIntlMiddleware(routing);
```

On each request, after public asset bypass and login redirect checks, the request passes through `intlMiddleware(request)`, which:
- Detects the locale from the URL prefix, cookie, or `Accept-Language` header
- Sets the `x-next-intl-locale` response header
- Rewrites the URL to include the locale parameter for the App Router

## Usage in Components

### useTranslations Hook

The primary API for accessing translations in client components:

```typescript
'use client';
import { useTranslations } from 'next-intl';

export default function BillingPlansPage() {
  const t = useTranslations('admin.billingPlans');
  const tCommon = useTranslations('common');

  return (
    <div>
      <h1>{t('title')}</h1>
      <button>{tCommon('save')}</button>
    </div>
  );
}
```

### Namespace Convention

Each page uses a namespace matching its route segment:
- `admin/billing-plans/page.tsx` -> `useTranslations('admin.billingPlans')`
- `dashboard/page.tsx` -> `useTranslations('dashboard')`
- Shared strings -> `useTranslations('common')` or `useTranslations('errors')`

### Locale-Aware Navigation

Use `useRouter` and `usePathname` from `next-intl/navigation` (not from `next/navigation`):

```typescript
import { useRouter, usePathname, useLocale } from 'next-intl';

function LanguageSwitcher() {
  const router = useRouter();
  const pathname = usePathname();
  const locale = useLocale();

  function switchLocale(newLocale: string) {
    router.replace(pathname, { locale: newLocale });
  }
}
```

## LocaleSyncProvider

Mounted in the locale layout, this provider synchronizes the locale across the application. It ensures that components using `useLocale()` always receive the current locale, and handles locale persistence in the `NEXT_LOCALE` cookie.

## Bilingual Error Messages

Error messages from the backend may arrive in either Chinese or English. The error handler (`src/lib/error-handler.ts`) translates them:

- Chinese messages from backend are passed through directly when the user's locale is `zh`
- English messages are translated to Chinese via pattern matching when locale is `zh`
- The `translateAutoText` utility from `@/lib/i18n/translate-auto-text` provides runtime translation for auto-generated text

See [error-handling.md](./error-handling.md) for the full translation pipeline.

## Public Routes and Locale

Public routes (identified by `isPublicRoute()` in `src/lib/public-routes.ts`) pass through the intl middleware normally. The `(product-landing)` route group contains marketing pages that are publicly accessible and still locale-aware.

The `stripLocalePrefix()` utility from `src/lib/locale-path.ts` is used in middleware to get the path without the locale prefix for route matching.
